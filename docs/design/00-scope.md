# 범위

## 기능 요구사항 (FR)

| ID | 기능 | 넣은 이유 |
|---|---|---|
| FR-1 | 대용량 영상 업로드, 중단 후 재개 | 쓰기 경로. 대역폭과 신뢰성 문제가 모두 여기서 나옴 |
| FR-2 | 비동기 트랜스코딩 (여러 해상도, HLS) | 몇 분씩 걸리는 작업의 실패, 재시도, 멱등성 |
| FR-3 | 스트리밍 재생 (Adaptive Bitrate) | 읽기 경로. 트래픽 대부분이 여기서 나옴 |
| FR-4 | 영상 메타데이터 조회, 채널별 영상 목록 | 읽기가 압도적인 일반 API의 대표 |
| FR-5 | 조회수 집계 | 쓰기 폭주와 최종 일관성 트레이드오프의 대표 |

## 비기능 요구사항 (NFR)

숫자는 W2에 부하 모델과 함께 확정합니다. 아래는 초안입니다.

| ID | 요구사항 | 목표 초안 |
|---|---|---|
| NFR-1 | 재생 가용성 | 99.99% |
| NFR-2 | 업로드 가용성 | 99.9% (재생보다 낮게 잡고 경로를 분리하는 근거) |
| NFR-3 | 재생 시작 지연 | p95 < 2초 |
| NFR-4 | 메타데이터 API 지연 | p99 < 200ms |
| NFR-5 | 원본 내구성 | 업로드 완료된 원본 유실 0 |
| NFR-6 | 일관성 | 업로드 상태는 업로더 본인에게 즉시 반영, 조회수는 수십 초 안에 반영 |
| NFR-7 | 확장성 | 모든 계층이 인스턴스 추가로 수평 확장 |

## 로컬 제약

모든 측정은 아래 조건에서 합니다. 자세한 예산은 `docs/capacity/00-method.md`에 있습니다.

| ID | 제약 | 영향 |
|---|---|---|
| L-1 | M2 Pro 12코어, 메모리 16GB. Docker 할당 약 10GB | 인프라와 레플리카 여러 개를 한 머신 안에 띄워야 함 |
| L-2 | 부하 발생기도 같은 머신에서 돈다 | 서버 프로세스의 자원 사용이 측정을 오염시킴 |

## 범위 밖

| 항목 | 제외 이유 |
|---|---|
| 추천 | ML 영역. 피드 API가 추천 서비스 결과를 받는다는 경계만 그림에 표시 |
| 라이브 스트리밍 | 지연 요구와 프로토콜이 다른 별개 시스템 |
| 광고, Content ID, DRM | 각각이 시스템 하나 규모 |
| 댓글 | 조회수, 메타데이터와 패턴이 겹쳐 새로 얻는 것이 적음 |
| 프론트엔드 | 백엔드 범위. 재생 검증은 ffplay나 정적 HLS 테스트 페이지로 대체 |
