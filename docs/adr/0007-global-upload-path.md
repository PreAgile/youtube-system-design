# ADR-0007: 해외 업로더의 업로드 경로

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-07 |
| 결정일 | 2026-10-07 |
| 관련 FR/NFR | FR-1, NFR-7, NFR-5 |

> **현재 적용 기준(2026-10-10):** [ADR-0009](0009-all-renditions-ready.md)가 관련 완료 용어·공개 조건·시간 목표를 부분 대체한다. 이 기록의 업로드 완료·완료 판정은 원본 전송·검증 완료를 뜻한다. 서비스의 업로드 완료·재생 가능은 대상 화질 전체와 매니페스트 준비 이후다. 원본 전송 시간과 그 이후의 전체 준비 시간을 분리하며, 전송 시간 수치 목표는 여전히 없다. 해외 전송 경로 선택은 유지한다. 아래 본문은 당시 결정 기록이다.

## 1. 문제와 제약

업로드는 청크를 한국 리전 Storage에 직접 올리고 재개·완료 때 Storage를 조회한다([ADR-0001](0001-upload-progress-and-completion.md)). 브라질 업로더가 최대 20GB 원본을 올리면 지역 간 RTT가 길어 연결 하나의 처리량이 떨어지고, 업로드가 길어질수록 끊길 확률도 커진다. 완료 응답을 준 원본은 잃어버리지 않아야 하고(NFR-7), 업로드 후 변환은 바로 시작되어야 한다(NFR-5). 문제 카드에는 업로드 속도 목표가 없다.

계산[가정: 업로더 업로드 대역폭 20Mbps, 먼 RTT에서 연결 하나가 5Mbps만 낼 때]: 20GB(160Gb)는 회선을 다 쓰면 약 2.2시간, 연결 하나 5Mbps면 약 8.9시간이다. TCP 처리량이 RTT에 대략 반비례한다는 일반적 성질에 기댄 설명이며 측정값이 아니다.

## 2. 대안과 판단 기준

기준은 (1) 완료 후 보존(NFR-7)과 "진행 기준은 Storage 한 곳"(ADR-0001) 유지, (2) 먼 RTT로 인한 처리량 손실 완화, (3) 변환 시작까지의 지연(NFR-5), (4) 운영 부품과 비용이다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| CDN·지역 캐시에 업로드를 캐시했다가 한국에서 요청 시 가져오기(사용자 첫 제안) | 사용자 가까이에서 받는다 | 캐시는 업로드(PUT·POST)를 저장하지 않고 원본으로 전달한다([CloudFront 문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html#CloudFrontRegionaledgecaches)). 캐시는 언제든 지워져 NFR-7을 보장하지 못한다. 변환은 요청을 기다리지 않고 바로 원본이 필요하다 |
| A. 한국 Storage 직접 + 청크 병렬 업로드 | ADR-0001을 바꾸지 않는다. 연결 수로 처리량 손실을 메운다 | 연결이 많아지고 RTT 자체는 그대로다 |
| B. 가까운 엣지가 받아 사업자 망으로 한국 Storage에 중계 | Client 쪽 연결의 RTT가 짧아진다. 저장 기준은 여전히 한국 Storage | 추가 전송 요금. 엣지는 저장하지 않으므로 Storage가 받은 뒤에 성공 응답이 온다 |
| C. 가까운 리전 Storage에 저장 후 한국으로 비동기 복제(또는 그 리전에서 변환) | 완료가 빠르다 | 업로드 세션·재개·완료 조회가 리전별로 나뉜다. 복제 시간이 변환 시작을 늦추거나 리전마다 변환 작업자가 필요하다 |

B의 예: AWS S3 Transfer Acceleration은 CloudFront 엣지에서 데이터를 받아 최적화된 경로로 S3에 보낸다([문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/transfer-acceleration.html)). 특정 제품을 선택한 것은 아니다.

## 3. 사용자 제안과 검토

- 사용자 첫 제안: 브라질 CDN이 업로드 청크를 캐시하고 지역 중간 캐시가 다시 캐시한 뒤, 한국에서 처음 요청이 오면 가져온다.
- 면접관 검토(LLM): 사용자 가까이에서 받는 방향은 맞지만 캐시는 쓰기를 저장하지 않고 보존을 보장하지 않는다. 실제 문제는 먼 RTT의 연결당 처리량 저하다. A·B·C를 비교하고 A + B를 추천했다.
- 사용자는 A + B를 고르며 "엣지 중계 서버가 백그라운드로, 비동기로 한국 Storage에 올린다"고 표현했다. 검토에서 B는 비동기가 아니라 중계라는 점을 바로잡았다. 엣지가 먼저 성공을 응답하고 나중에 한국으로 보내면 그 사이 데이터는 엣지에만 있어 캐시안과 같은 보존 문제가 생긴다.

## 4. 결정과 이유

사용자가 A + B를 선택했다.

- Client는 청크 여러 개를 동시에 서로 다른 연결로 올린다. 각 청크는 ADR-0001대로 독립적으로 재개된다.
- 청크 업로드 URL은 가까운 엣지를 가리킨다. 엣지는 청크를 저장하지 않고 사업자 망으로 한국 Storage에 바로 전달하며, Storage가 청크를 저장한 뒤에야 Client가 성공 응답을 받는다.
- 시작·재개·완료 같은 제어 요청과 Storage 조회, 완료 판정은 ADR-0001 그대로다.

이유(사용자): 한국 Storage에 직접 올리는 구조를 유지하면서, 청크를 병렬로 올리고 장거리 구간은 엣지와 사업자 망이 맡게 한다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 진행 기준과 완료 판정이 한국 Storage 한 곳으로 유지된다. Client 쪽 RTT가 짧아지고 병렬 연결로 처리량 손실을 줄인다. 변환 시작 지연이 늘지 않는다.
- 비용: 엣지 중계의 추가 전송 요금, 병렬 연결 수만큼의 동시 연결.

## 6. 검증과 남은 불확실성

- 미검증: 엣지 중계와 병렬 업로드로 실제 업로드 시간이 얼마나 줄어드는지. 지역별로 직접 업로드와 비교 측정해야 한다.
- 병렬 연결 수와 청크 크기는 측정 후 정한다.
- 업로드 속도 목표(NFR)는 추가하지 않았다. 목표가 생기면 이 결정을 그 기준으로 다시 확인한다.

## 7. 재검토 조건

- 측정한 업로드 시간이 목표에 못 미칠 때 C(가까운 리전 저장 후 복제)를 검토한다.
- 데이터를 업로더 지역에 저장해야 하는 요구가 생길 때.
- 엣지 중계 비용이 업로드량에 비해 과도할 때.
