# ADR-0006: 글로벌 재생 전달과 캐시 수명

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-06 |
| 결정일 | 2026-10-06 |
| 관련 FR/NFR | NFR-2, NFR-4, NFR-6, FR-2, FR-3 |

## 1. 문제와 제약

저장소·백엔드·RDB가 한국 리전에만 있으면 브라질 시청자의 재생 시작이 NFR-2(기준 p95 ≤ 2초, 취약 p95 ≤ 4초)를 넘는다. 재생 방식은 4초 세그먼트 + 매니페스트, client 판단, HTTP다([ADR-0005](0005-playback-segments.md)). 세그먼트는 시도별 경로라 한 번 만들면 바뀌지 않지만([ADR-0004](0004-transcoding-failure-handling.md)), 화질이 준비될수록 매니페스트와 재생 정보는 바뀐다. 피크 전송량은 약 15.6Tbps다[계산: 625만 × 2.5Mbps].

재생 시작 계산[가정: 서울–상파울루 지역 간 RTT 약 300ms, CDN 지점까지 접근 RTT + 20ms, API 쪽 왕복 2회 + 영상 쪽 왕복 3회, 360p 4초 첫 세그먼트, 손실·디코딩 제외]:

| 구성 | 기준 네트워크 | 취약 네트워크 |
|---|---|---|
| 한국만 | 약 2.0초 | 약 4.9초 |
| 영상만 CDN, 캐시 적중 | 약 1.2초 | 약 4.0초 |
| 영상만 CDN, 캐시 미스(한국 원본 2회) | 약 1.8초 | 약 4.6초 |
| 재생 정보도 가까이 + 영상 CDN | 약 0.6초 | 약 3.5초 |

## 2. 대안과 판단 기준

기준은 (1) 캐시 적중·미스 모두에서 NFR-2 충족, (2) 롱테일 영상의 저장·전송 낭비, (3) 원본 부하, (4) 화질 추가가 시청자에게 반영되는 지연, (5) 운영 부품 수다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| 영상: 한국 원본만 | 부품이 없다 | NFR-2를 넘고 원본이 전체 전송량을 감당한다 |
| 영상: CDN pull | 필요한 영상만 캐시해 낭비가 없다 | 지점의 첫 시청자는 캐시 미스로 느리다 |
| 영상: CDN push | 첫 시청자도 빠르다 | 롱테일까지 모든 지점에 복사하면 낭비가 크다 |
| 영상: 원본 다중 리전 복제 + CDN | 캐시 미스도 가까운 리전에서 끝난다 | 리전 수만큼 저장·복제 운영 |
| 재생 정보: 한국 API 유지 | 단순하다 | 취약 네트워크에서 API 왕복만 약 1.2초 |
| 재생 정보: CDN 짧은 캐시 | 공개 영상은 누구에게나 같은 응답이라 캐시할 수 있다 | 상태 변화가 캐시 수명만큼 늦게 보인다. 사용자별 응답은 캐시할 수 없다 |
| 재생 정보: 지역 API + RDB 읽기 복제본 | 사용자별 응답도 가깝게 처리한다 | 리전마다 서버·복제 운영, 복제 지연 |
| 재생 정보: 왕복 줄이기 | 순차 왕복이 줄어든다 | 응답 구조가 복잡해진다 |
| 매니페스트: 같은 URL + 수명 조절 또는 강제 삭제 | 경로가 하나다 | 길면 화질 추가가 늦게 반영되고, 짧으면 원본 확인 요청이 계속되며, 강제 삭제는 즉시 반영을 보장하지 않는다 |
| 매니페스트: 버전 경로 | 모든 버전이 바뀌지 않아 길게 캐시한다 | 버전 번호 경합을 처리해야 한다 |

## 3. 사용자 제안과 검토

- 사용자 첫 제안: CDN을 전 세계 여러 곳에 두고 한국에서 올린 영상의 정적 결과물을 브라질 CDN에 저장하거나 캐싱해 바로 내준다.
- 면접관 검토(LLM): 재생 정보 API가 한국에 남으면 취약 네트워크 목표를 넘는다. push와 pull의 차이, 롱테일 낭비, 캐시 미스 비용, 세그먼트와 매니페스트·재생 정보의 수명 차이를 제시했다.
- 사용자는 push 기준을 처음에 "재생 수가 많은 영상"으로 제안했다. 검토에서 이미 몰린 뒤에는 pull 캐시에 이미 있어 효과가 작다는 점을 확인하고 예측 신호로 바꿨다.
- 사용자는 매니페스트 수명을 처음에 영상 성격별(push는 길게, 나머지는 중간·짧게)로 제안했다. 검토에서 인기 새 영상일수록 공개 직후 화질이 추가되어 길게 캐시하면 360p에 고정된다는 점을 확인하고 버전 경로로 바꿨다.

## 4. 결정과 이유

사용자가 다음을 선택했다.

- 영상 경로: CDN pull을 기본으로 하고, 지점에 없으면 지역 중간 캐시(예: 남미), 그래도 없으면 한국 원본에서 가져온다. 이유(사용자): 첫 시청자는 잠시 느릴 수 있지만 이후 같은 영상의 세그먼트를 받는 시청자는 빠르게 본다.
- 선택적 push: 채널 구독자 수와 공개 직후 요청 증가 속도를 기준으로 시청이 몰릴 영상을 판단하고, 첫 세그먼트 몇 개만 미리 넣는다. 공개 조회수 기능이 아니라 내부 요청 신호를 쓴다.
- 매니페스트: 화질이 준비될 때마다 새 버전 경로(manifest-vN)로 만들고 길게 캐시한다. 내용은 그 시점 RDB의 준비된 화질 목록으로 만들고, 버전 번호는 RDB 조건부 갱신으로 올린다. 사용자는 같은 URL을 덮어쓸 때 지점들이 변경을 모른다는 설명을 확인하고 동의했다.
- 재생 정보: 공개 영상의 재생 정보(재생 가능 여부, 최신 매니페스트 위치)를 CDN에서 몇 초 수명으로 캐시하고, 순차 왕복을 줄이는 방법을 함께 쓴다. 짧은 수명이 필요한 곳은 재생 정보 하나다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 캐시 적중 시 계산상 취약 네트워크에서도 NFR-2를 충족한다. 롱테일 영상의 낭비 없이 인기 영상의 첫 시청도 빠르게 한다. 세그먼트·매니페스트는 캐시 삭제가 필요 없다. 한국 백엔드에 잠깐 장애가 나도 캐시된 재생 정보로 공개 영상 재생이 이어진다(NFR-6).
- 비용: CDN 전송 비용과 중간 캐시 운영. 지점·중간 캐시 모두 미스인 첫 시청자는 느리다. 재생 가능 상태와 새 화질은 재생 정보 수명만큼 늦게 보인다. 매니페스트 버전 경합을 처리해야 한다.

## 6. 검증과 남은 불확실성

- 계산의 지역 간 RTT, 지점 추가 RTT, 순차 왕복 횟수는 가정이며 측정하지 않았다.
- 용어: 여기서 "중간 캐시"는 지역마다 두는 계층형 캐시의 중간층으로, AWS CloudFront Regional Edge Cache에 해당한다([문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html#CloudFrontRegionaledgecaches)). 원본 근처 한 곳에 미스를 모으는 Origin Shield([문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html))나 Fastly Shielding과는 다른 층이며, 이 결정에는 포함하지 않았다. 2026-10-07 용어를 Shield에서 Regional cache로 바로잡았다(결정 내용 변경 아님).
- 중간 캐시가 있을 때 캐시 미스의 실제 재생 시작 시간과 지역별 캐시 적중률은 측정해야 한다.
- 재생 정보 캐시 수명(몇 초)과 push 기준값(구독자 수, 증가 속도 임계치), push할 세그먼트 수는 정책값으로 남아 있다.
- CDN 단가를 확인하지 않아 비용 비교는 하지 않았다.
- 비공개 영상 권한, 세그먼트 접근 통제가 범위에 들어오면 재생 정보 캐시가 성립하지 않을 수 있다.

## 7. 재검토 조건

- 중간 캐시를 두어도 캐시 미스 재생 시작이 NFR-2를 넘을 때 원본 다중 리전 복제를 검토한다.
- 비공개 영상, 기기 간 이어보기처럼 사용자별 재생 정보가 필요해질 때 지역 API + 읽기 복제본을 검토한다.
- 재생 정보 수명 때문에 화질 추가 반영 지연이 문제로 측정될 때.
