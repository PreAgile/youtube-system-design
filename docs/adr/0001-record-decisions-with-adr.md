# ADR-0001: 설계 결정을 ADR로 기록한다

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-09-28 |
| 결정일 | 2026-09-28 |
| 관련 FR/NFR | 전체 |
| 관련 ADR | 없음 |

## 1. 맥락

이 프로젝트는 매주 멘토 세션에서 설계를 발표하고 "왜"에 대한 질문을 받습니다. 결정의 근거가 코드와 대화에 흩어지면, 몇 주 뒤에는 무엇을 왜 골랐는지 스스로도 복원하기 어렵습니다.

## 2. 결정을 강제하는 요구사항

| 요구사항 | 이 결정에 주는 제약 |
|---|---|
| 모든 결정의 이유를 방어할 수 있어야 함 | 대안과 버린 이유까지 남아 있어야 함 |
| 결정자는 본인 | 초안과 결정을 분리해야 함 |

## 3. 선택지

- A. 결정마다 ADR 파일 하나, 고정 템플릿
- B. 설계 문서 안에 결정 이유를 서술
- C. 기록하지 않고 커밋 메시지에 남김

## 6. 추천안

A. 고정 템플릿이면 모든 결정이 같은 질문(대안, 비용, 깨지는 조건, 운영 지표)을 통과하게 되고, 그 순서가 그대로 면접 답변 순서가 됩니다.

## 7. 결정

A로 한다. 초안은 Proposed로 올리고, 7번 섹션은 결정자가 직접 쓴다.

## 8. 결과

- 비용: 결정 하나마다 문서 작성 시간이 든다.
- 규칙: Accepted된 ADR은 수정하지 않고 새 ADR로 대체한다. 생각이 바뀐 과정 자체가 기록으로 남는다.

## 9. 이 결정이 깨지는 조건

ADR 작성이 구현보다 느려져 주차 목표를 계속 놓치면, 작은 결정은 ADR 대신 설계 문서의 "결정 메모"로 낮춘다.
