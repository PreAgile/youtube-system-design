# ADR-0001: 설계 결정을 ADR로 기록한다

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-09-28 |
| 결정일 | 2026-09-28 |
| 관련 FR/NFR | 전체 (프로젝트 운영 방식) |
| 관련 ADR | 없음 |

## 1. 맥락

이 프로젝트는 매주 멘토 세션에서 설계를 발표하고 "왜"에 대한 질문을 받습니다. 결정의 근거가 코드와 대화에 흩어지면, 몇 주 뒤에는 무엇을 왜 골랐는지 스스로도 복원하기 어렵습니다. 리뷰 봇과 CI가 결정의 논리를 검증하려면, 검증할 대상이 정해진 형태로 있어야 합니다.

## 2. 결정을 강제하는 요구사항

| 요구사항 | 이 결정에 주는 제약 |
|---|---|
| 모든 결정의 이유를 방어할 수 있어야 함 | 대안과 버린 이유까지 남아 있어야 함 |
| 결정자는 본인 | 초안(추천)과 결정을 분리해야 함 |
| 리뷰 봇과 CI가 검증해야 함 | 기계가 읽을 수 있는 고정 구조가 필요함 |

## 3. 선택지

### A. 결정마다 ADR 파일 하나, 고정 템플릿

- 장점: 모든 결정이 같은 질문을 통과한다. CI가 구조를 검사할 수 있다
- 단점: 결정마다 작성 비용이 든다

### B. 설계 문서 안에 결정 이유를 서술

- 장점: 맥락과 결정이 한곳에 있어 읽기 편하다
- 단점: 결정 단위로 추적, 대체, 검증하기 어렵다. 결정이 바뀌면 과거 근거가 덮어써진다

### C. 커밋 메시지와 PR 본문에만 남김

- 장점: 추가 문서가 없다
- 단점: 결정을 한눈에 볼 수 없고, 봇과 CI가 검증할 대상이 흩어진다

## 4. 평가

| 기준 | 가중치 | A | B | C |
|---|---|---|---|---|
| 결정 단위 추적과 대체 | 상 | 유리 | 불리 | 불리 |
| CI, 봇 검증 가능성 | 상 | 유리 | 불리 | 불리 |
| 작성 비용 | 중 | 불리 | 보통 | 유리 |

## 5. 결정 전 검증

해당 없음. 도입 비용이 작고, 9번 조건으로 언제든 되돌릴 수 있습니다.

## 6. 추천안

A. 고정 템플릿이면 모든 결정이 같은 질문(대안, 비용, 깨지는 조건, 운영 지표)을 통과하고, 그 순서가 그대로 면접 답변 순서가 됩니다.

## 7. 결정

A로 한다. 초안은 Proposed로 올리고, 7번 섹션은 결정자가 직접 쓴다.

## 8. 결과

- 비용: 결정 하나마다 문서 작성 시간이 든다.
- 규칙: Accepted된 ADR은 수정하지 않고 새 ADR로 대체한다. CI가 이를 강제한다. 생각이 바뀐 과정 자체가 기록으로 남는다.

## 9. 이 결정이 깨지는 조건

ADR 작성이 구현보다 느려져 2주 연속 주차 목표를 놓치면, 영향 범위가 한 모듈 안에 머무는 작은 결정은 ADR 대신 설계 문서의 "결정 메모"로 낮춘다.

## 10. 운영에서 볼 지표와 장애 대응

| 지표 | 정상 범위 | 벗어나면 의심할 것 | 대응 |
|---|---|---|---|
| Proposed 상태로 2주 넘게 남은 ADR 수 | 0 | 결정이 미뤄지고 있음 | 다음 멘토 세션 안건으로 올림 |
| ADR 없이 머지된 결정 | 0 | 리뷰 누락 | 사후 ADR 작성 |

## 11. 예상 꼬리질문

| 질문 | 답의 요지 |
|---|---|
| 혼자 하는 프로젝트에 ADR은 과하지 않나? | 혼자라서 더 필요하다. 반박해 줄 동료가 없으니 결정을 고정된 질문에 통과시키는 장치가 필요하다 |
| Accepted ADR을 왜 고치지 않나? | 결정이 바뀐 이유가 곧 학습 기록이다. 덮어쓰면 그 과정이 사라진다 |
