# ADR-0001: 업로드 바이트 경로와 진행 상태의 기준, 완료 판정

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-05 |
| 결정일 | 2026-10-05 |
| 관련 FR/NFR | FR-1, FR-2, NFR-6, NFR-7 |

> **현재 적용 기준(2026-10-10):** [ADR-0009](0009-all-renditions-ready.md)가 관련 완료 용어·공개 조건·시간 목표를 부분 대체한다. 이 기록의 완료 응답은 현재 원본 전송·검증 완료 응답으로 해석한다. 서비스의 업로드 완료·재생 가능은 대상 화질 전체와 매니페스트 준비 이후다. 저장소 직접 조회와 원본 확정 방식은 유지한다. 아래 본문은 당시 결정 기록이다.

## 1. 문제와 제약

원본은 평균 600MB, 최대 20GB이고 재개 유효 기간은 7일이다(문제 카드 가정). FR-1은 중단 후 이미 전송이 확인된 부분을 활용해 이어 올리고, 원본 전체의 크기·무결성과 보존 조건을 확인한 뒤 완료 응답을 주라고 요구한다. NFR-7은 완료 응답을 받은 원본을 저장 장치 또는 가용 영역 하나의 장애에서 복구할 수 있어야 한다고 요구한다. NFR-6은 업로드 장애 중에도 기존 영상 재생 목표를 유지하라고 요구한다.

바이트를 저장소로 직접 보내면 백엔드는 전송을 직접 보지 못한다. 그래서 "어느 청크까지 저장됐는가"의 기준과 "완료"를 확정하는 주체를 정해야 한다.

## 2. 대안과 판단 기준

판단 기준은 우선순위 순으로 (1) 진행 기준이 실제 바이트와 어긋나지 않을 것, (2) 완료 응답 전에 크기·무결성을 검증할 수 있을 것, (3) 움직이는 부품이 적을 것이다. (1)·(2)는 FR-1·NFR-7의 완료 의미를 지키고, (3)은 최소 구조 단계의 단순성을 위한 것이다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| A. client가 청크마다 백엔드에 보고하고 RDB를 기준으로 삼음 | 구현이 단순하고 백엔드가 진행률을 바로 안다 | 저장 성공 후 보고 전에 끊기면 재전송이 생긴다. client 버그·거짓 보고 시 RDB가 실제와 어긋난다. 무결성 검증은 별도로 필요하다 |
| B. 저장소 이벤트를 받아 RDB에 반영하고 RDB를 기준으로 삼음 | RDB가 저장소보다 앞서지 않는다. client 보고에 의존하지 않는다 | 이벤트 지연·중복·순서 뒤바뀜에 멱등 처리가 필요하다. 누락 시 결국 저장소 재조회가 필요하다. 멀티파트 방식은 파트별 이벤트가 없을 수 있다(S3 기준 외부 사실, 미검증) |
| C. 재개·완료 시 백엔드가 저장소를 직접 조회해 기준으로 삼음 | 진행 기준이 바이트가 있는 한 곳뿐이다. 완료 시 한 번에 검증한다. 추가 이벤트 경로가 없다 | 재개마다 저장소 조회가 늘어난다. 청크가 많으면 목록을 여러 번 나눠 받아야 한다 |

## 3. 사용자 제안과 검토

- 첫 제안: client → 백엔드(API) → 객체 저장소(영상) + RDB(메타데이터).
- 바이트 경로(사용자 제안): client가 청크로 나누고, 백엔드가 업로드 메타데이터를 RDB에 기록한 뒤 청크별 업로드 URL을 발급하며, client가 저장소에 직접 올린다. 이유는 전송 부담을 client 쪽에 두어 백엔드와 무관하게 끊기지 않게 올리기 위해서다. 중단·재개 같은 제어 정보는 백엔드를 거쳐 RDB에 둔다.
- 진행 기준(사용자 첫 제안): B. 면접관 검토에서 이벤트 지연·중복·누락, 파트별 이벤트 부재 가능성, 무결성 검증 부재를 반례로 확인했다.
- 면접관 추천(LLM 제안): C. 사용자는 "client가 청크 3을 저장한 뒤 보고 전에 끊긴 경우" 흐름을 단계별로 확인한 뒤 C를 선택했다.

## 4. 결정과 이유

사용자가 C를 선택했다. 이유는 "가장 편하고 좋다", 즉 기준이 한 곳이라 단순하다는 것이다.

- 업로드 시작: client가 크기·청크 수를 알리면 백엔드가 RDB에 업로드 세션을 기록하고 업로드 URL을 발급한다.
- 청크 업로드: client가 저장소에 직접 올리고 저장소의 응답으로 청크 성공을 안다. 백엔드·RDB는 청크별 진행을 기록하지 않는다.
- 재개: 백엔드가 저장소에서 이미 저장된 청크를 조회해 남은 청크를 알려준다.
- 완료: client가 완료를 요청하면 백엔드가 모든 청크·전체 크기·체크섬을 저장소에서 확인하고 원본을 확정한 뒤 RDB 상태를 업로드 완료로 바꾸고 동기 응답한다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: RDB와 저장소의 진행 기록을 맞출 필요가 없다. 완료는 백엔드가 검증한 뒤에만 확정된다. 업로드 바이트가 백엔드를 지나지 않아 백엔드 재배포·장애가 진행 중인 전송을 끊지 않는다.
- 비용: 재개마다 저장소 조회가 한 번 늘어난다. 재개는 드문 동작이라 감당할 수 있다고 본다. 다른 화면에 업로드 진행률을 보여주려면 별도 방법이 필요하다.

## 6. 검증과 남은 불확실성

- 미검증: 선택할 저장소가 청크 목록 조회, 청크별 체크섬, 원본 병합을 어떤 조건으로 제공하는지 확인해야 한다.
- 미검증: 재개 유효 기간(7일)이 지난 미완료 청크의 정리 방식.
- NFR-7의 보존 조건을 저장소 자체 성질로 만족하는지, 별도 복제가 필요한지는 저장소를 비교할 때 확인한다.

## 7. 재검토 조건

- 업로드 진행률을 다른 기기·화면에서 실시간으로 보여줘야 하는 요구가 생길 때.
- 재개 빈도나 청크 수가 커져 재개 시 저장소 조회 비용이 문제가 될 때.
- 저장소가 청크 목록 조회나 검증 수단을 제공하지 않을 때.
