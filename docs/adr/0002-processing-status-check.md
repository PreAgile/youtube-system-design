# ADR-0002: 처리 상태 확인 방식

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-05 |
| 결정일 | 2026-10-05 |
| 관련 FR/NFR | FR-2, NFR-5 |

## 1. 문제와 제약

업로드 완료는 완료 요청의 동기 응답으로 알린다([ADR-0001](0001-upload-progress-and-completion.md)). 그 뒤의 변환은 서버가 스스로 진행하고 기준 화질 준비까지 p95 5분이 걸릴 수 있다(NFR-5). FR-2는 업로더가 처리 중·재생 가능·실패와 준비된 화질을 조회할 수 있어야 한다고 요구한다. client가 이 상태 변화를 알 방법을 정해야 한다.

## 2. 대안과 판단 기준

기준은 (1) 현재 규모에서의 부하, (2) 서버가 연결 상태를 기억해야 하는지와 운영 복잡도, (3) 상태 반영 지연이다. 요구사항에 실시간 반영 목표가 없으므로 (2)를 (3)보다 우선한다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| 폴링 | 서버가 연결을 기억하지 않는다. 스케일 아웃된 어느 서버든 RDB 상태를 읽어 답한다 | 상태가 바뀌지 않아도 요청이 반복된다. 반영 지연은 최대 조회 간격 |
| SSE | 상태 변화가 있을 때만 메시지를 보낸다. 반영이 거의 즉시다 | 연결을 유지해야 한다. 변환 완료 소식을 연결을 가진 서버까지 전달하는 경로가 필요하다. 재배포·중간 장비 타임아웃 때 재연결이 몰릴 수 있다 |

## 3. 사용자 제안과 검토

- 사용자가 처음 "SSE는 서버 부담이 더 크지 않나"라고 질문했다.
- 면접관 검토(LLM): 요청 수로는 SSE가 오히려 적다. 처리 중 영상 약 1,740개 [계산] 기준으로 5초 폴링은 초당 약 350건, 3초 폴링은 약 580건(피크 3배 약 1,740건)이고, SSE는 영상당 상태 변화 4~5회다. 차이는 부하보다 연결 유지와 이벤트 전달 경로의 복잡도라고 설명했다.
- 면접관 보충: SSE 재연결은 상태를 RDB에 두고 마지막 이벤트 ID로 이어받으면 반드시 같은 서버일 필요는 없다. 다만 새 상태 변화를 연결을 가진 서버까지 전달하는 경로는 여전히 필요하다.

## 4. 결정과 이유

사용자가 폴링을 선택했다. 이유: 이 규모에서는 부하가 작고, 3초마다 조회해도 RDB·백엔드에 부담이 크지 않다. 스케일 아웃된 서버에서도 stateless하게 조회하므로 단순하다. SSE는 요청을 상태 변화 횟수만큼으로 줄일 수 있지만 연결을 기억하는 stateful 구조, 연결을 가진 서버로의 라우팅, 끊김 후 재연결·재개 처리라는 복잡성이 생긴다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 상태 확인 API가 stateless하고 기존 API 서버에서 그대로 처리된다. 별도 연결 관리나 이벤트 전달 경로가 없다.
- 비용: 상태가 바뀌지 않은 조회가 반복된다. 상태 반영이 최대 조회 간격만큼 늦다. 현재 규모와 NFR-5에서는 감당할 수 있다고 본다.

## 6. 검증과 남은 불확실성

- 계산은 하루 업로드 50만 개와 처리 시간 5분 가정에서 나온 값이며 측정값이 아니다.
- 조회 간격(3~5초)과 처리 완료·실패 후 조회를 멈추는 조건은 API 설계 때 정한다.

## 7. 재검토 조건

- 상태 조회가 RDB·서버에 실제 부담이 될 만큼 동시 조회가 늘어날 때.
- 하나의 상태 화면을 매우 많은 client가 동시에 지켜보는 기능이 생길 때.
- 몇 초 지연도 허용되지 않는 상태 반영 요구가 생길 때.
