# ADR-0006: 업로드 방식

| 항목 | 값 |
|---|---|
| 상태 | Proposed |
| 분류 | 제품 설계 |
| 작성일 | 2026-09-29 |
| 결정일 | |
| 관련 FR/NFR | FR-1 재개 가능한 업로드, NFR-2 업로드 가용성, NFR-5 원본 보존, NFR-6 read-your-writes, NFR-7 멱등과 격리, NFR-8 비용 |
| 관련 ADR | ADR-0002 언어, ADR-0005 메타데이터 저장소, ADR-0010 Outbox |

## 1. 맥락

크리에이터가 올린 원본 바이트가 **어떤 경로로 객체 스토리지까지 가는지**, 그리고 **끊긴 업로드를 어떻게 이어 보내는지**를 정합니다. 이 결정이 W2의 API 명세(업로드 흐름)와 W4 구현(업로드 중단과 재개 데모)을 막고 있습니다.

이 ADR이 정하지 않는 것도 있습니다. 업로드 완료 뒤 트랜스코딩 작업을 발행하는 원자성은 ADR-0010, 업로드 상태를 저장할 DB는 ADR-0005, 먼 지역 사용자의 업로드 가속은 ADR-0012에서 정합니다.

### 업로드 경로의 부하 모양

수치는 `docs/design/00-scope.md`의 트래픽 가정에서 가져왔습니다.

| 항목 | 값 | 설계에 주는 의미 |
|---|---|---|
| 업로드 수 | 하루 50만 편, 피크 초당 약 17건 | 요청 수로는 가장 작은 경로 |
| 원본 크기 | 평균 약 300MB, 최대 256GB 또는 12시간([YouTube 고객센터](https://support.google.com/youtube/answer/71673)) | 수백 GB 파일과 수십 시간 전송을 전제해야 함 |
| 원본 유입 | 평균 약 14Gbps, 피크 약 42Gbps | 이 바이트가 지나는 계층은 대역폭 기준으로 크기를 정해야 함 |
| 동시 업로드 (가정) | 피크 42Gbps를 크리에이터 평균 업로드 속도 20Mbps로 나누면 약 2,100개 | 연결 하나가 수 분에서 수십 시간 유지됨 |
| 전송 환경 | 지하철에서 시작해 집 Wi-Fi에서 끝남 (범위 문서 도입부) | 끊김이 예외가 아니라 기본값 |

이 경로는 **요청 수가 아니라 바이트와 연결 시간으로 커집니다.** 그래서 질문은 "누가 이 바이트를 받는가"와 "끊기면 어디서부터 다시 보내는가"입니다.

## 2. 결정을 강제하는 요구사항

### 필수 조건 (하나라도 못 맞추면 탈락)

| 요구사항 | 제약 |
|---|---|
| FR-1 | 끊긴 지점부터 다시 보낼 수 있어야 함. 256GB 파일을 처음부터 다시 보내게 하면 안 됨 |
| NFR-5 | 업로드 완료 응답을 준 원본은 유실되지 않아야 함. 완료 응답은 원본이 내구성 있는 저장소에 다 쓰인 뒤에만 나가야 함 |
| NFR-7 격리 | 업로드 바이트가 메타데이터 API의 대역폭, 연결, CPU를 빼앗지 않아야 함 |
| NFR-7 멱등 | 완료 요청이 두 번 와도 영상이 두 개 생기거나 트랜스코딩이 두 번 발행되지 않아야 함 |
| NFR-6 | 크리에이터는 완료 직후 자기 영상이 "처리 중"으로 보여야 함 |

### 결정 기준 (우선순위 순)

| 순위 | 기준 | 연결 요구사항 | 우선순위의 이유 |
|---|---|---|---|
| 1 | **바이트가 지나는 계층을 우리가 운영해야 하는가** | NFR-2, NFR-7 | 그 계층은 42Gbps와 수십 시간짜리 연결을 들고 있어야 하고, 배포할 때마다 진행 중인 전송이 끊기며, 업로드 경로에 직렬로 붙는 장애 지점이 됨 |
| 2 | **업로드 중에 우리가 통제할 수 있는 것** | NFR-8, NFR-2 | 잘못된 파일을 일찍 거절하고, 남용을 멈추고, 저장 비용을 제한할 수 있는가 |
| 3 | **클라이언트가 치르는 복잡도** | FR-1 | 재개 로직을 누가, 얼마나 짜야 하는가 |

### 전제

- 원본 저장소는 S3 호환 객체 스토리지입니다. 프로덕션은 S3 또는 호환 서비스, 로컬은 MinIO입니다.
- 업로드 클라이언트는 우리가 만드는 앱과 웹입니다. 제3자가 쓰는 공개 업로드 API는 범위 밖입니다(9장).

## 3. 선택지

### 후보

| 후보 | 설명 |
|---|---|
| A. API 서버 경유 | 메타데이터 API가 바이트를 받아 스토리지에 씀 |
| B. Presigned 단일 PUT | API가 서명 URL 하나를 주고, 클라이언트가 파일 전체를 한 번에 스토리지로 PUT |
| C. Presigned Multipart | API가 멀티파트 업로드를 열고 파트별 서명 URL을 주면, 클라이언트가 파트 단위로 스토리지에 직접 PUT. 끊기면 안 올라간 파트만 다시 보냄 |
| D. 전용 업로드 수신 계층 + 오프셋 재개 프로토콜 | 메타데이터 API와 분리된 업로드 전용 서버군이 바이트를 받아 스토리지로 흘려 씀. 재개는 [tus](https://tus.io/protocols/resumable-upload)처럼 "서버가 받은 오프셋을 알려 주고 그 뒤부터 이어 보냄" 방식 |
| E. 스토리지 벤더 고유의 재개 세션 | GCS resumable upload처럼 벤더 API로 오프셋 재개 |

### 거르는 방법

| 단계 | 질문 | 통과 | 떨어진 후보와 이유 |
|---|---|---|---|
| 1 | 필수 조건을 충족하는가 | C, D, E | A는 NFR-7 격리 위반. 피크 42Gbps와 연결 2,100개가 메타데이터 API를 지남(범위 문서 도입부의 "가장 단순한 구현"). B는 FR-1 위반. 단일 PUT은 재개가 없고, S3는 단일 PUT을 5GB로 제한함([S3 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html)) |
| 2 | 전제(S3 호환 저장소)에 맞는가 | C, D | E는 모양이 C와 같지만(바이트가 스토리지로 직접 감) 특정 벤더 API에 묶임. C가 같은 이점을 S3 호환 API로 얻음 |
| 최종 | C와 D 비교 | 4장 | |

**D가 가장 강한 대안입니다.** 실제 YouTube Data API가 이 모양입니다. 세션 URI를 만들고, 끊기면 빈 PUT으로 받은 범위를 물어 `308 Resume Incomplete`와 받은 바이트 범위를 돌려받은 뒤 이어 보냅니다([YouTube Data API](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol)).

## 4. 평가

### 4-1. C는 어떻게 동작하나

멀티파트 업로드는 파일 하나를 여러 파트로 나눠 따로 올리고, 마지막에 스토리지가 이어 붙여 객체 하나로 만드는 S3 API입니다([S3 멀티파트 개요](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)).

| 단계 | 호출 | 누가 → 어디로 | 하는 일 |
|---|---|---|---|
| 1. 시작 | `POST /v1/uploads` | 클라이언트 → API | 제목, 설명, 공개 범위, 파일 크기를 받음. API가 `CreateMultipartUpload`로 `uploadId`를 받고, 영상 행(상태 UPLOADING)과 업로드 세션을 저장. 파트 크기와 파트 수를 돌려줌 |
| 2. 서명 | `POST /v1/uploads/{id}/parts:sign` | 클라이언트 → API | 요청한 파트 번호들의 서명 URL을 15분 유효로 발급. 한 번에 일부씩 발급 |
| 3. 전송 | `PUT <서명 URL>` | 클라이언트 → **스토리지 직접** | 파트 바이트를 보내고 ETag를 받음. 여러 파트를 병렬로 보낼 수 있음 |
| 4. 재개 | `GET /v1/uploads/{id}` | 클라이언트 → API | 끊긴 뒤 다시 켜지면, API가 `ListParts`로 스토리지에 이미 있는 파트를 알려 줌. 클라이언트는 빠진 파트만 다시 보냄 |
| 5. 완료 | `POST /v1/uploads/{id}:complete` | 클라이언트 → API | 클라이언트가 보낸 파트 목록(번호, ETag)을 `ListParts` 결과와 대조하고, 합계가 선언한 크기와 같은지 확인한 뒤 `CompleteMultipartUpload`. 상태를 UPLOADED로 바꾸고 트랜스코딩 작업을 발행(ADR-0010) |

API 서버는 1, 2, 4, 5만 처리합니다. 모두 작은 요청이고, **영상 바이트는 한 번도 API를 지나지 않습니다.**

#### 파트 크기

S3 제약은 파트 5MiB~5GiB(마지막 파트는 제한 없음), 업로드당 최대 10,000파트입니다([S3 한도](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)).

- 기본 파트 크기는 **16MiB**입니다. 평균 원본(300MB)은 약 18파트입니다. 끊겼을 때 잃는 양은 최대 한 파트이고, 5Mbps 모바일 업로드에서 약 27초 분량입니다.
- 큰 파일은 파트 수 한도에 걸리므로 `파트 크기 = max(16MiB, 파일 크기 / 9,000)`으로 늘립니다. 한도 10,000보다 여유를 둔 값입니다. 256GB 파일은 파트 하나가 약 28MB가 됩니다.

#### 재개의 기준은 누가 가지나

AWS 문서는 `ListParts` 결과로 완료 요청을 만들지 말고, 업로드한 파트 번호와 ETag를 직접 관리하라고 합니다. 목록은 검증용으로만 쓰라는 것입니다([S3 멀티파트 개요](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)). 그래서 역할을 이렇게 나눕니다.

| 상황 | 기준 |
|---|---|
| 완료 요청의 파트 목록 | 클라이언트가 PUT 응답으로 받은 ETag를 보관했다가 보냄 |
| 완료 전 검증 | API가 `ListParts`와 대조. 빠진 파트나 크기 불일치가 있으면 완료를 거절 |
| 클라이언트가 로컬 상태를 잃었을 때의 재개 | API가 `ListParts`로 이미 올라간 파트를 알려 줌. 클라이언트는 그 파트의 ETag를 다시 얻고 빠진 파트만 보냄 |

#### 완료의 멱등 (NFR-7)

완료 요청은 네트워크 재시도로 두 번 올 수 있습니다. 판단의 기준은 스토리지가 아니라 **우리 DB의 업로드 상태**입니다.

| 상태 | 두 번째 완료 요청이 오면 |
|---|---|
| UPLOADING | 정상 처리 |
| UPLOADED | 스토리지를 호출하지 않고 첫 번째와 같은 응답을 돌려줌 |
| 완료 도중 API가 죽어 스토리지 쪽은 끝났는데 DB는 UPLOADING | `CompleteMultipartUpload`가 실패하면(업로드 세션이 이미 없음) 객체 존재를 `HeadObject`로 확인하고 UPLOADED로 전이 |

`CompleteMultipartUpload`는 조건부 쓰기(같은 키에 객체가 없을 때만 생성)를 지원하므로, 같은 키에 두 번 쓰는 것도 스토리지 수준에서 막을 수 있습니다([S3 조건부 쓰기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html)).

### 4-2. 기준 1: 바이트가 지나는 계층을 우리가 운영해야 하는가

결정을 가르는 첫 번째 항목입니다.

| | C. Presigned Multipart | D. 전용 업로드 수신 계층 |
|---|---|---|
| 바이트 경로 | 클라이언트 → 스토리지 | 클라이언트 → 우리 서버군 → 스토리지 (두 구간) |
| 우리가 들고 있는 것 | 서명, 검증, 완료용 작은 요청(피크 초당 수백 건 수준) | 피크 42Gbps 수신과 42Gbps 송신, 동시 연결 약 2,100개 |
| 업로드 경로의 직렬 장애 지점 | API(작은 요청, 실패하면 재시도) + 스토리지 | 업로드 서버군 + 스토리지. 직렬로 연결된 계층의 가용성은 곱으로 줄어듦 |
| 배포의 영향 | API 배포는 몇 ms짜리 요청만 끊음 | 서버군을 배포할 때마다 진행 중인 전송이 끊김. 256GB 파일을 20Mbps로 보내면 약 28시간이라, 연결이 끝나기를 기다려 배포할 수 없음. 재개로 복구는 되지만 배포마다 대량 재개가 일어남 |
| 규모 대응 | 스토리지가 흡수 | 대역폭 기준으로 서버군을 증설. 대수 자체는 크지 않음(인스턴스당 5Gbps로 잡으면 피크에 10대 안팎) |

D는 대수가 많이 필요해서 불리한 것이 아닙니다. **오래 사는 연결과 대용량 바이트를 들고 있는 상태 있는 계층을 하나 더 운영해야 한다**는 점이 불리합니다. 그 계층의 배포, 장애, 용량 계획이 NFR-2(99.9%)에 직접 들어옵니다.

### 4-3. 기준 2: 업로드 중에 통제할 수 있는 것

D가 이기는 항목입니다. C를 고르면 무엇을 잃고, 얼마나 되찾을 수 있는지 적습니다.

| 통제 | D | C | C에서 되찾는 방법 |
|---|---|---|---|
| 잘못된 파일을 일찍 거절 | 첫 몇 MB를 보고 영상이 아니면 즉시 끊을 수 있음 | 완료 전에는 파트를 읽을 수 없음. 완료 뒤 워커가 `ffprobe`로 검증 | 되찾지 못함. 대신 잘못된 파일이 쓰는 저장 공간은 워커 검증 뒤 삭제로 제한됨 |
| 남용 차단(대역폭, 용량) | 스트림 도중 속도 제한, 차단 | 서명 URL을 가진 사람은 그 파트를 올릴 수 있음 | 시작할 때 선언 크기와 사용자별 일일 용량 한도를 검사. 서명 URL을 **일부씩 발급**하므로, 문제가 보이면 더 발급하지 않고 `AbortMultipartUpload`로 중단 |
| 서명 URL 유출 | 해당 없음 | URL은 가진 사람 누구나 쓰는 bearer 토큰 | 파트 하나, 15분으로 범위를 좁힘. 유출돼도 그 파트 자리에 쓸 수 있을 뿐이고, 완료 시 크기와 파트 검증에 걸림 |
| 저장소 벤더 독립 | 스토리지를 바꿔도 클라이언트 프로토콜은 그대로 | 클라이언트가 S3 멀티파트 방식에 묶임 | S3 API는 MinIO, Ceph RGW 등이 구현한 사실상 표준이라 호환 저장소 사이에서는 바꿀 수 있음 |

### 4-4. 기준 3: 클라이언트가 치르는 복잡도

| | C | D |
|---|---|---|
| 클라이언트가 할 일 | 파트 나누기, 병렬 전송, 파트별 재시도, ETag 보관, 서명 URL 재요청 | 오프셋을 묻고 그 뒤부터 순서대로 보내기 |
| 기성 도구 | AWS SDK의 멀티파트 도구, 브라우저용 라이브러리 다수 | tus 클라이언트 라이브러리 다수 |
| 처리량 | 파트를 병렬로 보내 지연이 긴 회선에서도 대역폭을 채움 | 연결 하나로 순서대로 보냄 |

C가 클라이언트에 더 많은 일을 시킵니다. 다만 앱과 웹은 우리가 만들고(2장 전제), 기성 라이브러리가 있어 감당할 수 있는 비용입니다.

### 4-5. 비용 (NFR-8)

| 항목 | C | D |
|---|---|---|
| 스토리지 요청 | 파트마다 PUT 1건. 평균 18파트 × 하루 50만 편 = 하루 약 900만 건 | 서버군이 스토리지에 쓸 때도 멀티파트를 쓰므로 비슷함 |
| 전송 | 클라이언트 → 스토리지 한 구간 | 한 구간 더(서버군 → 스토리지) |
| 계산 자원 | 거의 없음 | 서버군 상시 운영 |
| 미완료 업로드 | 멀티파트는 완료하거나 중단할 때까지 만료가 없고, 그동안 올라간 파트에 저장 요금이 붙음([S3 멀티파트 개요](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)). lifecycle 규칙 `AbortIncompleteMultipartUpload`로 N일 뒤 정리해야 함([S3 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html)) | 서버군이 같은 정리를 직접 구현 |

미완료 업로드의 크기를 가정해 보겠습니다. 업로드의 5%가 평균 절반쯤에서 포기된다면, 하루 150TB 유입 중 약 3.75TB가 미완료로 남습니다. 정리 기한을 7일로 두면 상시 약 26TB가 요금을 냅니다. 기한이 짧을수록 비용이 줄지만, 그만큼 크리에이터가 이어 올릴 수 있는 기간도 줄어듭니다.

### 4-6. 종합 (C vs D)

| 기준 | 순위 | C. Presigned Multipart | D. 전용 업로드 수신 계층 |
|---|---|---|---|
| 바이트 계층 운영 (NFR-2, NFR-7) | 1 | 운영하지 않음 | 상태 있는 계층을 하나 더 운영, 배포마다 대량 재개 |
| 업로드 중 통제 (NFR-8, NFR-2) | 2 | 일부 잃음. 조기 거절은 불가, 남용은 발급 중단으로 대응 | 모두 가능 |
| 클라이언트 복잡도 (FR-1) | 3 | 높음, 기성 라이브러리로 감당 | 낮음 |
| 비용 (NFR-8) | 참고 | 전송 한 구간, 서버군 없음 | 전송 두 구간, 서버군 상시 |

## 5. 결정 전 검증

별도 스파이크 없이 W4 구현에서 아래를 확인합니다. MinIO는 S3 멀티파트와 서명 URL을 지원하므로 같은 흐름을 로컬에서 재현할 수 있습니다.

| 검증 | 방법 | 확인하는 가정 |
|---|---|---|
| 끊긴 지점부터 재개 | 1GB 파일 업로드 도중 네트워크를 끊고, 클라이언트 로컬 상태를 지운 채 다시 시작 | 4-1 `ListParts` 기반 재개, FR-1 |
| 완료 멱등 | 같은 완료 요청을 동시에 2번, 순차로 2번. 완료 도중 API 프로세스 강제 종료 | 4-1 멱등 표, NFR-7 |
| 바이트가 API를 지나지 않음 | 업로드 중 API 인스턴스의 네트워크 수신량과 메타데이터 조회 p99 측정 | NFR-7 격리 |

| 서명 URL 만료 | 파트 PUT 도중 만료, 만료 직전 발급 | 10장 403 비율 지표 |

## 6. 추천안

**C. Presigned Multipart**를 추천합니다.

1. **주 근거: 바이트가 지나는 계층을 우리가 운영하지 않습니다 (NFR-2, NFR-7).** 피크 42Gbps와 수십 시간짜리 연결은 스토리지가 받고, 우리 API는 서명, 검증, 완료 같은 작은 요청만 처리합니다. 업로드 경로에 상태 있는 계층이 하나 더 생기지 않고, API 배포가 진행 중인 전송을 끊지 않습니다(4-2).
2. **재개가 스토리지 기능 위에 있습니다 (FR-1).** 파트 단위로 올라가므로 끊겨도 잃는 양은 최대 한 파트(기본 16MiB)이고, 재개할 위치는 `ListParts`로 스토리지가 알려 줍니다(4-1).
3. **완료 응답이 곧 내구성입니다 (NFR-5).** `CompleteMultipartUpload`가 성공해야 UPLOADED가 되므로, 완료 응답을 받은 원본은 이미 스토리지에 다 쓰여 있습니다.

### 잃는 것

- **잘못된 파일을 업로드 도중에 거절할 수 없습니다.** 완료 뒤 워커의 `ffprobe`에서야 알 수 있고, 그때까지 저장 공간과 전송을 씁니다.
- **업로드 도중 속도 제한을 걸 수 없습니다.** 서명 URL을 일부씩 발급해 멈추는 것이 최선입니다.
- **클라이언트가 복잡해집니다.** 파트 분할, 병렬 전송, ETag 보관을 앱과 웹이 모두 구현해야 합니다.
- **미완료 업로드 정리를 직접 챙겨야 합니다.** 정리 규칙을 빠뜨리면 요금이 계속 붙습니다.

### D가 맞는 경우

- 저장 전에 내용을 검사해야 하는 요구가 생긴다(9장).
- 제3자에게 공개 업로드 API를 제공한다. 이때는 단순한 오프셋 재개 프로토콜이 클라이언트에게 훨씬 쉽습니다.
- 전 세계에 업로드 수신 거점을 직접 둘 만큼 규모가 커진다. YouTube가 이 모양입니다.

### 면접에서 말하는 순서 (30초)

> 업로드는 요청 수는 초당 17건으로 가장 적지만, 바이트로는 피크 42Gbps이고 연결 하나가 수십 시간 갑니다. 그래서 바이트를 누가 받느냐가 핵심입니다. API 서버가 받으면 메타데이터 조회와 자원을 다투고, 전용 업로드 서버를 두면 상태 있는 계층이 하나 더 생겨 배포할 때마다 전송이 끊깁니다. 그래서 Presigned Multipart로 클라이언트가 스토리지에 파트 단위로 직접 올리게 했습니다. 끊기면 빠진 파트만 다시 보내고, 완료는 API가 파트 목록을 검증한 뒤 스토리지에서 확정합니다. 완료 요청은 DB 상태로 멱등하게 만들었습니다. 대신 업로드 도중에는 내용을 검사할 수 없어서, 검증은 완료 뒤 워커가 합니다. YouTube처럼 업로드 거점을 직접 운영할 규모가 되면 전용 수신 계층이 맞습니다.

## 8. 결과

- 이 결정으로 치르는 비용: 클라이언트 멀티파트 구현. 미완료 업로드 정리 규칙과 그 비용 감시. 서명 URL 발급 API와 파트 검증 로직
- 이 결정이 새로 만드는 문제
  - 서명 URL은 서명한 자격 증명이 유효한 동안만 유효합니다. 역할(role) 기반 임시 자격 증명으로 서명하면, 설정한 만료보다 일찍 만료될 수 있습니다([S3 서명 URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)). 서명에 쓰는 자격 증명의 남은 수명이 URL 만료(15분)보다 길어야 합니다
  - 서명 URL 검증은 시계에 의존하므로, 클라이언트와 서버 시계가 어긋나면 `SignatureDoesNotMatch`나 만료 오류가 납니다
- 후속으로 필요한 ADR: ADR-0010(완료 시 상태 전이와 트랜스코딩 작업 발행의 원자성), ADR-0012(먼 지역 업로드 가속)
- W2 API 명세에 4-1의 다섯 호출을 그대로 옮깁니다

## 9. 이 결정이 깨지는 조건

- 법이나 정책 때문에 저장 전에 내용을 검사해야 하는 경우. C로는 업로드 도중 검사가 불가능하다
- 제3자가 쓰는 공개 업로드 API를 제공하는 경우. 클라이언트 복잡도(기준 3)의 무게가 커진다
- 미완료 업로드 비율이 크게 올라, 4-5의 정리 비용이 D 서버군 비용을 넘는 경우
- 원본 저장소를 S3 호환이 아닌 저장소로 바꾸는 경우

## 11. 예상 꼬리질문

| 질문 | 답의 요지 |
|---|---|
| 왜 API 서버로 받지 않나? | 피크 42Gbps와 연결 약 2,100개가 메타데이터 API의 대역폭과 연결을 빼앗는다(NFR-7 격리). 초당 17건이라는 요청 수와 무관하다 |
| 전용 업로드 서버를 두면 격리도 되지 않나? | 된다. 그래서 가장 강한 대안이다. 다만 오래 사는 연결을 들고 있는 상태 있는 계층을 하나 더 운영해야 하고, 배포할 때마다 전송이 끊긴다(4-2) |
| YouTube는 어떻게 하나? | 공개된 Data API는 세션 URI와 오프셋 재개 방식이다. 즉 D 모양이다. 전 세계 수신 거점을 직접 운영하는 규모라 맞는 선택이고, 그 조건이 9장에 있다 |
| 파트 크기는 왜 16MiB인가? | 끊겼을 때 잃는 양(최대 한 파트)과 요청 수 사이의 절충이다. 큰 파일은 10,000파트 한도 때문에 `파일 크기 / 9,000`으로 늘린다 |
| 클라이언트가 파트 목록을 속이면? | 완료 전에 API가 `ListParts`와 대조하고, 합계를 선언한 크기와 비교한다. 목록은 클라이언트가 보내고 검증은 스토리지 기준으로 한다 |
| 완료 요청이 두 번 오면? | DB의 업로드 상태로 판단한다. UPLOADED면 스토리지를 다시 부르지 않고 같은 응답을 준다. 스토리지만 끝나고 DB가 못 바뀐 경우는 `HeadObject`로 확인해 전이한다 |
| 완료 뒤 트랜스코딩 발행이 실패하면? | 상태 전이와 발행을 원자적으로 묶는 문제이고 ADR-0010에서 Outbox로 다룬다 |
| 서명 URL이 유출되면? | 파트 하나, 15분짜리 bearer 토큰이다. 쓸 수 있는 건 그 파트 자리뿐이고, 완료 검증에서 크기 불일치로 걸린다 |
| 업로드를 포기하면 파트는 어떻게 되나? | 멀티파트는 만료가 없고 파트에 요금이 계속 붙는다. lifecycle 규칙으로 N일 뒤 정리한다. N은 재개 가능 기간과 비용의 절충이다 |
| 사용자가 영상이 아닌 파일을 올리면? | 업로드 도중에는 막을 수 없다. 완료 뒤 워커가 `ffprobe`로 검증해 실패 처리하고 원본을 지운다. 이것이 C의 대가다 |
