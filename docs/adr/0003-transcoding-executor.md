# ADR-0003: 변환 실행 주체

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-06 |
| 결정일 | 2026-10-06 |
| 관련 FR/NFR | FR-2, NFR-5, NFR-6 |

## 1. 문제와 제약

업로드 완료([ADR-0001](0001-upload-progress-and-completion.md)) 뒤 원본에서 360p·480p·720p·1080p를 만들어야 한다. 기준 화질은 p95 5분 안에 준비되어야 하고(NFR-5), 변환 장애 중에도 기존 영상 재생 목표를 유지해야 한다(NFR-6). 업로드는 하루 50만 개, 평균 초당 약 5.8개다(문제 카드 가정에서 계산).

## 2. 대안과 판단 기준

기준은 (1) 재생·API 경로와의 자원 격리, (2) 실패·재시도·화질 우선순위의 통제 가능성, (3) 운영 부담, (4) 규모에 따른 비용이다. (1)은 NFR-6의 직접 요구이므로 가장 앞에 둔다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| A. API 서버가 직접 변환 | 부품이 가장 적다 | 변환이 CPU를 점유해 API·재생 정보 응답이 느려진다. 작업 중 재배포·장애 시 "처리 중"에 고착된다. API와 변환의 확장 기준이 다르다 |
| B. 자체 변환 작업자 + 작업 대기열 | 자원이 분리된다. 시간 초과·재시도·360p 우선순위를 직접 정한다. 규모가 커질수록 단가를 통제할 수 있다 | 작업자 확장, 변환 도구, 실패 처리를 직접 구현·운영해야 한다 |
| C. 관리형 외부 변환 서비스 | 자원이 분리되고 운영 부담이 가장 낮다 | 출력 분 단위 과금이면 하루 약 2,000만 출력 분[계산: 50만 × 평균 10분(가정) × 4화질] 규모에서 비용이 크다(단가 미확인). 완료 신호 유실 시 재조회가 필요하다. 화질별 진행 제공 여부에 따라 360p 우선 처리가 제약된다 |

## 3. 사용자 제안과 검토

- 사용자 첫 제안: API 서버 직접 변환은 구현이 복잡하므로 외부 변환 서비스(C)에 맡기고 결과를 받는 것이 운영상 단순하다. 화질별 처리 시간과 CPU·메모리 부담이 문제일 것 같다고 했다.
- 면접관 검토(LLM): A의 핵심 문제는 자원 경쟁, 긴 작업 중 장애, 확장 기준 불일치다. 실행 주체와 무관하게 "비동기 변환 작업 + 작업 상태 기록 + 완료 신호" 구조가 필요하다. 이 규모에서는 B를 추천했다.
- 처리 시간 T는 측정 전 가정이며, 필요한 동시 작업 수는 초당 작업 수 × T로 계산한다.

## 4. 결정과 이유

사용자가 B를 선택했다. 이유: 구현 부담은 더 들지만 시간 초과·재시도 규칙을 자기 서버 상황에 맞출 수 있고, 인력이 과하게 들지 않는다면 감당할 만하다. C는 비용 부담이 있고, 완료 신호(hook)를 못 받거나 외부 작업이 죽었을 때 대처하기 어렵다고 판단했다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 변환이 API·재생 경로와 자원을 공유하지 않는다. 실패 감지·재시도·화질 우선순위를 요구사항에 맞춰 정할 수 있다.
- 비용: 작업 대기열, 작업자 확장, 실패 처리, 변환 도구 관리를 직접 구현·운영한다.

## 6. 검증과 남은 불확실성

- 미검증: 화질별 변환 시간과 CPU·메모리 사용량. 로컬 샘플 변환으로 측정해 필요한 작업자 수를 계산할 계획이다.
- 작업자 실패 감지·재시도 방식은 별도로 결정한다.
- C의 실제 단가는 확인하지 않았다. 비용 우위는 미검증이다.

## 7. 재검토 조건

- 업로드 규모가 크게 줄거나 운영 인력이 제한되어 관리형 서비스의 운영 이점이 비용보다 클 때.
- 측정한 변환 시간이 가정보다 훨씬 길어 자체 작업자 비용이 관리형 서비스 단가를 넘을 때.
