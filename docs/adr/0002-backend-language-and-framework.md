# ADR-0002: 백엔드 언어와 프레임워크

| 항목 | 값 |
|---|---|
| 상태 | Proposed |
| 작성일 | 2026-09-28 |
| 결정일 | |
| 관련 FR/NFR | FR-2 트랜스코딩, FR-5 조회수, NFR-4 메타데이터 p99, NFR-7 수평 확장, 로컬 제약 L-1 |
| 관련 ADR | ADR-0003 작업 큐, ADR-0004 이벤트 스트림, ADR-0009 조회수 집계 |

## 1. 맥락

구현을 시작하려면 API 서버와 트랜스코딩 워커의 언어를 정해야 합니다. 먼저 짚을 사실이 있습니다. 이 시스템에서 비용과 지연의 대부분을 만드는 곳은 언어가 아닙니다.

| 병목 | 실제로 결정하는 것 | 언어의 영향 |
|---|---|---|
| 영상 전송(이그레스) | CDN, 세그먼트 캐시 | 거의 없음. API 서버는 영상 바이트를 만지지 않음 |
| 트랜스코딩 CPU | FFmpeg(C, 하드웨어 가속) | 거의 없음. 워커는 FFmpeg 프로세스를 띄우고 결과를 올리는 조정자 |
| 메타데이터 지연 | 캐시 히트율, DB 인덱스 | 작음. 캐시 히트 경로에서 요청당 수 ms 이내 차이 |
| 조회수 쓰기 폭주 | 버퍼링 집계 구조 | 작음. 구조가 틀리면 어떤 언어로도 못 버팀 |

그래서 이 ADR의 질문은 "어떤 언어가 가장 빠른가"가 아니라 "NFR을 막지 않는 후보 중에서, 언어가 가진 특성이 이 시스템의 부하 모양과 프로젝트 제약에 가장 잘 맞는 것은 무엇인가"입니다.

## 2. 결정을 강제하는 요구사항

### 필수 조건 (하나라도 못 맞추면 탈락)

| 요구사항 | 제약 |
|---|---|
| NFR-4 메타데이터 p99 < 200ms | GC 정지나 스레드 고갈로 꼬리 지연이 튀지 않아야 함 |
| NFR-7 수평 확장 | 무상태 프로세스, 인스턴스 추가만으로 처리량이 늘어야 함 |
| FR-1, FR-3 | 동시 연결 수만 개를 OS 스레드 폭증 없이 처리하는 I/O 모델 |
| FR-2 | 외부 프로세스(FFmpeg) 실행, 출력 스트리밍, 타임아웃과 강제 종료 |
| 인프라 연동 | S3 호환 스토리지, Kafka 또는 메시지 큐, Redis, RDB 클라이언트가 운영 수준으로 성숙 |
| 관측성 | OpenTelemetry, Prometheus 지표, 운영 중 프로파일링 |

### 로컬 제약

| ID | 제약 | 영향 |
|---|---|---|
| L-1 | M2 Pro 12코어, 메모리 16GB. Docker 할당 약 10GB | 인프라(MySQL, Redis, Kafka, MinIO, Nginx)만 4~5GB. 남는 5GB 안에서 API와 워커를 여러 개 띄워 수평 확장 선형성을 측정해야 함 |
| L-2 | 부하 발생기도 같은 머신에서 돈다 | 서버 프로세스의 CPU, 메모리 사용이 작을수록 측정 오염이 줄어듦 |

## 4. 언어 특성 비교 (A vs B)

### 4-1. 동시성 모델

| | Java 21 Virtual Threads | Go goroutine |
|---|---|---|
| 구조 | JVM이 가상 스레드를 소수의 캐리어 스레드(ForkJoinPool) 위에 올림. 블로킹 지점에서 continuation을 떼어 냄 | 런타임 스케줄러(G, M, P)가 goroutine을 OS 스레드에 M:N으로 배치. 네트워크 대기는 netpoller가 처리 |
| 역사 | 2023년(JDK 21)에 들어옴. 그 전 20년 생태계는 스레드 풀 전제로 만들어짐 | 언어 탄생부터 goroutine 전제. 표준 라이브러리와 서드파티 전부가 이 모델에 맞춰짐 |
| 함정 | JDK 21에서는 `synchronized` 안에서 블로킹하면 캐리어 스레드를 붙잡는 pinning 발생(JDK 24에서 해결). 오래된 라이브러리가 스레드 로컬, 동기화 블록을 쓰면 효과가 줄어듦 | goroutine 누수(끝나지 않는 goroutine)가 조용히 쌓임. 모든 외부 호출에 `context` 취소와 타임아웃을 직접 전달해야 함 |
| 이 시스템에 주는 의미 | FR-1, FR-3의 대량 동시 연결을 처리할 수 있음. 단 드라이버, 풀 라이브러리가 VT 친화적인지 하나씩 확인해야 함 | 같은 요구를 추가 확인 없이 기본값으로 충족 |

### 4-2. 메모리와 GC

| | Java (G1 기본, Generational ZGC 선택 가능) | Go |
|---|---|---|
| 방식 | 세대별 GC. 객체를 옮기며 압축(compaction). 처리량과 할당 속도에 강함 | 비세대, 객체를 옮기지 않는 동시 mark-sweep. 짧은 정지 시간을 최우선으로 설계 |
| 할당 | 거의 모든 객체가 힙에 올라가고, 객체마다 헤더가 붙음 | 값 타입과 escape analysis로 상당 부분이 스택에 할당되어 힙 압력이 작음 |
| 기본 메모리 사용 | 힙 외에 메타스페이스, JIT 코드 캐시, 스레드 스택이 더해져 인스턴스당 수백 MB | 인스턴스당 수십 MB |
| 컨테이너 대응 | `MaxRAMPercentage`로 힙을 컨테이너 제한에 맞춤 | `GOMEMLIMIT`로 GC가 메모리 제한을 인식 |
| 이 시스템에 주는 의미 | NFR-4는 충족 가능(ZGC면 정지 시간 ms 이하). L-1에서 레플리카 수가 제한됨 | NFR-4 충족. L-1에서 API 3개, 워커 3개를 띄워도 1GB 안쪽 |

### 4-3. 실행 모델과 기동

| | Java | Go |
|---|---|---|
| 컴파일 | 바이트코드를 실행 중 JIT가 컴파일. 오래 돌수록 프로파일 기반 최적화로 처리량이 올라감 | 빌드 시 네이티브로 AOT 컴파일. 기동 직후부터 최종 성능 |
| 기동 | Spring Boot 기준 수 초, 이후 워밍업 구간 | 수십 ms |
| 배포물 | JRE를 포함한 이미지 | 정적 바이너리 하나, 이미지가 작음 |
| 이 시스템에 주는 의미 | 조회수 스파이크 때 인스턴스를 늘리면 새 인스턴스가 제 성능을 내기까지 지연이 있음 | 오토스케일로 붙은 인스턴스가 즉시 처리량을 냄 (NFR-7) |

### 4-4. 외부 프로세스 관리 (FR-2)

| | Java | Go |
|---|---|---|
| 도구 | `ProcessBuilder`, `Process.destroy`. 표준 출력, 에러를 각각 소비하지 않으면 파이프 버퍼가 차서 멈춤 | `os/exec` + `exec.CommandContext`. context가 취소되면 프로세스를 종료 |
| 이 시스템에 주는 의미 | 가능하지만 스트림 소비와 종료 처리를 신경 써서 짜야 함 | 타임아웃, 취소, 스트리밍이 언어 기본 도구로 짧게 표현됨 |

### 4-5. 오류 처리와 코드의 드러남

| | Java + Spring | Go |
|---|---|---|
| 오류 | 예외. 코드는 간결하지만, 어떤 예외에서 트랜잭션이 롤백되는지 같은 규칙이 프레임워크 안에 숨음 | 명시적 `error` 반환. 장황하지만 모든 실패 경로가 코드에 보임 |
| 조립 | DI 컨테이너, AOP, 자동 설정 | 생성자로 직접 조립 |
| 이 시스템에 주는 의미 | 개발은 빠르지만, "왜 이렇게 동작하나"를 설명하려면 프레임워크 내부까지 한 겹 더 파야 함 | 설계 결정(재시도, 멱등, 타임아웃)이 코드 표면에 드러나 리뷰와 방어가 쉬움. 대신 트랜잭션, 설정 관리를 직접 짠 코드도 방어 대상이 됨 |

### 4-6. 생태계

| 영역 | Java | Go |
|---|---|---|
| Kafka | 공식 클라이언트가 레퍼런스 구현. Kafka Streams는 Java 전용 | franz-go 등 순수 Go 클라이언트가 성숙. Kafka Streams 같은 상태 기반 스트림 처리는 직접 구현 |
| S3, Redis, RDB | 모두 성숙 | 모두 성숙 |
| 프로파일링 | JFR, async-profiler | pprof 내장, HTTP 엔드포인트로 운영 중 바로 수집 |
| 대규모 사례 | 대부분의 한국 대형 서비스 백엔드 | YouTube의 MySQL 샤딩 계층 Vitess, Kubernetes, Docker |

## 5. 결정 전 검증

별도 스파이크는 하지 않고 위 특성 비교로 결정합니다. 대신 W3 첫 로컬 측정 때 인스턴스 RSS, 기동 시간, p99 기준 최대 QPS를 함께 기록합니다. 4장의 예상과 크게 어긋나면 새 ADR로 다시 엽니다.

## 6. 추천안

**B. Go**를 추천합니다. 속도가 이유가 아닙니다. 이 프로젝트는 로컬에서 단위 용량을 재고 레플리카를 1개에서 3개로 늘려 선형성을 확인한 뒤 DAU 1억으로 환산합니다. 이 방법론에는 Go의 작은 메모리 사용, 즉시 기동, 워밍업 없는 성능이 직접 맞물립니다(4-2, 4-3). 트랜스코딩 워커의 프로세스 조정(4-4)과, 재시도, 멱등, 타임아웃이 코드 표면에 드러나는 성질(4-5)도 방어에 유리합니다.

다만 아래 중 하나라도 해당하면 A가 맞습니다.

- 조회수 집계를 Kafka Streams로 하기로 정한다 (ADR-0009)
- 9주 일정 안에 완성하는 것과 방어 깊이를 새 언어 학습보다 우선한다
- 멘토링의 목적이 지원 회사의 주력 스택(대부분 JVM) 역량을 보여주는 것이다

## 8. 결과

- B를 고르면: W1에 Go 기초, goroutine 스케줄러, GC 동작, context 전파를 학습할 시간을 따로 잡는다. 트랜잭션, 설정, 의존성 조립을 직접 짜므로 그 코드도 방어 대상이 된다
- A를 고르면: Docker 메모리 예산을 다시 짜고, 레플리카 수를 줄인 상태로 선형성 측정을 설계한다. 이 시스템이 쓰는 Spring 자동 설정(트랜잭션, 커넥션 풀, Kafka 리스너)은 동작 원리를 설명할 수 있어야 한다. VT pinning을 피하려고 JDK 24 이상을 검토한다

## 9. 이 결정이 깨지는 조건

- API가 영상 바이트를 직접 다뤄야 하는 요구(서버 사이드 광고 삽입 등)가 생겨 CPU 병목이 언어로 옮겨오는 경우
- 팀 단위 개발로 바뀌어 채용과 유지보수 비용이 기준에 들어오는 경우
- W3 측정값이 4장 예상과 크게 어긋나는 경우

## 11. 예상 꼬리질문

| 질문 | 답의 요지 |
|---|---|
| 왜 이 언어인가? | 이 시스템의 병목은 언어가 아니다. 필수 조건은 두 후보 모두 통과했고, 로컬 측정 방법론과 맞물리는 특성(메모리, 기동)으로 골랐다 |
| Virtual Threads가 나왔으니 Java도 goroutine과 같지 않나? | 모델은 비슷해졌지만 생태계가 그 모델을 전제로 만들어졌는지가 다르다. JDK 21의 pinning 문제가 그 차이를 보여준다 |
| 실제 YouTube는 무엇을 쓰나? | 초기 Python, 이후 C++, Java, Go가 섞여 있고 Vitess가 Go다. 대규모에서는 한 언어가 아니라 계층별로 고른다 |
| 트랜스코딩은 CPU를 많이 쓰는데 언어가 중요하지 않나? | CPU를 쓰는 건 FFmpeg다. 워커는 프로세스를 띄우고 진행을 감시하고 결과를 올리는 조정자라 I/O와 프로세스 관리가 중요하다 |
| JIT가 장기 실행에서 더 빠를 수 있지 않나? | 맞다. 그러나 이 시스템의 API는 CPU 병목이 아니고, 오토스케일로 자주 늘고 주는 환경에서는 워밍업 비용이 더 크게 작용한다 |
| GC 때문에 p99가 튀면? | 지표 표 참고. 측정해서 할당 경로를 줄이는 게 먼저고, 튜닝은 그다음이다 |
