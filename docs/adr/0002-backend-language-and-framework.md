| 항목 | 값 |
|---|---|
| 상태 | Proposed |
| 분류 | 제품 설계 |
| 작성일 | 2026-09-28 |
| 결정일 | |
| 관련 FR/NFR | FR-2 트랜스코딩, FR-4 메타데이터, FR-5 조회수, NFR-4 메타데이터 p99, NFR-5 원본 보존, NFR-7 멱등과 수평 확장, NFR-8 비용 |
| 관련 ADR | ADR-0003 작업 큐, ADR-0004 이벤트 스트림, ADR-0009 조회수 집계 |

## 1. 맥락

API 서버와 트랜스코딩 워커의 언어를 정해야 구현을 시작할 수 있습니다. 이 ADR은 로컬 실습에 편한 언어가 아니라, **이 시스템을 DAU 1억 규모의 프로덕션에서 운영한다면 서버를 무엇으로 짤 것인가**를 정합니다. 로컬 환경(L-1, L-2)은 결정한 언어로 단위 용량을 재는 측정 도구일 뿐, 선택 기준에 넣지 않습니다.

### 언어가 병목이 아니다

이 시스템에서 비용과 지연의 대부분을 만드는 곳은 언어가 아닙니다.

| 병목 | 실제로 결정하는 것 | 언어의 영향 |
|---|---|---|
| 영상 전송(이그레스) | CDN, 세그먼트 캐시 | 거의 없음. API 서버는 영상 바이트를 만지지 않음 |
| 트랜스코딩 CPU | FFmpeg(C, 하드웨어 가속) | 거의 없음. 워커는 FFmpeg 프로세스를 띄우고 결과를 올리는 조정자 |
| 메타데이터 지연 | 캐시 히트율, DB 인덱스 | 작음. 캐시 히트 경로에서 요청당 수 ms 이내 차이 |
| 조회수 쓰기 폭주 | 버퍼링 집계 구조 | 작음. 구조가 틀리면 어떤 언어로도 못 버팀 |

### 우리가 직접 짜는 서비스와 부하 모양

수치는 `docs/design/00-scope.md`의 트래픽 가정에서 가져왔습니다.

| 서비스 | 부하 모양 | 언어에 요구하는 특성 |
|---|---|---|
| 메타데이터 API (FR-4) | 피크 초당 약 6만 9,000건. 거의 모든 시간이 캐시, DB 응답 대기. 인기 영상이 생기면 트래픽이 몇 분 안에 급변 | 대량 동시 대기를 싸게 처리. **스케일아웃으로 붙은 새 인스턴스가 곧바로 정상 p99를 내는 것** |
| 업로드 제어 API (FR-1) | 피크 초당 약 17건. 바이트는 객체 스토리지로 직접 가고(ADR-0006) API는 서명 URL 발급과 완료 처리만 함 | 특별한 요구 없음. 완료 처리의 멱등(NFR-7) |
| 트랜스코딩 워커 (FR-2) | 하루 250만 분 × 4해상도. 작업 하나가 수 분 동안 외부 프로세스를 붙잡음. 배포, 인스턴스 회수로 중간에 끊기는 일이 일상 | **작업 취소와 타임아웃이 외부 프로세스 종료까지 전파되는 것** (NFR-5, NFR-7) |
| 조회 이벤트 수집 (FR-5) | 피크 초당 약 1만 7,400건 쓰기. 핫 영상 하나에 초당 약 170건 | 이벤트를 받아 큐에 넣는 얇은 계층. 상태 기반 집계를 어디서 할지는 ADR-0009 |

네 서비스 모두 **CPU를 쓰는 로직이 거의 없고, 외부 시스템을 기다리며 실패를 처리하는 얇은 조정자**입니다.

### 그래서 이 ADR의 질문

Java, Go, Node.js, Rust 모두 장치를 더하면 이 시스템의 요구사항을 맞출 수 있습니다. 어떤 언어도 이 시스템을 성립시키거나 망가뜨리지 않습니다. 따라서 "무엇이 가능한가"로는 고를 수 없고, 질문은 이렇게 됩니다.

> **가장 중요한 기준을 추가 장치 없이 기본값으로 충족하는 언어 중에서, 모든 서비스가 계속 치러야 하는 비용이 가장 작은 것은 무엇인가?**

## 2. 결정을 강제하는 요구사항

### 필수 조건 (하나라도 못 맞추면 탈락)

| 요구사항 | 제약 |
|---|---|
| NFR-4 메타데이터 p99 < 200ms | GC 정지나 스레드 고갈로 꼬리 지연이 튀지 않아야 함 |
| NFR-7 수평 확장 | 무상태 프로세스, 인스턴스 추가만으로 처리량이 늘어야 함 |
| FR-1, FR-3, FR-4 | 동시 연결 수만 개를 OS 스레드 폭증 없이 처리하는 I/O 모델 |
| FR-2 | 외부 프로세스(FFmpeg) 실행, 출력 스트리밍, 타임아웃과 강제 종료 |
| 인프라 연동 | S3 호환 스토리지, Kafka 또는 메시지 큐, Redis, RDB 클라이언트가 운영 수준으로 성숙 |
| 관측성 | OpenTelemetry, Prometheus 지표, 운영 중 프로파일링 |

3장의 후보는 모두 이 조건을 통과합니다. 필수 조건은 후보를 거르지 못하므로, 아래 결정 기준으로 가릅니다.

### 결정 기준 (우선순위 순)

| 순위 | 기준 | 연결 요구사항 | 우선순위의 이유 |
|---|---|---|---|
| 1 (주) | **스케일아웃 중에도 p99를 지키는가** | NFR-4, NFR-7 | 가장 바쁜 서비스(메타데이터 API)가, 가장 위태로운 순간(피크 중 증설)에 겪는 문제. 정상 상태 p99는 모든 후보가 충족하므로 차이가 나는 곳은 여기뿐 |
| 2 (보조) | **작업 취소가 외부 프로세스와 라이브러리 경계를 넘어 끝까지 전파되는가** | FR-2, NFR-5, NFR-7 | 규모가 커질수록 잦아지는 사건(배포, 인스턴스 회수, 임대 만료)에서 고아 프로세스와 결과 섞임을 막음 |

### 전제

- 신규 시스템이고, 조직에 이미 깔린 언어 플랫폼(공통 라이브러리, 배포 템플릿, 관측 설정, 온콜 역량)이 없다고 가정합니다. 이 전제가 깨지면 결론이 바뀔 수 있습니다(9장).
- 이 ADR은 우리가 직접 짜는 서비스의 언어만 정합니다. 조회수 집계에 Flink 같은 별도 스트림 엔진을 쓸지는 ADR-0009에서 정하며, 그 엔진의 구현 언어는 이 결정과 무관합니다.

### 결정 기준에서 뺀 것

| 항목 | 빼는 이유 |
|---|---|
| 로컬 자원 제약 (L-1, L-2) | 프로덕션 언어 선택과 인과 관계가 없음. 결정한 언어로 측정 방법을 맞춤 |

| 정상 상태 성능, 메모리, 멀티코어 사용 | 모든 후보가 충족하거나, 차이가 결정을 가를 만큼 크지 않음. 근거는 4-4 |

## 3. 선택지

### 후보

| 후보 | 설명 |
|---|---|
| A. Java 25 (LTS) + Spring Boot | 가장 강한 대안. 2025년 9월 GA된 최신 LTS([JDK 25](https://openjdk.org/projects/jdk/25/)). JDK 24부터 `synchronized` 안의 Virtual Threads pinning이 해결됐고([JEP 491](https://openjdk.org/jeps/491)), AOT 캐시로 워밍업을 줄일 수 있음([JEP 483](https://openjdk.org/jeps/483), [JEP 515](https://openjdk.org/jeps/515)) |
| B. Go | 네이티브 AOT 컴파일, goroutine, `context` 관례 |
| C. Node.js (TypeScript) | 이벤트 루프, V8 JIT. cluster나 1 vCPU 파드로 멀티코어 사용 |
| D. Rust (tokio) | 네이티브 AOT 컴파일, GC 없음, async/await |
| E. Kotlin + Spring Boot | A와 같은 JVM 런타임에 코루틴 |
| F. API는 Java, 워커는 Go | 서비스별로 다른 언어 |

### 거르는 방법

| 단계 | 질문 | 통과 | 떨어진 후보와 이유 |
|---|---|---|---|
| 1 | 필수 조건(2장)을 충족하는가 | 전부 | 없음 |
| 2 | 기준 1을 **기본값으로** 충족하는가 | B, D | C는 V8 JIT 워밍업이 남음(4-1). E는 A와 같은 런타임이라 A와 함께 판단. A는 장치로 충족 가능한 가장 강한 대안이라 **최종 비교에 남김** |
| 3 | 기준 2, 3에서 남은 후보 중 누가 나은가 | B | D는 기준 1에서 B와 같거나 낫지만, 그 이득이 나올 CPU 병목이 없는데 async 복잡도와 취소 안전성 비용을 모든 서비스가 치름(4-2, 4-3) |
| 최종 | A와 B 비교 | 4-5 | |

나머지 후보를 뺀 이유는 이렇습니다.

- **C(Node.js)는 못 해서 빠진 것이 아닙니다.** 결정을 가르는 기준에서 B보다 나은 점이 없어서 빠졌습니다. 기준 1에서는 A와 같은 쪽(워밍업 있음)에 서고, 기준 2, 3에서는 B와 비슷하거나 조금 불리합니다(4-2, 4-3).
- **E(Kotlin)** 는 기준 1, 2가 A와 같습니다. A 대비 얻는 것이 문법 편의와 코루틴 정도라 A로 대표합니다.
- **F(혼합)** 는 두 서비스가 요구하는 특성(1장)이 거의 같아 나눠서 얻는 것이 없고, 빌드, 공통 라이브러리, 관측 설정, 온콜 지식이 두 벌이 됩니다.

## 4. 평가: 언어 특성 비교

### 4-1. 기준 1: 스케일아웃 중에도 p99를 지키는가

#### 워밍업이란

Java는 빌드할 때 기계어가 아니라 바이트코드를 만들고, 실행 중에 점점 빨라집니다.

```
막 뜬 인스턴스 ──▶ 인터프리터로 한 줄씩 해석 (느림)
                 ──▶ 자주 불린 메서드를 C1이 빠르게 컴파일 (중간)
                 ──▶ 아주 자주 불린 메서드를 C2가 최적화 컴파일 (최고 성능)
```

C2 단계는 메서드 하나가 수천에서 1만 회 이상 불려야 옵니다. 클래스도 처음 쓰일 때 로딩되는데, Spring 앱은 클래스가 수천 개라 첫 요청들이 클래스 로딩과 프록시 생성 비용까지 떠안습니다. 그래서 막 뜬 JVM 인스턴스는 한동안 같은 요청을 더 느리게 처리합니다. 이 구간이 워밍업이고, 길이는 5장에서 측정합니다.

#### 워밍업이 p99에 닿는 경로

피크 시간에 메타데이터 API를 10대에서 15대로 늘린다고 하겠습니다.

1. 로드밸런서는 새 인스턴스 5대에도 요청을 똑같이 나눕니다.
2. 전체 요청의 약 1/3이 워밍업 중인 인스턴스로 갑니다.
3. p99는 가장 느린 1% 요청의 경계입니다. 느린 인스턴스가 요청의 33%를 받으면, 그 구간의 p99는 거의 그 인스턴스들의 지연으로 정해집니다.
4. 이 일이 트래픽이 가장 높은 순간, 즉 NFR-4가 가장 위태로운 순간에 일어납니다.

readiness 검사는 이 문제를 막지 못합니다. readiness는 프로세스가 떴고 커넥션이 준비됐다는 것만 알리고, JIT가 데워졌는지는 알리지 않습니다. JIT는 실제 요청을 받아야 데워지므로, readiness를 통과한 직후가 바로 워밍업 구간입니다.

#### JIT가 워밍업을 감수하고 얻는 것

JIT가 AOT보다 나쁜 방식은 아닙니다. 두 방식은 **기계어를 만드는 시점**이 다르고, 그래서 얻는 것과 내주는 것이 반대입니다.

AOT 컴파일러는 빌드할 때 소스 코드만 보고 판단하므로, 어떤 입력이 와도 맞도록 보수적으로 컴파일합니다. JIT는 실행 중에 실제 동작을 관찰한 뒤 컴파일합니다.

```java
interface Encoder { byte[] encode(Video v); }

for (Video v : videos) {
    encoder.encode(v);   // 구현체가 여러 개일 수 있는 인터페이스 호출
}
```

- AOT(Go)는 코드에서 구현체가 보이면 직접 호출로 바꿉니다([정적 devirtualization](https://github.com/golang/go/issues/19361)). 그러나 구현체가 실행 중에 정해지면(예: 설정으로 인코더를 고름) 빌드 시점에 알 수 없으므로, 구현체를 찾아 호출하는 간접 호출로 둡니다.
- JIT(Java C2)는 실행해 보니 `H264Encoder` 하나만 쓰인다는 것을 관찰하고, 그렇다고 **가정한 채** 그 코드를 호출 지점에 붙여 넣은(인라이닝) 뒤 추가 최적화를 합니다. 다른 구현체가 들어와 가정이 깨지면 최적화를 되돌리고(deoptimization) 다시 관찰합니다.

이 추측 기반 최적화 덕분에, 구현체나 분기가 실행 중에 정해지고 오래 돌며 CPU를 많이 쓰는 코드에서는 JIT의 최고 성능이 AOT보다 높을 수 있습니다.

| | JIT (Java, V8) | AOT (Go, Rust) |
|---|---|---|
| 얻는 것 | 실행 중 관찰에 기반한 추측 최적화(인라이닝, 가상 호출 제거). 높은 최고 성능 | 기동 직후부터 최종 성능. 예측 가능한 지연 |
| 내주는 것 | 워밍업, 실행 중 컴파일이 쓰는 CPU와 메모리(코드 캐시, 프로파일), 최적화를 되돌릴 때의 순간 지연 | 실행 중 정보를 쓰지 못해 최고 성능이 낮을 수 있음 |

두 진영은 서로의 장점을 가져오는 중입니다. Java는 GraalVM Native Image와 AOT 캐시로 워밍업을 줄이고, Go는 1.21부터 정식 지원하는 PGO(Profile-Guided Optimization)로 운영 중 수집한 pprof 프로파일을 빌드에 넣어, 가장 자주 불리는 구현체로 인터페이스 호출을 직접 호출로 바꾸고(devirtualization) 인라이닝을 늘립니다([Go 1.21 릴리스 노트](https://go.dev/doc/go1.21#compiler)). Go 문서는 대표 프로그램에서 약 2~14%의 개선을 보고합니다([Go PGO 문서](https://go.dev/doc/pgo)). JIT의 "관찰 후 최적화"를 빌드 시점으로 옮긴 것입니다.

#### 유불리는 부하 모양이 정한다

| 부하 모양 | 유리한 쪽 | 이유 |
|---|---|---|
| 오래 켜 두고, 안정적이고, CPU를 많이 씀 (배치, 스트림 처리, 계산 엔진) | JIT | 워밍업은 한 번이고, 높은 최고 성능을 오래 누림 |
| 자주 뜨고 지고, 첫 순간부터 예측 가능해야 함 (오토스케일, 서버리스, CLI) | AOT | 워밍업 비용을 기동할 때마다 다시 치름 |
| 대부분의 시간이 I/O 대기인 얇은 서비스 | AOT 쪽이 조금 | JIT의 강점(CPU 최고 성능)은 대기 시간에 묻혀 드러나지 않고, 약점(워밍업)만 증설 때마다 드러남 |

메타데이터 API는 두 번째와 세 번째에 동시에 해당합니다(1장). 그래서 이 서비스들에서는 AOT가 맞습니다. 이것은 JIT 언어가 일반적으로 불리하다는 뜻이 아닙니다. 오래 켜 두고 이벤트를 계산하는 조회수 집계 계층은 첫 번째에 가까워, JVM 기반 스트림 엔진이 맞을 수 있습니다(ADR-0009).

#### 후보별 비교

| | A. Java | B. Go | C. Node.js | D. Rust |
|---|---|---|---|---|
| 실행 방식 | 바이트코드 + JIT (C1, C2) | 빌드 시 네이티브 컴파일 | JavaScript + V8 JIT (Ignition, Sparkplug, Maglev, TurboFan. [V8 블로그](https://v8.dev/blog/maglev)) | 빌드 시 네이티브 컴파일 |
| 코드 워밍업 | 있음. Spring은 클래스 로딩까지 더해져 김 | 없음. 첫 요청부터 최종 성능 | 있음. JVM보다 짧음 | 없음 |
| 기본값으로 기준 1 충족 | 아니오. 장치 필요 | 예 | 아니오 | 예 |

AOT 컴파일이 없애는 것은 **코드 실행 속도의 워밍업**뿐입니다. DB 커넥션 풀 생성, 비어 있는 로컬 캐시 같은 워밍업은 언어와 무관하게 모든 후보에 똑같이 생깁니다.

#### Java가 워밍업을 줄이는 장치와 그 비용

| 장치 | 동작 | 늘어나는 것 |
|---|---|---|
| AOT 캐시 (Project Leyden, JDK 24의 [JEP 483](https://openjdk.org/jeps/483)부터) | 배포 전에 앱을 띄워 대표 요청을 흘리는 학습 실행(training run)을 합니다. JVM이 로딩, 연결한 클래스와(JDK 25의 [JEP 515](https://openjdk.org/jeps/515)부터) 메서드 실행 프로파일을 캐시 파일로 남기고, 운영 인스턴스는 이 파일로 기동과 워밍업을 줄입니다 | CI에 학습 실행 단계가 생김. 캐시는 JDK 버전과 jar가 정확히 같아야 쓰이므로 배포마다 다시 만듦. 학습 트래픽이 실제와 다르면 효과가 줄어 대표 트래픽 시나리오를 관리해야 함 |
| CRaC (Coordinated Restore at Checkpoint. [OpenJDK CRaC 프로젝트](https://openjdk.org/projects/crac/)) | 워밍업이 끝난 JVM 프로세스의 메모리 전체를 스냅샷으로 떠 두고, 새 인스턴스는 그 스냅샷에서 복원합니다. JIT 컴파일된 코드까지 복원되어 데워진 상태로 시작합니다 | 열린 파일과 소켓은 스냅샷에 담기지 않아, DB, Kafka 연결을 체크포인트 전에 닫고 복원 뒤 다시 여는 코드가 필요함([CRaC 문서](https://github.com/CRaC/docs)). 메모리 속 시크릿이 이미지에 들어가는 문제. 난수 시드, ID 생성기 상태가 복원된 인스턴스끼리 같아지는 문제. 리눅스 CRIU 기반이라 컨테이너에 추가 권한이 필요함. 메인라인 JDK에 포함되지 않아 CRaC 빌드를 제공하는 JDK 배포판을 골라야 함 |
| 워밍업 트래픽 | readiness 전에 합성 요청을 흘려 JIT를 데움 | 배포 시간 증가, 합성 요청 시나리오 관리 |
| 로드밸런서 slow start | 새 인스턴스에 보내는 트래픽 비율을 일정 시간에 걸쳐 서서히 올림(AWS ALB, Envoy 등이 지원) | 새 용량이 늦게 투입되어, 피크 중 기존 인스턴스가 과부하를 더 오래 견뎌야 함. 램프 시간을 워밍업 길이에 맞춰 조정해야 함 |
| 여유 대수 상시 유지 | 증설을 미리 해 두어 피크 중 증설을 피함 | 상시 비용 |

Java는 이 문제를 **풀 수 있습니다.** 다만 빌드 단계, 코드 규칙, 런타임 권한, 로드밸런서 설정을 추가로 관리해야 풀립니다. B와 D는 이 장치가 필요 없습니다.

### 4-2. 기준 2: 작업 취소가 끝까지 전파되는가

#### 왜 필요한가

DAU 1억 규모에서 워커가 작업 도중 멈추는 일은 예외가 아니라 일상입니다. 배포 때마다 롤링 재시작(SIGTERM)이 일어나고, 스팟 인스턴스가 회수되고, 작업 임대(lease)가 만료되어 다른 워커가 같은 작업을 가져갑니다. 이때 취소가 끝까지 전파되지 않으면 두 가지가 깨집니다.

| 전파가 끊긴 곳 | 결과 | 깨지는 요구사항 |
|---|---|---|
| 워커 → FFmpeg | 부모 워커는 멈췄는데 FFmpeg는 살아서 CPU를 계속 씀(고아 프로세스). 같은 노드의 다음 작업이 CPU를 빼앗김 | NFR-7 격리 |
| 워커 → 업로드 | 취소된 작업이 세그먼트 일부를 이미 올려 둔 상태에서 재시도 작업이 같은 경로에 씀. 두 시도의 결과가 섞임 | NFR-7 멱등, NFR-5 재처리 |

#### Go의 context

`context`는 "이 작업의 마감 시각과 취소 신호"를 담은 값으로, 함수의 첫 인자로 계속 넘깁니다. 표준 HTTP, `database/sql`, AWS SDK, Kafka 클라이언트(franz-go), Redis 클라이언트가 모두 `ctx`를 받는 것이 생태계 관례입니다.

```go
ctx, cancel := context.WithTimeout(jobCtx, 30*time.Minute)
defer cancel()

if err := download(ctx, src); err != nil {        // S3 다운로드
    return err
}
cmd := exec.CommandContext(ctx, "ffmpeg", args...) // ctx가 취소되면 FFmpeg를 종료
if err := cmd.Run(); err != nil {                   // 실패, 취소 시 업로드하지 않음
    return err
}
return upload(ctx, out)                             // S3 업로드
```

`jobCtx` 하나를 취소하면 다운로드, FFmpeg, 업로드가 모두 멈춥니다. 서드파티 라이브러리 경계를 넘어서도 같은 방식입니다.

#### context가 막는 범위

`context`는 워커가 살아서 취소를 결정할 수 있는 경로만 막습니다. 워커가 SIGKILL이나 OOM으로 강제 종료되면 코드가 실행되지 않으므로 취소도 없습니다. 경로별로 막는 수단이 다릅니다.

| 경로 | 예 | 막는 수단 | 언어의 역할 |
|---|---|---|---|
| 정상 취소 | SIGTERM(롤링 재시작), 타임아웃, 임대 만료 | `context` 전파 | 이 기준이 비교하는 곳 |
| 강제 종료 | SIGKILL, OOM killer | 커널: `Pdeathsig`(부모 스레드가 죽으면 자식에게 신호), 프로세스 그룹 단위 정리, 워커를 컨테이너 PID 1로 두어 컨테이너 종료 시 함께 정리 | 언어와 무관. Go는 `syscall.SysProcAttr`의 `Pdeathsig`, `Setpgid`로 표준 라이브러리에서 바로 씀([exec_linux.go](https://github.com/golang/go/blob/master/src/syscall/exec_linux.go)). `Pdeathsig`는 자식을 만든 스레드가 죽을 때 신호가 가므로 `runtime.LockOSThread`와 함께 씀 |
| 부분 업로드 | 어느 경로로든 중간에 끊긴 시도 | 시도(attempt)마다 다른 경로에 쓰고 완료 시 커밋하는 멱등 설계(NFR-7) | 언어와 무관 |

#### 후보별 비교

| | A. Java | B. Go | C. Node.js | D. Rust |
|---|---|---|---|---|
| 취소 수단 | 라이브러리마다 다름. JDBC `queryTimeout`, HTTP 클라이언트 timeout, S3 SDK `apiCallTimeout`. 공통 수단인 `Thread.interrupt`는 라이브러리가 무시하거나 삼키는 경우가 많음 | `context` 하나. Google은 요청 경로의 모든 함수가 첫 인자로 `Context`를 받도록 요구함([Go 블로그](https://go.dev/blog/context)) | `AbortSignal`. `child_process.spawn`, `fetch`는 받지만 받지 않는 라이브러리도 많음 | future를 drop하면 취소 |
| 외부 프로세스 | `Process.destroy`를 따로 호출. 표준 출력, 에러를 각각 소비하지 않으면 파이프 버퍼가 차서 멈춤 | `exec.CommandContext`가 취소 시 프로세스를 Kill([os/exec](https://pkg.go.dev/os/exec#CommandContext)) | `spawn({ signal })`이 취소 시 종료([Node.js 문서](https://nodejs.org/api/child_process.html)) | `tokio::process`의 `kill_on_drop(true)`. 기본값은 꺼져 있고, 종료된 프로세스 회수는 best-effort([tokio 문서](https://docs.rs/tokio/latest/tokio/process/struct.Command.html#method.kill_on_drop)) |
| 함정 | 이것을 한 흐름으로 묶어 줄 Structured Concurrency가 JDK 25에서도 아직 preview([JEP 505](https://openjdk.org/jeps/505)) | 모든 호출에 `ctx`를 넘기지 않으면 끊김. goroutine 누수 | 라이브러리가 신호를 받는지 하나씩 확인 | **취소 안전성**: `.await` 지점 어디서든 멈출 수 있어, 상태가 반쯤 바뀐 채 남는 코드를 쓰기 쉬움. `write_all` 같은 연산은 취소되면 데이터를 잃을 수 있음([tokio 문서](https://docs.rs/tokio/latest/tokio/macro.select.html#cancellation-safety)) |
| 기본값으로 기준 2 충족 | 직접 이어 붙여야 함 | 생태계 관례로 충족. 언어가 강제하지는 않으며, 누락은 `noctx`, `contextcheck` 린터([golangci-lint](https://golangci-lint.run/docs/linters/))와 코드 리뷰로 검사 | 부분적 | 예, 단 취소 안전성을 매번 따져야 함 |

### 4-3. 기준 3: 모든 서비스가 계속 치르는 복잡도

| | A. Java + Spring | B. Go | C. Node.js | D. Rust |
|---|---|---|---|---|
| 기준 1, 2를 메우는 비용 | 4-1의 장치, 취소 연결 코드 | 없음 | 워밍업 장치, 라이브러리별 신호 확인 | 없음 |
| 코드와 동작의 거리 | 트랜잭션, 재시도가 프레임워크 규칙 안에 있음. 예: `@Transactional`은 기본값으로 checked 예외에서 롤백하지 않음([Spring 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)). `@Retryable`, `@Transactional`은 프록시라 같은 클래스 안의 자기 호출에는 조용히 적용되지 않음([Spring 문서](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)) | 명시적 `error` 반환이라 실패 경로가 호출 지점에 보임. 대신 장황하고, `_`로 오류를 무시할 수도 있음 | 예외와 Promise 거부. 처리하지 않은 거부가 조용히 묻히기 쉬움 | `Result` 타입으로 실패 경로가 강제됨 |
| 직접 짜야 하는 것 | 적음. 선언적 기능이 많음 | 트랜잭션 경계, 설정 바인딩, 의존성 조립 | 중간 | 많음. async 트레이트 제약(`Send`, `Pin`), 라이프타임 |
| 프로세스 안 요청끼리 격리 | 요청마다 가상 스레드 | 요청마다 goroutine, 런타임 선점 | 한 요청의 긴 동기 작업(큰 JSON 직렬화 등)이 그 프로세스의 모든 요청을 막음 | 태스크마다 분리. 단 `.await` 없이 오래 도는 태스크가 워커 스레드를 붙잡음 |
| 빌드 | 보통 | 빠름 | 빠름 | 느림 |

이 서비스들의 핵심 로직은 도메인 규칙이 아니라 재시도, 멱등, 타임아웃(NFR-7)입니다. 그래서 A의 선언적 기능이 주는 생산성 이점은 작게 작용하고, 실패 경로가 코드에 드러나는 B, D가 리뷰와 장애 분석에 조금 유리합니다. 이 차이는 취향으로 반박될 수 있어 결정의 주 근거로 쓰지 않습니다.

### 4-4. 결정을 가르지 않는 것

아래는 흔히 언어 선택 이유로 꼽히지만, 이 시스템에서는 모든 후보가 충족하거나 차이가 작아 기준에서 뺐습니다.

| 항목 | 판단 | 근거 |
|---|---|---|
| 대량 동시 I/O 대기 | 모두 충족 | A는 Virtual Threads([JEP 444](https://openjdk.org/jeps/444). JDK 24부터 `synchronized` pinning 해결, 네이티브 호출 중 pinning은 남음), B는 goroutine, C는 이벤트 루프, D는 tokio |
| 정상 상태 GC 꼬리 지연 | 모두 NFR-4 충족 | A는 ZGC로 정지 ms 이하, B는 객체를 옮기지 않는 동시 mark-sweep([Go GC 가이드](https://go.dev/doc/gc-guide)), D는 GC 없음. 200ms 예산 앞에서 차이가 작음 |
| 멀티코어 사용 | 모두 가능 | C도 cluster나 1 vCPU 파드로 해결. 필요한 DB 커넥션 수는 프로세스 수가 아니라 `QPS × 쿼리 지연`(리틀의 법칙)이 정하므로, 프로세스가 많아도 풀을 작게 나누면 총합은 비슷함 |
| 인스턴스 메모리 | B, D가 작음 | 인스턴스 밀도는 달라지지만, 이 시스템의 비용은 이그레스가 지배함(NFR-8) |
| 정상 상태 CPU 처리량 | A의 JIT가 장기 실행에서 유리 | 이 서비스들에 CPU 병목이 없음(1장) |
| 생태계 | 모두 인프라 클라이언트 성숙 | 예외: Kafka Streams(프로세스 내장 상태 기반 스트림 처리)는 Java 전용. ADR-0009에서 이것을 고르면 9장 조건 |
| 대규모 사례 | 모두 있음 | A: Netflix는 백엔드 대부분이 Spring Boot 기반 Java 앱(약 2,800개)([InfoQ 발표](https://www.infoq.com/presentations/netflix-java/)). B: YouTube가 MySQL 확장을 위해 만든 Vitess가 Go로 쓰였음([Vitess 역사](https://vitess.io/docs/overview/history/), [저장소](https://github.com/vitessio/vitess)). 사례로는 결정이 갈리지 않음 |

### 4-5. 종합 (A vs B)

| 기준 | 순위 | A. Java 25 + Spring | B. Go |
|---|---|---|---|
| 스케일아웃 중 p99 (NFR-4, NFR-7) | 1 | 장치로 충족 (AOT 캐시, CRaC, 워밍업 트래픽, 여유 대수) | 기본값으로 충족 |

| 지속 복잡도 | 3 | 장치 운영 + 프레임워크 규칙 이해. 대신 직접 짜는 코드가 적음 | 트랜잭션, 설정, 조립을 직접 짬 |
| 프로세스 내장 스트림 처리 (FR-5) | 조건부 | 가능 (Kafka Streams) | 불가, 별도 엔진 필요 |

## 5. 결정 전 검증

## 6. 추천안

**B. Go**를 추천합니다.

어떤 후보든 장치를 더하면 이 시스템을 만들 수 있습니다. 그래서 가장 중요한 기준을 기본값으로 충족하는지, 나머지 비용이 얼마인지로 골랐습니다.

1. **주 근거: 스케일아웃 중에도 p99를 지킵니다 (NFR-4, NFR-7).** 메타데이터 API는 트래픽이 가장 높을 때 인스턴스를 늘리고, 그때 새 인스턴스가 받는 요청 비율만큼 p99가 그 인스턴스의 지연으로 정해집니다(4-1). Go는 빌드 시 네이티브로 컴파일되어 새 인스턴스가 첫 요청부터 최종 성능을 냅니다. Java도 AOT 캐시, CRaC로 줄일 수 있지만, 학습 실행 단계, 체크포인트 관리, 컨테이너 권한 같은 운영 장치를 하나씩 더해야 합니다.
2. **보조 근거: 정상 취소 경로에서 작업 취소가 외부 프로세스까지 전파됩니다 (FR-2, NFR-5, NFR-7).** 배포와 인스턴스 회수로 워커가 중간에 멈추는 일은 이 규모에서 일상이고, 취소가 끊기면 고아 FFmpeg와 결과 섞임이 생깁니다(4-2). 강제 종료 경로는 언어와 무관하게 커널 장치가 맡습니다. Go는 `context` 하나가 서드파티 라이브러리와 `exec.CommandContext`까지 닿는 것이 생태계 관례입니다.
3. **Rust가 아닌 이유:** 기준 1, 2를 똑같이 기본값으로 충족하지만, 그 이상의 이득(GC 없음, 더 적은 메모리)이 나올 CPU 병목이 없습니다. 반면 async 복잡도와 취소 안전성 비용은 모든 서비스가 계속 치릅니다(4-3).

### 잃는 것

- Kafka Streams처럼 서비스 프로세스 안에 상태 기반 스트림 처리를 넣는 선택지. 조회수 집계가 이것을 필요로 하면 Flink 같은 별도 엔진을 쓰거나 직접 구현해야 합니다(ADR-0009).
- 트랜잭션 관리, 설정 바인딩, 의존성 조립 같은 Spring의 선언적 기능. 직접 짜야 하고, 그 코드도 리뷰 대상이 됩니다.
- JIT의 장기 CPU 처리량. 지금은 CPU 병목이 없어 작지만, 9장 첫 조건이 생기면 커집니다.

### A가 맞는 경우

- 조직에 이미 JVM 플랫폼이 있다. 이때는 기준 1을 메우는 장치도 이미 플랫폼에 있을 가능성이 크고, 플랫폼을 다시 만드는 비용이 언어 특성 차이보다 큽니다.
- ADR-0009에서 조회수 집계를 서비스 프로세스 안의 Kafka Streams로 하기로 정한다.
- 5장 측정에서 Java(AOT 캐시)의 정상 p99 도달 시간이 오토스케일 반응 시간보다 충분히 짧게 나온다.

### 면접에서 말하는 순서 (30초)

> 이 시스템의 비용과 지연은 CDN, FFmpeg, 캐시가 정하고, 우리가 짜는 서버는 외부 시스템을 기다리는 얇은 조정자입니다. 그래서 어떤 언어로도 만들 수 있고, 차이는 기본값으로 얻느냐 장치를 더해 얻느냐입니다. 가장 중요한 기준은 피크 중 증설할 때 p99를 지키는 것인데, JIT 언어는 새 인스턴스가 워밍업 중이라 그 인스턴스가 받는 비율만큼 p99가 흔들립니다. Go는 네이티브 컴파일이라 이 문제가 기본값으로 없고, 워커 취소도 context 하나로 FFmpeg 종료까지 전파됩니다. Rust도 이 두 기준을 충족하지만 이득이 나올 CPU 병목이 없어 복잡도만 남습니다. 대신 Kafka Streams는 포기하고, 조직에 JVM 플랫폼이 있다면 Java를 골랐을 겁니다.

## 8. 결과

- B를 고르면: 트랜잭션, 설정, 의존성 조립을 직접 짜므로 그 코드도 방어 대상이 된다. 모든 외부 호출에 `context`와 타임아웃을 넘기는 규칙을 코드 리뷰 기준에 넣고, `noctx`, `contextcheck` 린터를 CI에 넣는다. FFmpeg는 `Pdeathsig`와 프로세스 그룹을 설정해 띄운다. ADR-0009에서 Kafka Streams는 선택지에서 빠진다
- A를 고르면: AOT 캐시 학습 실행이나 워밍업 트래픽을 배포 파이프라인에 넣는다. 이 시스템이 쓰는 Spring 자동 설정(트랜잭션, 커넥션 풀, Kafka 리스너)의 동작 원리를 설명할 수 있어야 한다. 외부 호출마다 타임아웃과 취소를 따로 연결한다
- 프로젝트 비용 (결정 기준 아님): B는 goroutine 스케줄러, GC 동작, `context` 전파 학습 시간을 W2 전에 따로 잡는다. 5장 비교 측정용 Java 엔드포인트 작성에 반나절 정도를 잡는다. B는 로컬 L-1 안에서 레플리카를 더 많이 띄울 수 있어 선형성 측정이 쉬워지는 부수 효과가 있다

## 9. 이 결정이 깨지는 조건

- 서비스가 CPU를 쓰는 로직을 떠안는 경우. 예: 서버 사이드 광고 삽입, 요청마다 도는 추천 점수 계산. JIT의 장기 처리량(A)이나 GC 없는 실행(D)이 의미를 갖는다. 그 계층만 따로 고르는 것도 검토한다
- 이 시스템이 기존 JVM 플랫폼을 가진 조직에 들어가는 경우 (2장 전제)
- ADR-0009가 서비스 프로세스 내장 스트림 처리를 요구하는 경우
- 5장 측정에서 Java(AOT 캐시)의 기동 후 정상 p99 도달 시간이 오토스케일 반응 시간(지표 수집 주기와 파드 기동 시간의 합)보다 충분히 짧아, 4-1의 차이가 사라지는 경우

## 11. 예상 꼬리질문

| 질문 | 답의 요지 |
|---|---|
| 왜 이 언어인가? | 어떤 언어로도 만들 수 있다. 가장 중요한 기준(증설 중 p99)과 보조 기준(취소 전파)을 기본값으로 충족하는 후보 중 비용이 가장 작은 것이 Go다 |
| Node.js도 cluster로 멀티코어를 쓰면 되지 않나? | 된다. 그래서 멀티코어는 기준에서 뺐다(4-4). Node가 빠진 이유는 기준 1에서 V8 JIT 워밍업이 남아 Java와 같은 쪽에 서고, 나머지 기준에서 Go보다 나은 점이 없어서다 |
| Rust가 더 빠르고 GC도 없는데? | 기준 1, 2는 Go와 똑같이 충족한다. 그 이상의 이득은 CPU 병목에서 나오는데 이 서비스들에는 없고, async 복잡도와 취소 안전성 비용은 모든 서비스가 치른다 |
| JDK 25면 AOT 캐시, CRaC로 워밍업이 풀리지 않나? | 줄일 수 있다. 다만 학습 실행, 체크포인트 관리, 컨테이너 권한 같은 운영 장치가 늘어난다. 차이가 작다는 측정이 나오면 다시 연다(9장) |
| Virtual Threads가 나왔으니 Java도 goroutine과 같지 않나? | JDK 24 이후 동시성 모델의 차이는 작다. 그래서 동시성은 결정 이유가 아니다(4-4) |
| 그럼 JIT 언어는 AOT보다 불리한가? | 아니다. JIT는 실행 중 관찰로 더 높은 최고 성능을 얻는 대신 워밍업을 치른다. 오래 켜 두는 CPU 중심 계층에서는 JIT가 유리하고, 자주 증설되는 I/O 조정자에서는 AOT가 유리하다(4-1). 조회수 집계 계층은 JVM 엔진이 맞을 수 있다 |
| Go도 PGO가 있지 않나? | 있다. 운영 프로파일을 빌드에 넣어 JIT식 최적화 일부를 빌드 시점에 얻는다. 우리 서비스는 CPU 병목이 없어 지금은 도입하지 않고, CPU가 병목이 되면 먼저 검토한다 |
| readiness 검사가 있으면 워밍업 인스턴스가 트래픽을 안 받지 않나? | readiness는 기동과 커넥션 준비만 알리고 JIT 상태는 모른다. JIT는 실제 요청을 받아야 데워진다. slow start로 줄일 수 있지만 새 용량이 늦게 투입되는 비용이 있다(4-1) |
| context가 SIGKILL도 막나? | 못 막는다. 정상 취소 경로는 context가, 강제 종료는 커널(`Pdeathsig`, 프로세스 그룹, 컨테이너 PID 1)이, 부분 업로드는 시도별 경로와 커밋이 막는다. Go는 그 커널 장치를 표준 라이브러리로 바로 쓴다(4-2) |
| AOT면 워밍업이 아예 없나? | 코드 실행 속도의 워밍업만 없다. 커넥션 풀, 로컬 캐시 워밍업은 모든 언어에 똑같이 있다 |
| Netflix는 Java로 대규모 스트리밍을 운영하는데? | 모든 후보가 그 규모에서 된다. Netflix는 약 2,800개 Java 앱을 Spring Boot로 표준화한 조직이고(4-4), 그것이 9장 두 번째 조건이다 |
| 실제 YouTube는 무엇을 쓰나? | 공개 자료로 확인한 것은 MySQL 확장 계층 Vitess가 YouTube에서 Go로 만들어졌다는 것이다(4-4). 전체 언어 구성은 단정하지 않는다. 대규모에서는 한 언어가 아니라 계층별로 고른다. 우리도 스트림 엔진은 따로 고른다(ADR-0009) |
| 트랜스코딩은 CPU를 많이 쓰는데 언어가 중요하지 않나? | CPU를 쓰는 건 FFmpeg다. 워커는 조정자라 프로세스 관리와 취소 전파가 중요하다 |
| 명시적 오류 처리가 좋아서 고른 것 아닌가? | 아니다. 이 서비스들에서 조금 유리하지만 취향으로 반박될 수 있어 주 근거로 쓰지 않았다(4-3) |
| 메모리를 적게 쓰니 비용이 싸지 않나? | 인스턴스 밀도는 좋아지지만 이 시스템 비용은 이그레스가 지배한다(NFR-8) |
| GC 때문에 p99가 튀면? | 10장 지표로 먼저 확인한다. 할당 경로를 줄이는 게 먼저고, `GOGC`, `GOMEMLIMIT` 튜닝은 그다음이다 |
