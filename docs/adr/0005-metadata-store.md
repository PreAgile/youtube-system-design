# ADR-0005: 메타데이터 저장소

| 항목 | 값 |
|---|---|
| 상태 | Proposed |
| 분류 | 제품 설계 |
| 작성일 | 2026-09-29 |
| 결정일 | |
| 관련 FR/NFR | FR-2 처리 상태, FR-4 메타데이터 조회, NFR-4 메타데이터 p99, NFR-6 read-your-writes, NFR-7 멱등과 수평 확장 |
| 관련 ADR | ADR-0002 언어, ADR-0008 캐시, ADR-0010 Outbox, ADR-0011 샤딩 키 |

## 1. 맥락

[데이터 모델](../design/01-data-model.md)의 영상, 업로드 세션, 해상도별 변환 상태를 저장할 DB를 정해야 합니다. W2의 API 명세와 W3의 첫 구현(메타데이터 API)이 이 결정을 기다립니다.

### 이 저장소의 부하 모양

| 항목 | 값 | 출처 |
|---|---|---|
| 읽기 | 피크 약 6만 9,000건/초. 캐시 히트율 95%를 가정하면 DB에 약 3,500건/초 | 00-scope.md, 데이터 모델 7-1 |
| 쓰기 | 약 170건/초. 대부분 상태 전이 같은 작은 조건부 UPDATE | 데이터 모델 5장 |
| 조회 모양 | PK 조회, `(channel_id, visibility, published_at, video_id)` 인덱스 범위 조회. 복잡한 조인이나 집계 없음 | 데이터 모델 5장 |
| 크기(가정) | 1년 약 550GB, 5년 약 2.7TB | 데이터 모델 7-1 |
| 일관성 | 일반 시청자는 약간 늦어도 되지만, 크리에이터는 자기 쓰기를 즉시 봐야 함 | NFR-6 |

이 모양이 결정의 방향을 정합니다. **쓰기는 한 대로 충분하고, 읽기는 복제본으로 늘리며, 몇 년 뒤에는 데이터 크기 때문에 샤딩합니다**(데이터 모델 7-2). 그래서 질문은 "어느 DB가 더 빠른가"가 아니라 이것입니다.

> **복제본으로 읽기를 늘리는 단계와, 그 뒤 샤딩으로 가는 단계를 가장 적은 추가 장치로 밟을 수 있는 DB는 무엇인가?**

## 2. 결정을 강제하는 요구사항

### 필수 조건 (하나라도 못 맞추면 탈락)

| 요구사항 | 제약 |
|---|---|
| NFR-7 멱등 | 조건부 UPDATE와 여러 행을 묶는 트랜잭션(데이터 모델 4장) |
| FR-4 | 보조 인덱스로 채널별 최신순 범위 조회 |
| NFR-4 | PK 조회와 범위 조회가 캐시 미스 경로에서도 p99 200ms 예산 안 |
| NFR-7 수평 확장 | 읽기 복제본, 이후 샤딩으로 가는 경로가 있어야 함 |
| 운영 | 관리형 서비스, 백업과 시점 복구, Go 드라이버 성숙 |

### 결정 기준 (우선순위 순)

| 순위 | 기준 | 연결 요구사항 | 우선순위의 이유 |
|---|---|---|---|
| 1 | **샤딩으로 가는 경로가 검증되었는가** | NFR-7 | 5년 약 2.7TB로 커지는 데이터를 결국 나눠야 함. 한번 고른 DB는 바꾸기 가장 어려운 결정 |
| 2 | **복제본에서 read-your-writes를 기본으로 지원하는가** | NFR-6 | 2단계(복제본)부터 매일 쓰는 경로. 직접 만들면 모든 크리에이터 읽기에 붙는 코드가 됨 |
| 3 | **복제본 읽기가 프라이머리와 서로 간섭하지 않는가** | NFR-4 | 읽기를 복제본으로 보내는 것이 이 설계의 기본 확장 수단 |
| 4 | **자주 바뀌는 작은 행의 갱신 비용** | 없음(참고 기준) | 상태 전이가 쓰기의 대부분이지만, 쓰기 약 170건/초에서는 어느 요구사항의 한계에도 닿지 않음. 그래서 순위를 가르는 데 쓰지 않고 참고로만 둠 |

### 전제

- 신규 시스템이고, 조직에 이미 운영 중인 DB 플랫폼이 없습니다(ADR-0002와 같은 전제).
- 조회수는 이 DB의 행을 조회마다 갱신하지 않습니다(ADR-0009).

## 3. 선택지

### 후보

| 후보 | 설명 |
|---|---|
| A. MySQL 8.4 LTS (InnoDB) | 샤딩 단계에서 Vitess |
| B. PostgreSQL 18 | 샤딩 단계에서 Citus, 또는 Multigres |
| C. 분산 SQL (CockroachDB, TiDB, Spanner 등) | 처음부터 자동 샤딩과 합의 기반 복제 |
| D. 키-값 또는 와이드 컬럼 NoSQL (DynamoDB, Cassandra 등) | 파티션 키 기반 수평 확장 |

### 거르는 방법

| 단계 | 질문 | 통과 | 떨어진 후보와 이유 |
|---|---|---|---|
| 1 | 필수 조건을 충족하는가 | A, B, C | D는 여러 행 트랜잭션과 조건부 전이(영상, 업로드 세션, 해상도 행을 함께 바꿈)와 채널별 범위 조회를 모두 테이블 설계와 애플리케이션 코드로 풀어야 함. 불가능하지는 않지만, 이 데이터 모델의 핵심인 트랜잭션을 포기하는 비용이 얻는 확장성보다 큼 |
| 2 | 지금 필요한 것에 비해 비용이 맞는가 | A, B | C는 샤딩을 처음부터 제공하지만, 쓰기마다 합의(consensus) 왕복이 커밋 지연에 더해짐. 쓰기 약 170건/초인 지금은 샤딩이 몇 년 뒤의 일이라(1장), 그때까지 쓰지 않는 기능의 지연을 매 쓰기마다 치름 |
| 최종 | A와 B 비교 | 4장 | |

C는 9장의 "깨지는 조건"에서 다시 등장합니다.

**엔진과 배포 형태는 다른 축입니다.** Aurora 같은 공유 스토리지형 관리형 DB는 MySQL과 PostgreSQL 호환판이 모두 있고, 클러스터 볼륨이 최대 256TiB까지 자랍니다([AWS 발표](https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-aurora-mysql-database-clusters-256-tib-storage/)). 이 배포 형태를 쓰면 5년 약 2.7TB는 한 클러스터 안에 들어가고, 샤딩이 필요한 시점은 A와 B 모두 더 늦어집니다. A와 B의 순서는 바꾸지 않지만, **기준 1(샤딩 경로)이 결정에 주는 무게를 줄입니다.** 이 점은 4-1과 6장에 반영합니다. 어떤 배포 형태를 쓸지는 이 ADR의 범위가 아니며, 로컬 측정(5장)은 엔진 단위로 합니다.

A의 버전은 최신 LTS인 9.7이 아니라 8.4입니다. 2026년 9월 기준 Vitess는 MySQL 8.0과 8.4까지만 지원하고, 9.7 지원은 계획 단계이기 때문입니다([Vitess 지원 DB](https://vitess.io/docs/25.0/overview/supported-databases/)). 샤딩 경로(기준 1)를 끊지 않는 버전을 고릅니다.

## 4. 평가

### 4-1. 기준 1: 샤딩으로 가는 경로

| | A. MySQL + Vitess | B. PostgreSQL + Citus / Multigres |
|---|---|---|
| 도구 | Vitess: MySQL 앞에 라우팅 계층(VTGate)을 두고 샤드를 하나의 DB처럼 보이게 함([Vitess 개요](https://vitess.io/docs/overview/whatisvitess/)) | Citus: PostgreSQL 확장으로 행 기반, 스키마 기반 샤딩([Citus 문서](https://docs.citusdata.com/en/stable/get_started/what_is_citus.html)). Multigres: Vitess 공동 창시자가 만드는 PostgreSQL판 Vitess. 다만 v0.1 알파에는 샤딩 기능이 아직 없음 |
| 성숙도 | CNCF 졸업 프로젝트(2019)([CNCF](https://www.cncf.io/projects/vitess/)). YouTube의 DB 트래픽을 5년 넘게 처리했고(과거형. 현재 YouTube의 사용 여부는 공개 자료로 확인하지 못함), Slack, Square 등이 운영 | Citus는 오픈소스로 성숙. Multigres는 2026년 6월 4일 v0.1 알파이며, 문서가 프로덕션용이 아니라고 밝힘([Supabase](https://supabase.com/blog/multigres-v0-1-alpha)) |
| 이 시스템과의 거리 | YouTube의 MySQL 확장 문제에서 출발한 도구. 영상 PK 조회와 채널별 목록 같은 접근 패턴에 맞을 것이라는 판단은 이 설계의 추론이며, 공개 자료가 직접 말하는 것은 아님 | Citus는 다중 테넌트와 분석 쿼리 분산에 강점. 이 시스템에서도 쓸 수 있지만 같은 모양의 대규모 사례는 A보다 적음 |
| 샤딩 뒤 read-your-writes | VTGate가 `@@read_after_write_gtid`를 받아 복제본에서 `WAIT_FOR_EXECUTED_GTID_SET`을 실행함. 4-2의 방식이 샤딩 뒤에도 같은 모양으로 유지됨([Vitess sysvars](https://pkg.go.dev/vitess.io/vitess/go/vt/sysvars), [RFC #6843](https://github.com/vitessio/vitess/issues/6843)) | Citus와 Multigres에서 같은 기능은 확인하지 못함 |

B에도 경로가 있습니다. 차이는 **샤딩이 필요해졌을 때 쓸 수 있는 도구가 지금 검증돼 있는가**입니다.

이 기준에는 약점이 있습니다. 샤딩은 몇 년 뒤의 일이고, 공유 스토리지형 배포를 쓰면 더 늦어지거나 오지 않을 수도 있습니다(3장). 그때의 PostgreSQL 쪽 도구 상태는 지금 알 수 없습니다. 그래도 1순위로 두는 이유는 비용의 비대칭입니다. 샤딩이 필요해졌는데 경로가 없으면 데이터가 가장 클 때 DB 엔진을 옮겨야 합니다. 반대로 A를 골라서 잃는 표현력은 지금 쿼리가 단순해서 작습니다(4-5). 다만 이 비대칭은 "샤딩이 실제로 온다"는 가정에 달려 있으므로, 결정의 확신도 그만큼 낮습니다(6장).

### 4-2. 기준 2: 복제본에서 read-your-writes

데이터 모델 7-3의 방법(쓰기 뒤 복제 위치를 들고 있다가, 복제본이 따라온 뒤 읽기)을 DB가 얼마나 지원하는지 봅니다.

| | A. MySQL | B. PostgreSQL 18 |
|---|---|---|
| 쓰기 뒤 위치 받기 | `session_track_gtids = OWN_GTID`로 커밋 응답(OK 패킷)에 GTID가 실려 옴([MySQL WL#6972](https://dev.mysql.com/worklog/task/?id=6972)) | 커밋 뒤 `pg_current_wal_lsn()`을 따로 조회 |
| 복제본에서 기다리기 | `WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)`. 문서는 "GTID 집합이 적용될 때까지 기다리는 함수"로 설명하고, read-your-writes는 그 응용([MySQL 문서](https://dev.mysql.com/doc/refman/8.4/en/gtid-functions.html)). Vitess가 같은 용도로 씀(4-1) | 18에서는 `pg_last_wal_replay_lsn()`을 반복 조회(폴링). 기본 명령 `WAIT FOR LSN`은 PostgreSQL 19부터. 2026년 9월 24일 Beta 4이고 10월 정식 출시 예정([PostgreSQL 19 문서](https://www.postgresql.org/docs/19/sql-wait-for.html), [로드맵](https://www.postgresql.org/developer/roadmap/)) |
| 기본값으로 충족 | 예 | 18에서는 직접 구현, 19부터 예 |

**커밋 시점에 보장하는 방법도 있습니다.** PostgreSQL은 18에서도 `synchronous_commit = remote_apply`로, 동기 대기 복제본이 커밋을 적용해 조회에 보일 때까지 커밋을 기다리게 할 수 있습니다([PostgreSQL 문서](https://www.postgresql.org/docs/18/runtime-config-wal.html)). MySQL에도 Group Replication의 일관성 설정이 있습니다. 둘 다 이 설계의 기본안으로 두지 않는 이유는 같습니다. 보장 범위가 동기 대기 복제본뿐이라, 읽기 확장을 위해 늘리는 비동기 복제본 N대에는 적용되지 않습니다. 또 모든 쓰기가 복제본 적용까지 기다리므로 커밋 지연이 크게 늘고(문서도 이를 명시), 동기 복제본이 멈추면 쓰기도 멈춥니다. 크리에이터의 자기 읽기는 전체 읽기의 작은 일부이므로, 그 일부를 위해 모든 쓰기의 지연과 가용성을 내주는 것은 맞지 않습니다.

이 기준의 차이는 **PostgreSQL 19 정식 출시와 함께 거의 사라집니다.** 결정 시점에 19가 나와 있으면 이 기준은 동률로 봅니다. 남는 차이는 샤딩 뒤에도 같은 방식이 도구로 지원되는가이고, 그것은 기준 1(4-1)에서 다룹니다.

### 4-3. 기준 3: 복제본 읽기와 프라이머리의 간섭

| | A. MySQL | B. PostgreSQL |
|---|---|---|
| 복제 방식 | 논리 복제(binlog). 복제본은 받은 변경을 자기 InnoDB에 다시 적용 | 물리 복제(WAL). 복제본은 프라이머리와 바이트 단위로 같은 페이지를 가짐 |
| 복제본의 긴 읽기 | 프라이머리의 정리 작업과 충돌하지 않음. 다만 복제본 안에서는 긴 읽기가 메타데이터 잠금을 잡고 있으면, 복제돼 온 DDL이 그 잠금을 기다리며 복제 지연이 생김([MySQL 문서](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html)) | 프라이머리의 `VACUUM`이 지운 행을 복제본의 읽기가 아직 보고 있으면 충돌. 기다리다 `max_standby_streaming_delay`를 넘으면 **복제본 쿼리를 취소**함. 막으려고 `hot_standby_feedback`을 켜면 프라이머리에서 죽은 행 정리가 늦어져 **테이블이 부풂**([PostgreSQL 문서](https://www.postgresql.org/docs/current/hot-standby.html)) |

이 시스템의 복제본 읽기는 대부분 짧은 PK 조회라 두 DB 모두 충돌이 드물 것으로 예상합니다. 그래서 이 기준의 변별력은 작습니다. 차이는 충돌이 났을 때 영향이 어디로 가느냐입니다. B는 프라이머리의 테이블 부풂(모든 사용자에게 영향)이나 복제본 쿼리 취소 중에서 골라야 하고, A는 복제본 하나의 지연으로 끝납니다.

### 4-4. 기준 4: 자주 바뀌는 작은 행의 갱신

| | A. MySQL (InnoDB) | B. PostgreSQL |
|---|---|---|
| UPDATE 동작 | 행을 제자리에서 고치고 옛 값은 undo 로그에 둠 | 새 행 버전을 쓰고 옛 버전은 나중에 `VACUUM`이 정리 |
| 인덱스 갱신 | 바뀐 컬럼이 들어 있는 인덱스만 | 인덱스에 든 컬럼이 안 바뀌고 페이지에 빈 공간이 있으면 HOT 갱신으로 인덱스를 건드리지 않음. 아니면 모든 인덱스에 새 항목([PostgreSQL 문서](https://www.postgresql.org/docs/current/storage-hot.html)) |
| 이 시스템에서 | 상태 컬럼 갱신 비용이 작음 | 데이터 모델은 `status`에 인덱스를 두지 않으므로 상태 전이는 대부분 HOT 갱신이 될 수 있음. 인덱스 컬럼인 `published_at`이 처음 찍히는 한 번만 모든 인덱스를 갱신. 나중에 워커가 상태로 조회하려고 `status` 인덱스를 추가하면 달라짐 |

Uber가 2016년 PostgreSQL에서 MySQL로 옮기며 든 이유(쓰기 증폭, 물리 복제의 대역폭)가 이 항목과 기준 3입니다([Uber 블로그](https://www.uber.com/blog/postgres-to-mysql-migration/)). 다만 PostgreSQL 9.2 시절 이야기이고 그 뒤 많이 개선됐으므로, 경향을 보여 주는 사례로만 씁니다. 쓰기가 약 170건/초이고 데이터 모델상 HOT이 대부분 유지되는 이 시스템에서는 **참고 기준**입니다.

### 4-5. B가 이기는 것

| 항목 | 내용 |
|---|---|
| 표현력 | 부분 인덱스, JSONB, 풍부한 SQL, 트랜잭션 안의 DDL |
| 쿼리 계획기 | 복잡한 조인과 집계에 강함 |
| 확장 생태계 | PostGIS, pgvector 등 |
| 생태계 흐름 | 신규 서비스에서 채택이 늘고 있고, Multigres처럼 샤딩 경로도 빠르게 생기는 중 |

이 시스템의 쿼리는 PK 조회와 단순 범위 조회라(1장) 이 강점이 지금은 작게 작용합니다. 추천, 검색, 분석이 범위에 들어오면 달라집니다(9장).

### 4-6. 결정을 가르지 않는 것

| 항목 | 판단 |
|---|---|
| 단일 노드 성능 | 이 부하(DB 기준 약 3,500 읽기/초, 170 쓰기/초)는 둘 다 한 대로 충분 |
| 온라인 스키마 변경 | MySQL은 컬럼 추가가 기본 `INSTANT`([MySQL 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)), PostgreSQL도 기본값 있는 컬럼 추가가 빠름. 큰 테이블 변경은 둘 다 별도 도구가 필요 |
| 클러스터형 인덱스 | InnoDB는 PK 순서로 행을 저장하고 보조 인덱스에 PK를 담음([MySQL 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)). 데이터 모델 3장의 짧고 시간순인 PK는 두 DB 모두에서 좋은 선택이라 결정과 무관 |
| Go 드라이버, 관리형 서비스 | 둘 다 성숙 |

### 4-7. 종합 (A vs B)

| 기준 | 순위 | A. MySQL 8.4 + Vitess | B. PostgreSQL 18 + Citus / Multigres |
|---|---|---|---|
| 샤딩 경로의 검증 (NFR-7) | 1 | 대규모 운영으로 검증, 샤딩 뒤 read-your-writes까지 지원 | Citus는 경로 있음, Multigres는 샤딩 전 알파. 같은 모양의 대규모 사례는 적음 |
| 복제본 read-your-writes (NFR-6) | 2 | 기본 지원 | 18은 직접 구현, 19부터 기본. 19 출시 뒤 동률 |
| 복제본과 프라이머리 간섭 (NFR-4) | 3 | 프라이머리 영향 없음, 복제본 안에서 DDL 지연 | 쿼리 취소와 테이블 부풂 사이 절충. 둘 다 드묾 |
| 작은 행 갱신 | 참고 | 유리 | 데이터 모델상 HOT 대부분 유지 |
| 표현력, 생태계 | 참고 | 보통 | 유리 |

| 복제 지연 | 쓰기 부하를 늘리며 복제본 지연 측정 | 데이터 모델 7-3 |
| 인스턴스당 단위 용량 | 캐시 미스 경로의 PK 조회, 채널 목록 조회 p99와 최대 QPS | NFR-4, 데이터 모델 7-1의 3,500건/초 |

## 6. 추천안

**A. MySQL 8.4 LTS (InnoDB)** 를 추천합니다.

1. **주 근거: 샤딩이 필요해졌을 때의 경로가 지금 검증돼 있습니다 (NFR-7).** Vitess는 대규모 운영으로 검증됐고, 샤딩 뒤에도 같은 GTID 방식의 read-your-writes를 지원합니다(4-1). 샤딩이 실제로 오는지는 불확실하지만, 오면 데이터가 가장 클 때 엔진을 옮겨야 한다는 비대칭 때문에 1순위로 둡니다. 버전은 Vitess가 지원하는 8.4로 고릅니다.
2. **보조 근거: 복제본에서 read-your-writes를 지금 기본 기능으로 합니다 (NFR-6).** 다만 PostgreSQL 19가 나오면 이 차이는 사라집니다(4-2).
3. **보조 근거: 복제본 쪽 충돌이 프라이머리로 번지지 않습니다 (NFR-4).** 두 DB 모두 드물어 변별력은 작습니다(4-3).

**확신의 정도:** A와 B의 차이는 크지 않습니다. 2와 3은 작거나 곧 사라지는 차이이고, 결정은 사실상 1의 비대칭 하나에 걸려 있습니다. 그 비대칭은 "샤딩이 실제로 필요해진다"는 가정에 달려 있으므로, 멘토 세션에서는 이 가정과 공유 스토리지형 배포(3장)를 함께 검토받습니다.

### 잃는 것

- PostgreSQL의 표현력과 확장 생태계(부분 인덱스, JSONB, PostGIS, pgvector). 지금은 쿼리가 단순해 작지만, 검색이나 추천이 들어오면 커집니다.
- 최신 LTS(9.7)의 기능. Vitess가 9.7을 지원할 때까지 8.4에 머뭅니다.
- PostgreSQL 쪽으로 기우는 생태계 흐름. 몇 년 뒤 Multigres가 샤딩까지 갖추고 성숙하면 기준 1의 차이가 줄어듭니다.

### B가 맞는 경우

- 조직에 이미 PostgreSQL 운영 역량과 플랫폼이 있다.
- 검색, 추천, 분석처럼 복잡한 쿼리나 확장 기능이 메타데이터 DB에 들어온다.
- 샤딩이 오지 않는다고 판단할 근거가 있다(공유 스토리지형 배포로 운영 한계 안에 머무는 경우). 그러면 기준 1의 무게가 사라지고, PostgreSQL 19 이후로는 표현력이 남는 차이가 된다.
- Multigres나 Citus가 이 모양의 부하에서 검증된다(9장).

### 면접에서 말하는 순서 (30초)

> 메타데이터는 쓰기가 초당 170건이라 한 대로 충분하고, 읽기는 초당 6만 9,000건이지만 캐시와 복제본으로 늘립니다. 샤딩은 쓰기 때문이 아니라 몇 년 뒤 수 TB로 커지는 데이터 때문에 하고, 공유 스토리지형 관리형을 쓰면 더 늦어질 수도 있습니다. 그래서 차이는 "샤딩이 필요해졌을 때 검증된 경로가 있느냐"에 걸려 있고, Vitess가 있는 MySQL 8.4를 추천합니다. Vitess는 샤딩 뒤에도 GTID로 크리에이터의 read-your-writes를 지원합니다. 대신 PostgreSQL의 표현력을 포기합니다. 복제본 read-your-writes의 차이는 PostgreSQL 19로 사라지므로, 둘의 차이는 크지 않다는 것도 함께 말합니다.

## 8. 결과

- 이 결정으로 치르는 비용: PK는 짧고 시간순이어야 함(데이터 모델 3장). 복제본 읽기 경로에 GTID를 들고 다니는 코드. Vitess로 갈 때를 대비해 샤드를 넘는 조인과 트랜잭션을 만들지 않는 쿼리 규칙
- 이 결정이 새로 만드는 문제: Vitess가 9.7을 지원하기 전까지 8.4에 머묾. 8.4의 지원 종료 전에 Vitess와 함께 올리는 계획이 필요
- 후속으로 필요한 ADR: ADR-0011(샤딩 키). 샤드를 넘는 쿼리 규칙은 그때 확정

## 9. 이 결정이 깨지는 조건

- 메타데이터 DB에 검색, 추천, 분석 같은 복잡한 쿼리나 확장 기능이 필요해지는 경우
- 조직에 PostgreSQL 플랫폼이 있는 곳으로 들어가는 경우
- 샤딩 시점(데이터 모델 7-2)에 Multigres나 Citus가 이 모양의 부하에서 검증된 경우. 그때는 샤딩 전 마이그레이션 비용과 비교해 다시 연다
- 공유 스토리지형 배포로 샤딩 없이 운영 한계 안에 머문다는 판단이 서는 경우. 기준 1의 무게가 사라지므로 다시 연다
- 쓰기가 크게 늘어 한 대의 프라이머리로 부족해지고, 합의 기반 자동 샤딩의 비용을 치를 가치가 생기는 경우(C 재검토)

## 11. 예상 꼬리질문

| 질문 | 답의 요지 |
|---|---|
| 왜 PostgreSQL이 아닌가? | 둘 다 한 대 단계에서는 충분하고, 복제본 read-your-writes 차이는 PostgreSQL 19로 사라진다. 남는 차이는 샤딩이 필요해졌을 때 검증된 경로가 있느냐다(4-1). 차이가 크지 않다는 것을 인정하고, 샤딩이 실제로 온다는 가정에 기대고 있다고 말한다 |
| PostgreSQL의 `remote_apply`면 read-your-writes가 기본 아닌가? | 동기 대기 복제본에만 적용되고, 모든 쓰기가 적용까지 기다려 지연이 늘며, 동기 복제본이 멈추면 쓰기도 멈춘다. 일부 읽기를 위해 모든 쓰기를 내주는 것이라 기본안으로 두지 않았다(4-2) |
| Aurora를 쓰면 샤딩이 필요 없지 않나? | 그럴 수 있고, 그러면 기준 1의 무게가 줄어든다. 배포 형태는 엔진과 다른 축이라 A와 B 모두에 해당한다. 그래서 확신이 낮다고 6장에 적었다(3장, 9장) |
| 왜 최신 LTS인 9.7이 아니라 8.4인가? | Vitess가 아직 8.4까지만 지원한다. 샤딩 경로를 끊지 않는 버전을 골랐다 |
| 쓰기가 170건/초인데 왜 샤딩을 이야기하나? | 쓰기가 아니라 데이터 크기 때문이다. 수 TB가 되면 백업, 복구, 스키마 변경, 복제본 추가 시간이 운영 한계에 닿는다(데이터 모델 7-2) |
| 처음부터 CockroachDB나 Spanner를 쓰면? | 샤딩이 몇 년 뒤의 일인데 쓰기마다 합의 왕복과 운영 비용을 지금부터 치른다. 쓰기가 크게 늘면 다시 검토한다 |
| DynamoDB 같은 NoSQL은? | 영상, 업로드 세션, 해상도 행을 함께 바꾸는 트랜잭션과 채널별 범위 조회가 이 모델의 핵심이라, 그걸 애플리케이션으로 푸는 비용이 크다 |
| 크리에이터가 수정 직후 옛 값을 보면? | 커밋 응답의 GTID를 세션에 들고, 복제본에서 `WAIT_FOR_EXECUTED_GTID_SET`으로 기다린 뒤 읽는다. 제한 시간을 넘으면 프라이머리에서 읽는다 |
| 복제 지연이 크게 늘면? | 일반 시청자는 늦은 값을 봐도 되고(NFR-6), 크리에이터 읽기는 프라이머리로 넘어간다. 10장 지표로 프라이머리 부하를 같이 본다 |
| PK를 UUID로 하면 안 되나? | InnoDB는 PK 순서로 행을 저장하고 보조 인덱스마다 PK를 담는다. 무작위 UUID는 삽입마다 페이지를 쪼개고 인덱스를 키운다. 내부 PK는 시간순 BIGINT로 두고, 주소에는 추측할 수 없는 무작위 `public_id`를 따로 쓴다(데이터 모델 3장) |
| Uber가 MySQL로 옮긴 이유가 지금도 유효한가? | 2016년 PostgreSQL 9.2 시절 이야기라 그대로 적용하지 않는다. 경향(쓰기 증폭, 물리 복제)만 참고했고 이 시스템에서는 4순위다 |
