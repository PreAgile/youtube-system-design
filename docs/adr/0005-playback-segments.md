# ADR-0005: 재생 방식과 세그먼트 길이

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-06 |
| 결정일 | 2026-10-06 |
| 관련 FR/NFR | FR-3, FR-4, NFR-2, NFR-3, NFR-4, NFR-6, NFR-8 |

## 1. 문제와 제약

재생 중 네트워크가 10Mbps에서 1.5Mbps로 떨어져도 재생을 멈추지 않고 화질을 바꿔야 한다(FR-3, NFR-4). 원하는 위치로 이동하고 연결 복구 후 이어볼 수 있어야 한다(FR-4, NFR-3, NFR-8). 재생 시작은 기준 네트워크 p95 ≤ 2초, 취약 네트워크 p95 ≤ 4초다(NFR-2). 변환 결과는 화질별로 저장소에 있다([ADR-0003](0003-transcoding-executor.md), [ADR-0004](0004-transcoding-failure-handling.md)).

## 2. 대안과 판단 기준

기준은 (1) 재생을 멈추지 않는 화질 전환, (2) 네트워크 판단의 정확도와 지연, (3) 시청자별 서버 상태 유무, (4) 시청자 가까이 복사·캐시할 수 있는지(NFR-2 대비), (5) 위치 이동·복구의 단순성이다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| A. 화질별 파일 하나 + 구간 요청 | 변환 결과가 단순하다 | 시각을 바이트 위치로 바꾸는 색인이 필요하고 전환이 거칠다 |
| B. 세그먼트 + 매니페스트, client가 화질 판단(HTTP) | 세그먼트 경계마다 전환한다. client가 직접 측정한다. 서버 상태가 없다. 같은 URL은 같은 파일이라 캐시할 수 있다 | 화질 간 같은 시각 경계와 키프레임 정렬이 필요하다. 파일·요청 수가 많다 |
| C. 송출 서버가 시청자별로 밀어줌(서버 판단) | 서버가 즉시 화질을 바꾼다. 초저지연에 유리하다 | 피크 약 625만 세션을 유지해야 한다. 일반 HTTP 캐시를 쓸 수 없다. 서버는 client 피드백으로 추정한다 |
| D. HTTP 세그먼트 + 서버가 화질 결정 | 서비스가 화질을 통제한다 | 판단마다 왕복이 늘고 서버는 client 보고로 추정한다 |

세그먼트 길이 비교 [계산: 취약 네트워크 1.5Mbps·RTT 300ms, 360p 0.7Mbps(가정), 첫 프레임까지 순차 왕복 약 5회(가정), 손실·디코딩 제외]:

| 길이 | 첫 세그먼트 다운로드 | 재생 시작 합계 | 피크 세그먼트 요청 |
|---|---|---|---|
| 2초 | 약 0.93초 | 약 2.4초 | 초당 약 310만 건 |
| 4초 | 약 1.87초 | 약 3.4초 | 초당 약 156만 건 |
| 6초 | 약 2.8초 | 약 4.3초(NFR-2 취약 4초 초과) | 초당 약 104만 건 |

짧을수록 시작·이동·전환 반응이 빠르고, 길수록 요청 수가 적고 키프레임이 드물어 압축 효율이 높다.

## 3. 사용자 제안과 검토

- 사용자 첫 제안: client가 네트워크를 추적하고 재생 목록을 미리 당겨 받으며 다음 파일마다 계산해 화질을 낮춘다. 파일 전체 다운로드는 무리이므로 실시간 송출 서버(UDP)가 필요할 것 같다고 추측했다.
- 면접관 검토(LLM): 앞부분은 B의 핵심과 같다. HTTP도 세그먼트 단위로 받으므로 송출 서버가 필요 없다. 문제는 UDP가 아니라 시청자별 송출 구조이며, HTTP/3도 UDP 위에서 동작한다.
- 사용자가 처음 든 "매니페스트를 통한 인증"은, 공개 영상 범위이고 세그먼트를 저장소에서 직접 받으면 매니페스트 조회만으로 세그먼트 접근이 통제되지 않아 이유에서 뺐다. 세그먼트 접근 통제는 후속 주제로 둔다.
- 사용자는 처음 6초 이상을 제안했으나 위 계산에서 NFR-2 취약 네트워크 목표를 넘는 것을 확인했다.

## 4. 결정과 이유

사용자가 B와 4초 세그먼트를 선택했다.

- 변환 작업자는 화질별 결과를 4초 세그먼트로 만들고, 모든 화질이 같은 시각 경계에서 키프레임으로 시작하게 한다. 화질 목록과 세그먼트 주소를 담은 매니페스트를 함께 만든다.
- 재생: client가 백엔드의 재생 정보 API에서 매니페스트 위치를 받고, 매니페스트와 세그먼트를 저장소에서 직접 HTTP로 받는다. client가 측정한 처리량과 버퍼 잔량으로 다음 세그먼트의 화질을 고른다.

이유(사용자가 동의한 항목):

- client가 실제 네트워크를 가장 빠르고 정확하게 알아 서버 왕복 없이 바로 판단한다.
- 세그먼트 단위로 받아야 client가 매번 맞는 화질을 고를 수 있다.
- 시청자별 서버 상태가 없다.
- 같은 URL은 같은 파일이라 시청자 가까이 복사·캐시할 수 있다(NFR-2).
- 위치 이동과 연결 복구가 해당 세그먼트를 다시 요청하는 것으로 끝난다(FR-4, NFR-3, NFR-8).
- 재생은 완성된 세그먼트만 읽어 변환 장애와 분리된다(NFR-6).
- 4초는 취약 네트워크 재생 시작 계산에서 NFR-2를 충족하고, 위치 이동·전환 반응도 6초보다 빠르다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 재생 경로에 시청자별 서버 상태가 없고, 다음 단계에서 세그먼트를 시청자 가까이 둘 수 있다.
- 비용: 6초보다 요청이 약 1.5배 많고 키프레임이 잦아 같은 화질에 비트가 더 든다. 영상당 파일 수가 많아진다(10분 영상, 4화질 기준 약 600개).
- 결과가 여러 파일이므로 ADR-0004의 시도별 위치 + 조건부 등록 방식이 그대로 필요하다.

## 6. 검증과 남은 불확실성

- 재생 시작 계산은 순차 왕복 횟수와 화질별 비트레이트를 가정한 값이다. 실제 연결 수립 왕복 수와 손실 영향은 측정해야 한다.
- 세그먼트 길이별 파일 크기 차이(압축 효율)는 변환 측정 실험에서 함께 확인한다.
- 세그먼트 형식(업계 표준 형식 중 무엇을 쓸지)과 세그먼트 접근 통제는 정하지 않았다.
- 재생 정보 API가 백엔드·RDB를 지나므로 이 경로의 격리는 NFR-2 단계에서 다룬다.
- 범위 정정(2026-10-08, PR #9 리뷰): 4절의 "연결 복구가 세그먼트 재요청으로 끝난다"는 재생 중 네트워크 복구에만 해당한다. 앱 재접속 후 마지막 위치에서 이어보기(FR-4, NFR-8)는 위치 기록이 필요하며 이 결정에 포함되지 않는다.

## 7. 재검토 조건

- 측정한 재생 시작 시간이 4초 세그먼트로도 NFR-2를 넘거나, 2초로도 충분히 여유가 있을 때.
- 세그먼트 요청 수가 캐시를 도입한 뒤에도 비용·부하 문제가 될 때.
- 초저지연 라이브처럼 서버 송출이 필요한 범위가 추가될 때.
