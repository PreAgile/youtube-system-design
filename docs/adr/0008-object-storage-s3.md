# ADR-0008: 객체 저장소로 Amazon S3 사용

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-07 |
| 결정일 | 2026-10-07 |
| 관련 FR/NFR | FR-1, NFR-7, NFR-2 |

## 1. 문제와 제약

ADR-0001~0007은 영상 원본·세그먼트·매니페스트를 담는 곳을 "객체 저장소(Storage)"로만 불렀다. 업로드 재개(청크 목록 조회), 완료 검증, 보존(NFR-7), 엣지 중계, CDN 원본처럼 저장소의 실제 기능에 기대는 결정이 쌓여, 어떤 저장소인지 정해야 각 결정의 전제를 확인할 수 있다.

## 2. 대안과 판단 기준

기준은 (1) 청크(파트) 단위 업로드와 이미 올린 파트 조회, (2) 가용 영역 하나의 장애에도 원본 보존(NFR-7), (3) 엣지 중계·CDN과의 연결이다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| 특정 제품을 정하지 않고 "객체 저장소"로 유지 | 제품에 묶이지 않는다 | 파트 크기·개수 한도, 보존 범위 같은 전제를 확인할 수 없다 |
| Amazon S3 | 멀티파트 업로드와 파트 목록 조회를 제공한다. 기본 등급은 3개 이상 가용 영역에 저장한다. Transfer Acceleration·CloudFront와 연결된다 | AWS에 묶인다. 파트 한도와 요금 체계를 따라야 한다 |

다른 클라우드의 객체 저장소는 이번에 비교하지 않았다.

## 3. 사용자 제안과 검토

- 사용자 결정: 저장소를 S3라고 부르는 것이 맞다며 README와 그림의 Storage를 S3로 바꾸도록 했다.
- 면접관 검토(LLM): S3로 정하면 앞선 결정의 전제를 문서로 확인할 수 있다.
  - 멀티파트 한도: 업로드당 파트 10,000개, 파트 크기 5MiB~5GiB(마지막 파트 제외), 파트 목록 조회는 한 번에 최대 1,000개([문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)). 20GB를 5MiB 파트로 나누면 약 3,800개라 한도 안이며, 재개 때 목록 조회는 최대 4번 나눠 받는다[계산].
  - 보존: S3 Standard는 3개 이상 가용 영역에 저장하고 가용 영역 하나의 물리적 손실에 견디도록 설계되었다([문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html#sc-compare)). One Zone 등급은 이 조건을 만족하지 않으므로 원본에 쓰지 않는다.
  - 엣지 중계(ADR-0007)는 S3 Transfer Acceleration이 같은 방식이다([문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/transfer-acceleration.html)).

## 4. 결정과 이유

사용자가 객체 저장소를 Amazon S3(한국 리전)로 정했다. 원본은 S3 Standard 등급에 둔다. 이유(사용자): 저장소를 S3라고 부르는 것이 맞다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 업로드 재개(파트 목록 조회), 완료(멀티파트 완료 후 검증), 보존(다중 가용 영역)의 전제를 공식 문서로 확인할 수 있다.
- 비용: AWS에 묶인다. 청크 크기는 5MiB 이상이어야 하고, 파트가 1,000개를 넘으면 재개 조회가 여러 번 필요하다.

## 6. 검증과 남은 불확실성

- 보존·가용성 수치는 AWS의 설계 목표이며 이 시스템에서 측정한 값이 아니다.
- 완료 처리 중 장애(멀티파트 완료 후 RDB 갱신 전 중단)의 재시도 흐름은 PR #9 리뷰에서 지적되었고 아직 정하지 않았다.
- 청크 크기와 병렬 수는 측정 후 정한다.

## 7. 재검토 조건

- 다른 클라우드나 자체 저장소로 옮겨야 하는 요구가 생길 때.
- 원본이 S3 한도(객체 최대 크기, 파트 수)를 넘는 요구가 생길 때.
