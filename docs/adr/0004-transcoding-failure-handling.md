# ADR-0004: 변환 작업의 실패 처리와 대기열

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 작성일 | 2026-10-06 |
| 결정일 | 2026-10-06 |
| 관련 FR/NFR | FR-2, NFR-5, NFR-6 |

## 1. 문제와 제약

변환은 자체 작업자가 실행한다([ADR-0003](0003-transcoding-executor.md)). 작업자가 변환 도중 죽거나 멈추면 영상이 "처리 중"에 갇히지 않아야 하고, 기준 화질은 p95 5분 안에 준비되어야 한다(NFR-5). 장애 판단이 틀려 같은 작업이 두 번 실행될 수 있으므로 결과가 섞이거나 낡은 결과가 최신 결과를 덮어쓰지 않아야 한다. 깨진 원본은 무한히 재시도되지 않고 실패 상태로 드러나야 한다(FR-2).

## 2. 대안과 판단 기준

기준은 (1) 멈춘 작업까지 감지하는가, (2) 단일 장애점이 없는가, (3) 중복 실행에도 결과가 하나로 정해지는가, (4) 감지 지연이 NFR-5에 맞는가, (5) 부품 수다.

| 유력 대안 | 기준에 따른 장점 | 비용과 한계 |
|---|---|---|
| 중앙 헬스체크 후 재배정 | 직관적이고 작업자 현황을 한눈에 본다 | 감시자가 단일 장애점이다. 서버 단위라 멈춘 작업을 놓친다. 감시자가 배정을 모두 관여해 유연하지 않다. 중복 실행·재시도 상한을 따로 설계해야 한다 |
| 작업 임대 + 진행 중 연장 | 작업 단위로 감시한다. 감시자가 없고 만료된 작업은 아무 작업자나 가져간다 | 임대 시간이 짧으면 중복 실행, 길면 감지 지연이 늘어난다. 중복 실행은 결과 등록 단계에서 막아야 한다 |
| 주기적 정리 작업(스위퍼) | 구현이 가장 단순하다 | 감지가 느리고 대략적이라 단독으로는 NFR-5를 맞추기 어렵다 |
| 대기열: RDB 작업 표 | 새 부품이 없다. 임대·조건부 갱신이 같은 곳에 있다 | 작업자 폴링·임대 연장 부하가 메타데이터 RDB에 함께 걸린다 |
| 대기열: 별도 대기열 시스템 | 임대 기능을 기본 제공하고 부하가 RDB와 분리된다 | 운영할 부품이 늘어난다 |

## 3. 사용자 제안과 검토

- 사용자 첫 제안: 서버가 헬스체크로 작업자 생존과 작업 진행을 확인하고, 죽으면 다른 서버로 옮기거나 확장해 마저 작업한다.
- 면접관 검토(LLM): 서버 생존과 작업 진행은 다르고, 중앙 감시자는 단일 장애점이며, 오판 시 중복 실행이 생긴다. 변환은 보통 작업 단위를 처음부터 다시 한다. 장애 복구와 확장은 별개 문제다.
- 면접관 정정(LLM): 결과를 (영상, 화질) 고정 위치에 덮어쓰자는 첫 제안은 결과가 여러 파일일 때 두 실행의 파일이 섞일 수 있어, 시도별 위치에 쓰고 RDB가 승자 위치를 가리키는 방식으로 바꿨다.
- 사용자가 개념을 확인했다: 만료된 작업은 별도 감시자가 아니라 할 일을 찾는 작업자의 조회 조건으로 회수된다. 임대번호(펜싱 토큰)는 작업자 번호가 아니라 작업을 가져간 횟수이며, 중복 실행이 아니라 중복 등록을 막는다.

## 4. 결정과 이유

사용자가 다음 조합을 선택했다.

- 화질별 작업으로 나누고 360p를 우선한다.
- 작업자는 작업을 가져갈 때 임대번호를 올리고 임대 만료 시각을 기록하며, 진행 중이면 연장한다. 만료된 작업은 다른 작업자가 할 일을 조회할 때 가져간다.
- 결과는 시도별 위치에 저장하고, 현재 임대번호와 같을 때만 RDB의 화질 상태와 결과 위치를 갱신한다.
- 시도 횟수 상한(3회)을 넘으면 작업과 영상을 실패로 표시한다.
- 정리 작업은 작업 복구가 아니라 아무도 가리키지 않는 시도 결과와 만료된 업로드 청크를 지우는 데 쓴다.
- 대기열은 RDB 작업 표로 시작하고, 부하가 걸리면 별도 대기열 시스템으로 옮긴다.

이유(사용자): 중앙 헬스체크는 단일 장애점이 생기고 멈춘 작업을 놓치며 감시자가 모든 것을 관여해 유연하지 않고, 중복 실행과 재시도 상한이 고려되지 않아 무한 재배정될 수 있다. 스위퍼는 단순하지만 대략적이라 NFR을 충족하지 못한다. 처리 상태 폴링(ADR-0002)과 같이, 현재 규모에서는 RDB 조회로 단순하게 처리하고 부하가 걸리면 큐로 옮긴다.

## 5. 얻는 것과 감수한 비용

- 얻는 것: 감시자 없이 작업 단위로 장애가 회수된다. 중복 실행이 생겨도 RDB는 한 번의 실행 결과만 가리킨다. 깨진 원본은 실패로 드러난다. 새 부품이 없다.
- 비용: 중복 실행 시 CPU가 낭비된다. 시도별 결과와 만료 청크를 지우는 정리 작업이 필요하다. 작업자 폴링과 임대 연장 부하가 메타데이터 RDB에 함께 걸린다.

## 6. 검증과 남은 불확실성

- 계산[처리 시간 5분 가정]: 작업 생성 초당 약 23건(5.8개 × 4화질), 영상 기준 임대 연장 초당 약 58건(동시 약 1,740개 ÷ 30초)이며 화질별 작업 수만큼 늘어난다. 측정값이 아니다.
- 미검증: 임대 시간(예: 2분, 30초마다 연장)과 재시도 간격. 변환 시간을 측정한 뒤 NFR-5에 맞춰 정한다.
- 미검증: 작업자 동시 조회 시 행 잠금과 건너뛰기 동작은 선택할 RDB에서 확인한다.

## 7. 재검토 조건

- 작업자 폴링·임대 연장이 RDB 부하로 나타나거나 API의 RDB 응답(NFR-1)이 흔들릴 때 별도 대기열 시스템으로 옮긴다.
- 중복 실행으로 인한 CPU 낭비가 측정상 의미 있는 비율이 될 때 임대 시간을 조정한다.
- 화질 결과의 저장 형식이 정해진 뒤 시도별 위치 방식이 맞는지 다시 확인한다.
