# 리뷰 기준

이 저장소의 리뷰는 코드 품질보다 **결정의 논리**를 먼저 검증합니다. 모든 PR은 "왜 이렇게 했나, 무엇을 포기했나, 왜 그게 최선인가"에 답할 수 있어야 하고, 리뷰어(사람, 봇, CI)는 그 답의 빈틈을 찾습니다.

## 1. 모든 리뷰가 묻는 질문

| # | 질문 | 이런 경우 지적한다 |
|---|---|---|
| Q1 | 무엇을 결정했나 | 결정이 한 문장으로 요약되지 않는다. 여러 결정이 한 ADR에 섞여 있다 |
| Q2 | 어떤 요구사항이 이 결정을 강제하나 | FR/NFR을 적었지만 결정과 인과 관계가 없다(장식용 연결). 요구사항 없이 취향으로 골랐다 |
| Q3 | 대안은 충분히 검토했나 | 가장 강한 대안이 빠졌다. 일부러 약하게 쓴 대안과만 비교했다 |
| Q4 | 트레이드오프는 무엇인가 | 얻는 것만 있고 잃는 것이 없다. 잃는 것을 왜 감당할 수 있는지 근거가 없다 |
| Q5 | 왜 이것이 최선인가 | 평가 기준과 가중치가 요구사항에서 나오지 않았다. 평가표 결과와 추천이 어긋나는데 이유가 없다 |
| Q6 | 근거는 믿을 만한가 | 측정 조건 없는 숫자, 출처 없는 주장, "일반적으로 빠르다" 같은 일반론 |
| Q7 | 언제 이 결정이 틀리게 되나 | 깨지는 조건이 구체적인 수치나 사건이 아니다 |
| Q8 | 운영에서 맞았는지 어떻게 아나 | 결정의 성공과 실패를 판단할 지표가 없다 |
| Q9 | 코드가 결정과 일치하나 | 코드가 Accepted ADR과 다르게 구현됐다. ADR 없는 새 결정이 코드에 들어왔다 |
| Q10 | 다른 결정과 충돌하지 않나 | 다른 ADR의 가정이나 결론과 모순된다 |

## 2. 근거의 강도

강한 근거부터 씁니다. 약한 근거만 있는 주장은 Q6으로 지적합니다.

1. 이 저장소에서 로컬 측정한 값 (조건 포함)
2. 공식 문서, 명세, 소스 코드
3. 공개된 대규모 운영 사례
4. 일반론

## 3. 코멘트 분류

리뷰 코멘트 앞에 분류를 붙여서, 반영할지 반박할지 빨리 가를 수 있게 합니다.

| 분류 | 뜻 | 연결 질문 |
|---|---|---|
| `[논리 공백]` | 결론까지 가는 중간 단계가 빠졌다 | Q1, Q2, Q5 |
| `[대안 누락]` | 검토해야 할 대안이 빠졌거나 약하게 쓰였다 | Q3 |
| `[트레이드오프 누락]` | 잃는 것이 적혀 있지 않다 | Q4 |
| `[근거 부족]` | 주장에 근거가 없거나 약하다 | Q6 |
| `[깨지는 조건 모호]` | 재검토 시점을 판단할 수 없다 | Q7, Q8 |
| `[ADR 불일치]` | 코드와 ADR, 또는 ADR끼리 어긋난다 | Q9, Q10 |
| `[구현 결함]` | 데이터 유실, 중복 처리, 타임아웃 누락, 리소스 누수 | 코드 리뷰 |

문체, 이름, 서식 같은 지적은 위 분류보다 우선순위가 낮습니다.

## 4. 역할 분담

| 검증자 | 맡는 것 |
|---|---|
| CI (`scripts/check_design.py`) | 기계적으로 확인 가능한 것: ADR 섹션 구조, 선택지 2개 이상, 분류별 요구사항 ID 필수 여부와 존재, Accepted ADR 변경 제한(5장), Superseded 대상 존재, 목록과 파일 일치, PR 본문의 ID 존재와 '잃는 것', 긴 대시, 깨진 링크 |
| AI 리뷰 봇 | 이 문서의 Q1~Q10으로 논리 검증, 코드 결함 |
| 멘토 세션 | 봇이 판단할 수 없는 것: 범위 선택의 타당성, 면접관 관점의 설득력 |
| 결정자 | 모든 지적을 반영하거나, 근거를 들어 반박하고 PR에 답글로 남긴다 |

## 5. Accepted ADR에 허용되는 변경

Accepted ADR은 고치지 않고 새 ADR로 대체하는 것이 원칙입니다. CI는 아래 두 가지만 허용합니다.

1. 상태를 `Superseded by ADR-XXXX`로 바꾸는 것. 대체한 ADR 파일이 실제로 있어야 합니다.
2. 형식 보완. 기존 줄을 하나도 바꾸거나 지우지 않고 줄을 추가하는 것만 허용하며, 7번 결정 섹션은 한 글자도 바뀌면 안 됩니다. 추가한 부분에는 "형식 보완" 표시와 날짜를 남깁니다.

사람의 판단에 맡기는 예외는 두지 않습니다. 1인 프로젝트에서 리뷰어의 확인은 곧 자기 확인이기 때문입니다.

## 6. ADR 분류

| 분류 | 뜻 | 요구사항 연결 |
|---|---|---|
| 제품 설계 | 시스템의 동작, 구조, 기술 선택에 관한 결정 | 관련 FR/NFR에 요구사항 ID가 하나 이상 있어야 함 |
| 프로젝트 운영 | 문서화, 리뷰, 진행 방식에 관한 결정 | ID 없이 서술 가능 |
