## 2. 첫 세션 전 어디까지 작업하나

| 순서 | 우선도 | 작업 | 완료 기준 |
|---|---|---|---|
| 1 | 선행 | PR #8 정리 | 미해결 리뷰와 사실 주장을 원문으로 재확인하고 데이터 모델과 업로드 계약의 불일치를 해소한다. 머지 후 가이드를 별도 PR로 분리한다 |
| 2 | 필수 | Excalidraw HLD 완성본과 시퀀스 2개 | 네 경로를 한 장에 연결하고 업로드 완료·복구, 재생 시작의 경계를 그린다 |
| 3 | 필수 | 최소 API 명세 | 그림의 요청에 대응하는 요청/응답·권한·멱등성·실패 후 결과 확인을 적는다 |
| 4 | 필수 | ADR-0007 초안 | 포맷·세그먼트·매니페스트·인가·갱신 질문에 추천안 또는 미정 사유가 있다 |
| 5 | 필수, 분량 제한 | 작업 큐·이벤트 비교 메모 | 후보, 기준, 추천 방향, ACK·중복·재시도 계약과 미정 사항만 적는다 |
| 6 | 필수 | 45분 리허설 2회 | 빈 보드에서 설명하고 1회차에 넘친 구간을 줄이며 막힌 질문을 기록한다 |

시간이 부족하면 ADR-0003·0004의 정식 11개 섹션 문서화와 추가 그림부터 미룬다. 비교 메모는 HLD에 두고, 정식 ADR로 만들 때는 저장소 템플릿을 따른다. 전체 경로, 최소 API, 재생 계약, 리허설은 남긴다. 세션까지 이것도 어렵다면 구현을 시작하기보다 검토 범위를 멘토와 조정한다.

API 명세의 권장 위치는 `docs/design/02-api.md`, HLD는 `docs/design/03-high-level-design.md`다. 아직 없는 파일이며, 작성할 때 이 가이드에 링크를 추가한다.

HLD 그림의 편집 원본은 `excalidraw/`의 `.excalidraw` 파일로 둔다. `03-high-level-design.md`는 원본 링크, 내보낸 그림, 화살표 설명과 미정 사항을 담는다. 완성본을 수정하면 내보낸 그림도 갱신한다. 빈 연습본은 발표 연습용이며 설계의 기준 원본을 대신하지 않는다.

API 범위는 업로드 시작·파트 서명·재개·완료, 영상 조회·수정, 채널 목록, 재생 정보, 크리에이터·운영자의 재처리 요청, 조회 이벤트 수집이다. 각 API에서 누가 호출하는지, 같은 요청이 두 번 오면 어떻게 되는지, 실패 뒤 무엇으로 결과를 확인하는지 적는다. 조회 이벤트의 시청 판정과 중복 키는 후보를 표시하고 상세 결정은 ADR-0009에서 한다.

**첫 세션의 정지선:** 업로드 시작부터 여러 해상도의 변환본·매니페스트 생성, CDN을 통한 적응형 재생까지 전체 경로를 설명한다. 업로드 재개와 완료 복구, 워커 실패, 인기 영상의 부하를 질문받으면 보드에서 설계를 구체화할 수 있다.

CDN과 메타데이터 캐시, API·워커 확장, DB 복제·샤딩의 필요 조건은 첫 설계 발표에 포함한다. 캐시 정책, 조회수 집계, 샤딩, 글로벌 설계의 상세 ADR과 구현·측정은 로드맵의 후속 단계에서 다룬다. 설계 설명이 가능하다는 것과 구현 검증이 끝났다는 것을 구분한다.

### 인터뷰 수준으로 설명할 최소 범위

참고: [Hello Interview 제작자의 YouTube 설계 자료](https://www.hellointerview.com/learn/system-design/problem-breakdowns/youtube), [사용자가 제시한 영상](https://www.youtube.com/watch?v=IUrQ5_g3XKs). 영상 직접 재생은 확인하지 못했으며, 아래 범위는 제작자의 공개 글과 저장소 요구사항을 대조한 준비 목표다.

| 주제 | 보드에서 설명할 질문 |
|---|---|
| 요구사항·엔티티·API | 업로드와 재생에서 무엇을 보장하며, 영상 바이트와 메타데이터는 왜 나누는가? |
| 대용량 업로드와 재개 | 바이트가 API를 우회하는 이유, 파트 진행 확인, 완료 검증과 중간 종료 복구는? |
| 비동기 변환 파이프라인 | 원본에서 어떤 변환본과 매니페스트를 만들고, 작업을 어떻게 병렬화·재시도하는가? |
| 적응형 재생 | 플레이어가 매니페스트와 세그먼트를 받아 네트워크 상태에 따라 화질을 바꾸는 흐름은? |
| CDN과 캐시 | CDN 미스 시 어디로 가고, 영상 바이트 캐시와 메타데이터 캐시는 어떻게 다른가? |
| 확장과 장애 | API·워커·DB·스토리지 중 무엇이 먼저 병목이며, 어떤 경로가 장애여도 재생이 가능한가? |
| 조회수 경로 | 이벤트를 버퍼링·집계하는 이유와 중복 제거 경계는? W2에는 경로와 미정 사항을 보여주고 상세는 W7에서 검증한다 |

업로드 파트는 전송·재개 단위이고, 재생 세그먼트는 재생 가능한 미디어 단위다. 두 가지를 같은 조각으로 취급하지 않는다. 또한 참고 자료의 DB나 처리 구조를 그대로 채택하지 않고, 이 저장소의 접근 패턴과 상태 전이 요구로 대안을 평가한다.

### 참고 자료와 다르게 잡은 부분

아래 비교는 제작자의 공개 글 기준이다. 영상 전체의 구현 선택과 같다고 단정하지 않는다.

| 주제 | Hello Interview 공개 글 | 이 저장소의 방향과 이유 |
|---|---|---|
| 메타데이터 DB | 영상 ID 단건 조회 중심으로 Cassandra와 videoId 파티셔닝 | MySQL 추천안(Proposed). 조건부 상태 전이·완료 트랜잭션, 채널 범위 조회와 read-your-writes를 함께 다룬다(FR-2, FR-4, NFR-6, NFR-7) |
| 처리 시작 | S3 객체 생성 알림에서 처리 서비스로 연결 | API가 스토리지 완료를 검증하고 세션·영상·Outbox 기록을 한 DB 트랜잭션으로 반영하는 방향. 완료 복구와 중복 처리의 경계를 명시한다(NFR-5, NFR-7). 전달·소비 계약은 ADR-0010에서 결정한다 |
| 병렬 작업 | 시간 구간 세그먼트별 DAG 처리 | 현재 모델의 해상도별 상태와 attempt를 기준으로 시작한다(FR-2, NFR-7). 긴 영상의 처리 시간이 목표를 못 맞추면 구간 분할을 대안으로 평가한다. 구간·해상도별 상태, GOP/키프레임 정렬, 결과 합치기와 매니페스트 확정 비용이 추가된다 |
| 조회수 | 핵심 범위 밖이며 추가 딥다이브 | FR-5로 포함한다. W2에 수집·버퍼링·집계 경로를 표시하고, 중복 제거와 반영 지연의 상세 설계·검증은 W7에서 한다(NFR-6, NFR-7) |

### ADR-0007에서 답할 재생 질문

- 변환본과 미디어·마스터 재생 목록은 누가 만들고, 언제 재생 가능한 결과로 확정하는가?
- 새 해상도가 준비되면 마스터 재생 목록의 URL·버전을 바꾸는가? CDN 캐시 키·TTL·무효화와 플레이어의 재조회는 어떻게 연결되는가?
- 재생 정보 API의 준비된 해상도 목록과 매니페스트 내용이 잠시 다를 때 무엇을 기준으로 재생하는가?
- 긴 영상 재생 중 서명 만료를 어떻게 갱신하며, 갱신 실패 때 재생은 어떻게 되는가?
- 세그먼트마다 서명 URL을 발급할지, 경로 범위 서명이나 쿠키로 인가할지? 매니페스트·세그먼트 접근과 캐시 키에 어떤 비용이 생기는가?
- 공개 범위를 비공개로 바꿀 때 기존 재생 권한이 언제까지 남는가? 토큰 유효 시간과 캐시의 지연을 어떻게 제한하는가?

이 질문은 결정할 계약이며 현재 구현으로 보장되는 동작이 아니다. 저해상도 선공개 정책도 데이터 모델의 미정 사항과 함께 결정한다.

## 3. 내가 잡은 판단 기준

다음은 기존 FR/NFR을 발표용으로 묶은 것이다. 개별 기술의 평가 기준과 우선순위는 각 ADR에서 별도로 설명한다.

| 기준 | 연결 요구사항 | 선택할 때 묻는 질문 | 검증할 것 |
|---|---|---|---|
| 경로 격리 | NFR-1, NFR-7 | 업로드와 인코딩의 부하·장애가 준비된 영상의 재생을 흔드는가? | 업로드 부하, 워커 종료 중 재생과 메타데이터 지연 |
| 정합성과 복구 | NFR-5, NFR-7 | 완료 응답은 무엇을 보장하고, 중복 요청과 중간 종료 뒤 어떻게 복구하는가? | 동시 완료, 스토리지 완료 후 API 종료, 작업 중복 전달 |
| 사용자별 일관성 | FR-3, NFR-6 | 즉시 보여야 하는 상태와 지연을 허용하는 값은 무엇인가? | 자기 변경 조회, 권한 검사, 조회수 중복 제거와 반영 지연 |
| 확장 경로 | FR-4, NFR-7 | 인스턴스 증가 뒤 공유 병목은 무엇이며, 복제·샤딩으로 넘어갈 조건과 비용은? | 레플리카 1·2·3의 선형성, DB 저장량·조회 병목. ADR-0005의 샤딩 경로 비교와 연결 |
| 성능과 비용 검증 | NFR-3, NFR-4, NFR-8 | 목표 지연을 지키는 용량은 얼마이며, 어떤 자원이 먼저 병목이 되는가? | API p99, 재생 세 구간, 인코딩 속도와 변환본 크기 |

판단 순서: **필수 조건을 만족하는가 → 가장 중요한 기준을 어떻게 충족하는가 → 추가 운영 비용과 포기하는 것은 무엇인가 → 어떤 실험이 추천안을 뒤집을 수 있는가.**

## 4. 멘토에게 설명하는 순서

세션 준비 기준은 45분 모의 인터뷰다. 아래 10분 요약은 인터뷰 뒤 피드백 정리 또는 짧은 세션의 대체안이다. 10분 발표 후 45분 인터뷰를 연속으로 해야 한다는 뜻이 아니다. 시간은 연습용 배분이며 성능 목표가 아니다.

| 시간 | 설명 | 보여줄 자료 |
|---|---|---|
| 0~1분 | 목적과 범위 | FR/NFR, 제외 범위 |
| 1~3분 | 핵심 문제와 판단 기준 | 영상의 중간 상태, 위 기준 표 |
| 3~5분 | 전체 흐름 | HLD 한 장 |
| 5~8분 | 업로드 선택과 실패 복구 | ADR-0006, API, 상태 전이 |
| 8~10분 | 미검증 가정, 실험, 피드백 요청 | 검증 목록과 질문 |

### 45분 보드 연습

| 시간 | 그리거나 적을 것 | 설명 목표 |
|---|---|---|
| 0~5분 | 핵심 FR/NFR, 제외 범위, 규모 가정 | 멘토와 문제 범위를 합의한다 |
| 5~10분 | 주요 엔티티와 API | 데이터와 요청의 경계를 정한다 |
| 10~20분 | 업로드·변환·재생·조회수 HLD | 기능이 동작하는 전체 경로를 연결한다 |
| 20~35분 | 선택한 딥다이브 2개 | 업로드 복구, 해상도별 변환, 적응형 재생 중 2개를 질문에 따라 깊게 다룬다. 나머지는 HLD에서 입출력과 실패 경계를 설명한다 |
| 35~39분 | CDN, 메타데이터 캐시, 병목과 확장 | 인기 영상과 부하 증가에 대응한다 |
| 39~42분 | 조회 이벤트 수집·버퍼링·집계·중복 제거 경계 | 매 조회마다 영상 행을 갱신하지 않는 이유와 W7에서 결정할 항목을 설명한다 |
| 42~45분 | 미검증 가정과 다음 실험 | 설계 가정과 실제 검증 결과의 경계를 설명한다 |

멘토 질문에 따라 딥다이브 시간은 조정한다. 모든 기술의 상세 ADR을 낭독하지 않고, 해당 결정이 필요한 지점에서 이유와 대안을 설명한다.

Excalidraw에는 공부용 완성본과 빈 연습본을 준비한다. 연습본에서 요구사항부터 직접 그리며 상자는 책임, 화살표는 전달 데이터와 시점을 설명한다. 가이드는 사전 준비와 복습에 사용한다.

### 시작: 무엇을 만들고 왜 이 범위인가

> YouTube의 핵심 경로 중 업로드한 영상이 여러 해상도로 재생 가능해지는 과정과 메타데이터·조회수까지 잡았습니다. 추천과 검색은 제외했습니다. 이 프로젝트의 목적은 중간 상태와 장애 복구를 직접 구현하고 측정해서 설계를 검증하는 것입니다.

### 문제: 내가 어렵다고 본 것은 무엇인가

> 영상이 저장됐다고 바로 재생 가능한 건 아닙니다. 업로드는 끝났지만 변환이 진행 중일 수 있고, 360p만 먼저 준비될 수도 있습니다. 완료 요청과 작업이 중복되거나 프로세스가 죽어도 원본이 유실되거나 상태가 잘못 넘어가지 않게 하는 것을 핵심 문제로 봤습니다.

### 기준: 기술을 고르기 전에 무엇을 우선했나

> 경로 격리, 정합성과 복구, 사용자별 일관성, 확장 경로, 측정 가능한 성능과 비용을 기준으로 잡았습니다. 각 선택에서는 필수 조건을 먼저 확인하고, 가장 중요한 기준을 충족하는 방식과 추가 운영 비용을 비교했습니다.

### 예시: 왜 Presigned Multipart를 추천하나

> 업로드는 요청 수보다 바이트와 연결 시간이 문제라서, 파일은 객체 스토리지로 직접 보내고 API는 제어 요청을 맡기는 방식을 추천합니다. 대신 클라이언트의 파트 관리가 복잡해지고 업로드 중 내용 검사는 포기합니다. 스토리지와 DB는 한 트랜잭션으로 묶을 수 없으므로, 스토리지만 완료된 경우를 확인하고 DB 상태 전이를 복구하는 경로를 두었습니다. 아직 구현 검증 전인 추천안입니다.

여기서 HLD의 업로드 화살표를 짚고 API, 세션 상태, 영상 상태, Outbox 기록 순서로 내려간다. 언어와 DB 선택은 이 흐름에 필요한 조건을 설명한 뒤 소개한다.

### 경계: 무엇이 사실이고 무엇이 가정인가

> DAU, 피크 배수, 캐시 히트율은 설계 가정이고 로컬 측정값은 아닙니다. 현재는 설계 문서와 검증 계획을 작성한 단계입니다. 로컬에서는 중복 요청과 강제 종료 복구, API 지연과 단위 용량을 확인할 계획입니다. 월간 가용성과 글로벌 규모는 로컬 실험만으로 증명할 수 없는 부분으로 구분했습니다.

## 5. 먼저 검증할 가정

전부 첫 세션 전에 구현할 필요는 없다. 첫 세션에는 실험과 성공 조건을 설명한다. 업로드 설계가 의존하는 스토리지 호환성은 전체 구현 전에 작은 스파이크로 확인하는 것을 제안한다.

| 단계 | 실험 | 확인할 결과 |
|---|---|---|
| 세션 후, 전체 업로드 구현 전 스파이크 제안 | MinIO 체크섬·조건부 완료·서명에 포함한 Content-Length 강제 | SDK가 서명에 Content-Length와 체크섬을 포함하고, MinIO가 다른 길이·내용을 거절하는가 |
| W3 | 메타데이터 API 부하 | 조건을 기록하고 p99 200ms 목표를 지키는 최대 QPS 측정 |
| W4 | 동시·순차 완료 요청 | 세션·영상 상태가 일관되고 해당 완료의 Outbox 행이 하나인가 |
| W4 | 스토리지 완료 직후 API 종료 | 재요청이 기존 객체를 확인하고 DB 상태와 Outbox 기록을 복구하는가 |
| W4 | 전송 중단 후 로컬 상태를 지우고 재개 | 이미 올라간 파트를 확인하고 빠진 파트만 전송하는가 |
| W4 | 완료 요청과 만료 정리의 Abort를 동시에 반복 | 완료와 중단 중 하나만 성공하고, 원본 유무와 세션·영상 상태가 일치하는가. 둘 다 성공하면 현재 복구 순서를 재검토한다 |
| W5 | 워커 강제 종료와 작업 중복 전달 | 유효한 시도만 결과를 확정하고 작업이 복구되는가 |
| W6 | 재생 중 업로드·워커 경로 장애 | 준비된 영상의 재생이 계속되는가 |
| W6 | 복제 지연 중 공개 범위를 비공개로 바꾸고 동시 조회 | 옛 공개 레코드가 캐시에 재삽입되지 않고, 권한 검사가 옛 공개 값으로 통과하지 않는가 |

세부 실험은 [ADR-0006의 결정 전 검증](../adr/0006-upload-path.md#5-결정-전-검증)과 [용량 산정 방법](../capacity/00-method.md)을 따른다. 측정 결과는 조건과 원시 수치를 함께 남긴다.

## 6. 멘토에게 요청할 피드백

> 이번에는 요구사항에서 판단 기준을 제대로 도출했는지, 상태 전이와 실패 복구에 빠진 경계가 있는지, 첫 구현으로 어떤 가정부터 검증해야 하는지를 봐주시면 좋겠습니다.

- 범위가 핵심 설계 능력을 보여주기에 적절한가?
- 가장 중요한 판단 기준과 우선순위가 요구사항에서 자연스럽게 나오는가?
- 가장 강한 대안을 공정하게 비교했고, 포기한 것을 감당할 근거가 있는가?
- 완료 응답, DB 커밋, 작업 발행, 재생 가능 사이에 빠진 실패 경로가 있는가?
- 어떤 실험 결과가 나오면 현재 추천안을 바꿔야 하는가?

## 7. 세션 전후 체크리스트

### 세션 전

- [ ] 정상 경로와 실패·복구 경로를 그림으로 따라 설명한다.
- [ ] 각 선택을 요구사항 → 기준 → 대안 → 트레이드오프 → 검증 순서로 설명한다.
- [ ] Proposed 추천안을 이미 확정되거나 구현된 사실처럼 말하지 않는다.
- [ ] 트래픽 가정과 측정값을 구분한다.
- [ ] 답이 없는 부분은 미정 사항과 후속 실험으로 적는다.
- [ ] `python3 scripts/check_design.py`로 문서 구조와 링크를 검사한다.

### 세션 후

- [ ] 답하지 못한 질문을 `docs/interview/qa-bank.md`에 기록한다. 해당 파일은 필요할 때 생성한다.
- [ ] 기준의 문제인지, 설계의 누락인지, 근거 부족인지 구분한다.
- [ ] 피드백을 반영하고 결정자가 ADR의 결정 섹션과 상태를 갱신한다.
- [ ] W3의 실행 환경, DB 마이그레이션, 메타데이터 API와 첫 측정으로 넘어간다.

실험으로 새 사실을 얻으면 해당 설계·ADR·측정 문서를 갱신하고 이 가이드의 진행 체크도 함께 갱신한다.
