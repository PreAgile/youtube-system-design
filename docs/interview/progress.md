# 현재 연습 진행 상태

갱신일: 2026-10-06

## 현재 단계

**업로드·처리 경로 결정 완료(ADR-0001~0004). 재생 경로 검토 시작: 재생 중 화질 전환 질문 대기 중.**

[진행 규칙](../../AGENTS.md)과 [현재 문제 카드](../../README.md)가 기준이다. 문제 카드의 수치는 면접관이 제시한 연습용 가정이며 사용자 승인이나 구현·측정 결과가 아니다.

## 확정된 진행 방식과 요청 범위

- 문제·FR/NFR·배경지식에서 시작해 사용자가 한 질문씩 답한다.
- 대용량 업로드와 재개, 여러 화질의 글로벌 재생, 국가 간 네트워크 지연과 복구·이어보기를 다룬다. 사용자 요청으로 구독·해지·알림함·모바일 푸시는 제외한다.
- 합의한 선택만 README·ADR·실제 Excalidraw 그림에 기록한다.
- **2026-10-05 사용자 요청으로 가이드 방식 추가:** 사용자 제안을 검토할 때 다른 대안과 트레이드오프를 함께 제시하고, 면접관이 판단한 베스트 안과 이유를 알려준다. 추천은 LLM 의견이며 사용자가 고르기 전까지 결정이 아니다. 새 개념(예: SSE)은 정의부터 설명한다.
- 기본 도형, 검은 손그림 선, 짧은 이름을 사용하고 실제 렌더러에서 내보낸다.
- 이번 요청에 따라 기존 작업을 보존하고 로컬 문서·기록 구조를 초기화했다.

## README 필터링 결과

사용자가 현재 문제 카드의 추가·제외 항목을 검토하고 정리하도록 요청했다. 글로벌 재생과 네트워크 복구에 집중하도록 다음을 반영했다.

- 기기 간 동기화·동시 기기 충돌·공개 해제 후 접근 효력은 후속 주제로 분리했다. 같은 기기의 재접속·연결 복구는 유지했다.
- NFR ID는 유지했다. NFR-1·NFR-3은 해당 경로의 보조 목표로 분리하고, NFR-8은 기기 간 반영 목표에서 같은 기기의 복구 지연으로 바꿨다. 아직 관련 ADR이나 구현은 없다.
- 자동 화질 전환, 느려짐·완전 단절·복구, 접근 네트워크 RTT와 지역 간 지연의 차이를 명확히 했다.
- 코덱과 컨테이너의 정의를 추가하고, 수치·범위 조건은 연습용 가정임을 유지했다.

이 변경은 문제 카드 편집이며 사용자 기술 결정이나 가정 수치의 승인이 아니다. 조건 질문이 나오면 설명·조정하고 최소 구조 질문으로 돌아온다.

## 최소 구조: 사용자 제안 (2026-10-05)

첫 답변: `client → 백엔드 서버(API) → 객체 스토리지 + RDB`. 영상 파일은 저장소, 메타데이터는 RDB.

두 번째 답변에서 바이트 경로를 정했다.

- **업로드(사용자 선택과 이유가 명확):** client가 영상을 청크로 나눈다. 백엔드가 업로드 메타데이터를 RDB에 기록한 뒤, 청크별 업로드 URL을 저장소에서 받아 client에 준다. client가 저장소에 직접 올린다. 이유: 전송 부담을 client 쪽에 두어 백엔드 상태와 무관하게 끊기지 않게 올리기 위해서.
- **제어 정보:** 중단·재개·진행 같은 상태와 로그성 데이터는 백엔드를 거쳐 RDB에 저장한다. 이유: client가 저장소와 직접 통신하면 백엔드가 중단·재개를 알 수 없기 때문.
- **재생(제안, 검토 중):** client가 네트워크를 판단하고, 백엔드가 맞는 비트레이트의 화질 파일 URL을 주며, UDP로 실시간 전송한다.

면접관 검토(LLM 의견이며 사용자 결정 아님):

- 업로드 바이트와 제어 정보의 분리는 NFR-6의 경로 격리 방향과 맞는다.
- 빈틈: 바이트가 백엔드를 거치지 않으므로, 어떤 청크가 실제로 저장됐는지의 기준(RDB 기록 vs 저장소)과 완료 판정 시점(FR-1, NFR-7)이 정해지지 않았다.
- 재생 쪽 남은 질문: 객체 저장소의 일반적인 제공 방식(HTTP)과 UDP 제안의 관계, 재생 도중 네트워크가 바뀔 때 화질 파일 하나로 전환할 수 있는지(FR-3), 화질 판단 주체가 client인지 백엔드인지.

### 세 번째 답변: 진행 상태의 기준과 완료 판정 (사용자 제안)

- 청크 업로드 후 client가 알리기 전에 끊겨도, 저장소의 업로드 완료 이벤트(hook)가 백엔드에 전달되고 백엔드가 RDB에 기록한다.
- 재개 시 client는 백엔드를 통해 RDB를 조회해 이어 올린다.
- 진행 상태의 기준은 RDB 기록이다. 저장소의 실제 상태는 이벤트로 비동기 반영한다.
- 모든 청크의 이벤트를 받아 RDB의 청크 수·진행률이 다 차면 완료로 표시한다. client 표시는 SSE로 받는다.

면접관 검토와 추천(LLM 의견, 사용자 결정 아님):

- 좋은 점: RDB를 저장소 이벤트로만 갱신하면 "RDB에는 완료인데 저장소에 없음"은 생기지 않는다. 어긋나도 재전송 낭비로 끝난다.
- 빈틈: 이벤트 지연·중복·순서 뒤바뀜·누락 처리, 멀티파트 방식에서 파트별 이벤트가 없을 수 있는 점(S3 기준 외부 사실, 확인 권장), 크기·무결성 검증 주체 부재(FR-1).
- 비교한 대안: (A) client 보고 기준, (B) 저장소 이벤트 → RDB 기준(사용자 제안), (C) 재개·완료 시점에 백엔드가 저장소를 직접 조회해 기준으로 삼음.
- 추천: C. 재개·완료 판정은 저장소 조회, 완료 확정은 client의 완료 요청을 받은 백엔드가 검증 후 수행. 상태 표시는 완료 요청의 동기 응답 + 처리 상태 주기 조회(폴링). SSE는 선택적 개선.

### 네 번째 답변: 결정 (2026-10-05)

- 사용자가 C를 선택했다. 이유: 가장 편하고 좋다(기준이 한 곳). ADR-0001에 기록.
- 처리 상태 확인: "폴링은 부담이 크지 않고, SSE는 서버 부담이 더 크지 않나"라고 질문. 면접관 검토: 요청 수로는 SSE가 오히려 적다. 차이는 부하보다 연결 유지와 상태 변화 전달 경로의 복잡도다. 이 규모에서는 둘 다 부하가 작다. 추천은 폴링(LLM 의견).

- 다섯 번째 답변: 폴링 선택. 이유는 현재 규모의 부하가 작고, stateless라 스케일 아웃된 서버에서도 단순하며, SSE는 stateful 연결·라우팅·재연결 복잡도가 있다는 것. 조회 부하가 크거나 한 화면을 많은 client가 동시에 볼 때는 SSE가 적합하다고 판단. ADR-0002에 기록.

### 변환 실행 위치: 사용자 제안 (검토 중)

- 사용자 제안: API 서버에서 직접 변환하면 구현이 복잡하다. 대기업은 자체 최적화를 하겠지만, 그렇지 않다면 외부 변환 서비스에 맡기고 서버는 결과를 받는 것이 운영이 단순하다. 화질별 처리 시간, CPU·메모리 사용량, 서버 부담 처리가 문제일 것 같다고 했다(경험 없음을 밝힘).
- 면접관 검토(LLM): API 서버 직접 변환의 문제는 자원 경쟁(NFR-1·NFR-6), 긴 작업 중 서버 장애·재배포 시 "처리 중" 고착, API와 변환의 확장 기준 불일치다. 실행 주체와 별개로 "비동기 변환 작업 + 작업 상태 기록 + 완료 신호" 구조가 필요하다. 외부 서비스도 완료 신호 유실 시 재조회가 필요하다(ADR-0001의 B와 같은 문제). 비교안: A 직접, B 자체 작업자 + 작업 대기열, C 관리형 외부 서비스. 추천: B(이 규모에서 화질별 우선순위·재시도·비용 통제). C는 작은 규모에서 타당. 비용 우위는 단가 확인 전 미검증.
- 개념 질문: SSE에서 상태 변화를 연결을 가진 서버까지 전달하는 방식(전체 브로드캐스트, 연결 위치 기록 후 직접 전달, 해시 기반 고정 배치, 서버 내부 폴링)을 설명함.

### 변환 실행 주체 결정과 실패 처리 제안 (2026-10-06)

- 사용자가 B를 선택. 이유는 ADR-0003에 기록.
- 실패 처리 사용자 제안: 서버가 헬스체크로 작업자 생존과 작업 진행을 계속 확인하고, 죽으면 다른 서버로 옮기거나 확장해 마저 작업한다.
- 면접관 검토(LLM): 서버 생존과 작업 진행은 다르다(살아 있지만 멈춘 작업). 중앙 감시자는 단일 장애점이 되고, 네트워크 단절 시 오판으로 같은 작업이 두 번 실행될 수 있다. 변환은 중간부터 이어가기 어려워 보통 작업 단위를 처음부터 다시 한다. 장애 복구와 부하에 따른 확장은 별개 문제다. 비교안: 중앙 헬스체크, 작업 임대(lease) + 작업별 진행 보고, 주기적 정리 작업(스위퍼), 작업 단위 쪼개기, 재시도 상한 + 실패 상태. 추천: 작업 임대 + 작업별 진행 보고 + 화질 단위 작업 + 재시도 상한 후 실패 상태 + 결과 저장과 상태 갱신의 멱등 처리.

- 사용자 평가: 중앙 헬스체크는 단일 장애점, 멈춘 작업 누락, 감시자 집중으로 유연성 부족, 중복 실행·재시도 상한 미고려. 스위퍼는 단순하지만 대략적이라 NFR을 단독으로 충족하기 어렵다.
- 개념 질문(임대 기록 위치, 고정 위치, 조건부 갱신 조건, 실패 인지 주체, 대기열과 Kafka의 관계)에 답했다.
- 면접관 정정(LLM): 앞서 "결과를 고정 위치에 덮어쓰기"를 권했으나, 화질 결과가 여러 파일이면 두 실행의 파일이 섞일 수 있다. 시도별 위치에 쓰고 조건부 갱신으로 RDB가 승자 위치를 가리키게 하는 방식을 추천으로 바꿨다. 패배한 시도의 파일은 정리 작업이 지운다.
- 면접관 추천(LLM): 현재 규모에서는 RDB의 변환 작업 표를 대기열로 사용(임대 만료 시각·임대 번호·시도 횟수 기록). 별도 대기열 시스템은 규모·격리 요구가 커질 때 검토. Kafka는 분 단위 개별 작업의 임대·재시도에 기본적으로 맞지 않는 로그 구조라고 설명(버전별 기능은 확인 필요).

- 사용자가 실패 처리 추천 조합과 "RDB 작업 표로 시작, 부하 시 큐로 이전"을 확정했다. ADR-0004에 기록.
