# Design YouTube, 영상 업로드와 스트리밍

영상을 올리면 몇 분 안에 모든 기기에서 볼 수 있게 만들고, 시청 폭주가 업로드와 원본 데이터를 흔들지 않도록 설계하는 백엔드 시스템

이 저장소는 YouTube의 핵심 경로(업로드, 트랜스코딩, 재생, 메타데이터, 조회수)를 시스템 디자인 인터뷰 형식으로 설계하고, 백엔드를 실제로 구현해 로컬에서 측정한 수치로 그 설계를 검증합니다. 앞부분은 설계 문서이고, 뒷부분은 이 저장소가 어떤 구조로 진행되고 문서를 어떻게 쓰는지 설명합니다.

## 1부. 설계

요구사항의 원문과 ID 정의는 [docs/design/00-scope.md](docs/design/00-scope.md)가 기준입니다. 이 README는 그 문서와 ADR을 한 번에 읽을 수 있게 요약합니다. 둘이 다르면 00-scope.md와 ADR이 맞습니다.

### Introduction & Requirements

크리에이터가 10분짜리 여행 영상을 올립니다. 휴대전화로 찍은 원본은 수백 MB이고, 업로드는 지하철에서 시작해 집 Wi-Fi에서 끝납니다. 업로드가 끝나고 몇 분 뒤 구독자가 알림을 누르면, 스마트폰에서는 360p로 먼저 재생이 시작되고 네트워크가 좋아지면 화질이 올라갑니다. 같은 시각 거실 TV에서 보는 다른 구독자는 1080p로 봅니다. 화면 아래 조회수는 조금씩 늘어납니다.

사용자에게는 영상 하나지만 서버가 하는 일은 서로 다릅니다. 업로드는 큰 파일을 끊김 없이 받아 안전하게 저장하는 일입니다. 트랜스코딩은 원본 하나를 여러 해상도로 바꾸는, 몇 분에서 몇 시간이 걸리는 계산입니다. 재생은 수많은 사람에게 같은 조각을 빠르게 나눠 주는 일이고, 조회수는 짧은 시간에 몰리는 작은 쓰기를 모아 세는 일입니다.

가장 단순한 구현은 API 서버가 파일을 받아 디스크에 저장하고, 요청이 오면 그 파일을 통째로 내려 주는 방식입니다. 사용자가 적다면 이것으로 충분합니다.

사용자가 늘면 이 구조가 무너지는 순서가 있습니다. 업로드 몇 개가 API 서버의 대역폭과 연결을 붙잡고, 그동안 메타데이터 조회까지 느려집니다. 원본 파일 하나를 모든 기기에 그대로 보내면 느린 네트워크의 사용자는 재생을 시작하지 못합니다. 조회마다 DB의 조회수 행을 UPDATE하면, 인기 영상 하나의 행 잠금이 전체 쓰기 처리량을 결정합니다.

이 시스템에서 가장 어려운 상태는 영상이 "있다"와 "볼 수 있다" 사이에 있는 시간입니다. 업로드는 끝났지만 트랜스코딩은 진행 중이고, 360p는 준비됐지만 1080p는 아직입니다. 워커가 인코딩 도중 죽으면 같은 작업이 다시 돌고, 업로드 완료 알림이 두 번 올 수도 있습니다. 이 사이 상태를 어떻게 저장하고 누구에게 어떤 일관성으로 보여줄지가 설계의 중심입니다.

그래서 업로드, 트랜스코딩, 재생, 집계 경로를 분리합니다. 한 경로의 부하와 장애가 다른 경로로 번지지 않게 하는 것이 먼저입니다.

### 공개된 사실과 이 설계의 범위

2026년 9월에 확인한 YouTube 고객센터 안내에 따르면, 인증된 계정은 256GB 또는 12시간 중 작은 쪽까지 영상 하나를 올릴 수 있습니다. 같은 고객센터는 낮은 해상도가 먼저 처리되고 HD와 4K는 더 오래 걸린다고 설명하며, 조회수는 실제 시청인지 검증하는 과정 때문에 늦게 반영될 수 있다고 안내합니다.

Google은 2021년 ASPLOS 논문 「Warehouse-Scale Video Acceleration」에서 YouTube 트랜스코딩용 전용 칩(VCU)을 공개했습니다. YouTube의 MySQL 샤딩 계층인 Vitess는 YouTube에서 만들어져 공개된 오픈소스입니다.

아래의 스키마, 큐, 상태 머신, API, 수치는 위 공개 동작을 만족시키기 위한 설계 가정입니다. YouTube의 실제 내부 구현을 재현한 명세가 아닙니다. 출처 링크는 [00-scope.md의 참고 자료](docs/design/00-scope.md#참고-자료)에 있습니다.

### Functional Requirements

FR-1. 크리에이터는 영상 파일을 업로드할 수 있습니다. 전송이 끊기면 처음부터가 아니라 끊긴 지점부터 다시 보낼 수 있습니다.

FR-2. 시스템은 원본을 여러 해상도의 스트리밍 형식으로 변환합니다. 낮은 해상도가 준비되면 높은 해상도를 기다리지 않고 재생할 수 있고, 크리에이터는 처리 상태를 확인할 수 있습니다.

FR-3. 시청자는 영상을 스트리밍으로 재생합니다. 네트워크에 따라 화질이 자동으로 바뀌고, 원하는 위치로 이동할 수 있으며, 비공개 영상은 권한이 있는 사람만 봅니다.

FR-4. 사용자는 영상의 제목, 설명, 채널, 게시 시각, 조회수와 채널별 최신 영상 목록을 조회합니다. 크리에이터는 제목, 설명, 공개 범위를 수정합니다.

FR-5. 시스템은 영상별 조회수를 집계합니다. 같은 시청이 여러 번 세어지지 않고, 결과는 짧은 지연 뒤에 반영될 수 있습니다.

### Non-Functional Requirements

아래 수치는 이 설계의 목표이며 YouTube의 공개 SLA가 아닙니다.

| ID | 목표 | 이렇게 둔 이유 |
|---|---|---|
| NFR-1 | 재생 경로 월간 가용성 99.99% | 업로드나 트랜스코딩이 멈춰도 이미 준비된 영상은 계속 재생되어야 함 |
| NFR-2 | 업로드 경로 월간 가용성 99.9% | 업로드는 재시도할 수 있고 실패가 한 사람에게 국한됨 |
| NFR-3 | 재생 버튼부터 첫 화면까지 p95 2초 | API, 매니페스트, 첫 세그먼트 세 구간을 따로 측정 |
| NFR-4 | 메타데이터 API 서버 처리 p99 200ms | 요청 수로 가장 바쁜 서버 |
| NFR-5 | 완료 응답을 준 원본은 유실 없음 | 트랜스코딩이 실패해도 원본으로 다시 처리 |
| NFR-6 | 크리에이터는 자기 변경을 즉시 봄, 조회수는 1분 안에 반영 | 쓴 사람과 보는 사람의 일관성 요구가 다름 |
| NFR-7 | 두 번 처리해도 같은 결과, 인스턴스 추가로 수평 확장, 경로 간 격리 | 재시도와 중복 전달은 정상 상황 |
| NFR-8 | 비용은 이그레스, 저장, 인코딩 계산량을 함께 평가 | 이그레스가 비용의 대부분 |

### Out of Scope

추천과 홈 피드 랭킹, 라이브 스트리밍, 광고와 수익화, Content ID, DRM, 댓글, 좋아요, 구독, 검색, 프론트엔드는 구현하지 않습니다. 각각은 시스템 하나 규모이거나 이미 다루는 패턴의 반복입니다. 좋아요, 구독, 제목 검색은 핵심 경로가 끝난 뒤의 Stretch로 둡니다.

### Traffic & Capacity Assumptions

DAU 1억 명, 한 명이 하루 5편을 보고, DAU의 0.5%가 하루 한 편을 올린다고 가정합니다. 피크는 평균의 3배입니다.

| 경로 | 피크 규모 | 커지는 단위 | 설계에 주는 의미 |
|---|---|---|---|
| 세그먼트 전송 (읽기) | 초당 약 130만 건, 약 13Tbps | 바이트 | CDN이 대부분을 흡수해야 함. 히트율 95%여도 원본에 초당 약 6만 5,000건 |
| 메타데이터 조회 (읽기) | 초당 약 6만 9,000건 | 요청 수 | 캐시와 읽기 복제본 |
| 조회 이벤트 (쓰기) | 초당 약 1만 7,400건, 핫 영상 하나에 초당 약 170건 | 요청 수, 핫 키 | 행 UPDATE가 아니라 버퍼링 집계 |
| 업로드 (쓰기) | 초당 약 17건, 약 42Gbps | 바이트, 연결 시간 | 바이트가 API 서버를 지나지 않게 |
| 트랜스코딩 | 하루 250만 분 × 4해상도 | 계산량 | 워커 격리, 큐 적체 관리 |
| 메타데이터 쓰기 | 초당 약 170건 | 요청 수 | 쓰기는 작음. 샤딩은 읽기와 저장량 때문 |

요청 수로 보면 메타데이터 읽기와 쓰기는 약 400대 1이고, 바이트로 보면 이그레스와 업로드 유입은 약 300대 1입니다. 두 비율 모두 읽기 중심이라는 같은 결론이지만, 줄이는 수단이 다릅니다. 메타데이터는 캐시로, 영상 바이트는 CDN으로 줄입니다.

이 숫자들은 출발점이 아닙니다. 필요한 대수는 로컬에서 부품 하나가 SLO를 지키며 처리하는 양(단위 용량)을 잰 뒤 `필요 대수 = 피크 부하 / (단위 용량 × 목표 사용률)`로 계산합니다. 방법은 [docs/capacity/00-method.md](docs/capacity/00-method.md)에 있습니다.

## 2부. 이 저장소가 진행되는 방식

### 한 주의 흐름

멘토 세션이 주 1회 있고, 한 주는 세션을 중심으로 돕니다. 주차별 산출물은 [docs/roadmap.md](docs/roadmap.md)에 있습니다.

1. **세션 전:** 그 주의 설계 문서, 구현, 측정을 만들고 ADR 초안을 `Proposed`로 올립니다. PR을 열어 CI와 리뷰 봇의 검증을 받습니다.
2. **세션:** 설계를 발표하고 질문을 받습니다.
3. **세션 후:** 답하지 못한 질문은 `docs/interview/qa-bank.md`에 적고, ADR의 7장 "결정"을 결정자가 직접 쓴 뒤 `Accepted`로 바꿉니다.

정지선은 W9입니다. Stretch 기능은 W9까지 끝난 뒤에만 손댑니다.

### 저장소 구조

```
docs/
  design/       요구사항(00-scope.md), 이후 API, 데이터 모델, HLD, 딥다이브
  adr/          설계 결정 기록. 목록은 README.md, 템플릿은 0000-template.md
  capacity/     로컬 측정 방법, 측정 결과, DAU 1억 환산, 글로벌 설계
  interview/    발표 순서, 꼬리질문 대비
  review-policy.md  리뷰가 검증하는 질문 Q1~Q10
  roadmap.md        주차별 진행 계획
scripts/
  check_design.py   ADR 구조와 요구사항 연결을 검사하는 CI 스크립트
excalidraw/     다이어그램 원본 (.excalidraw)
```

### 결정을 기록하는 방법

모든 결정은 FR이나 NFR 하나 이상에 연결됩니다. 연결되지 않는 결정은 범위 밖으로 뺍니다. 언어, 프레임워크, 인프라 선택도 예외가 아닙니다.

새 ADR은 [0000-template.md](docs/adr/0000-template.md)를 복사해 다음 번호로 만듭니다. 섹션 11개가 정해져 있고, CI가 순서와 이름을 검사합니다.

| 섹션 | 쓰는 것 |
|---|---|
| 1. 맥락 | 무엇을 정해야 하고, 미루면 무엇이 막히나. 부하 모양을 숫자로 |
| 2. 결정을 강제하는 요구사항 | 필수 조건(못 맞추면 탈락), 우선순위를 둔 결정 기준, 전제, 기준에서 뺀 것 |
| 3. 선택지 | 후보 전부와 거르는 단계. 가장 강한 대안을 반드시 남김 |
| 4. 평가 | 결정 기준별 비교와 종합 |
| 5. 결정 전 검증 | 로컬에서 가정을 확인하는 측정 |
| 6. 추천안 | 추천, 잃는 것, 다른 선택지가 맞는 경우, 면접용 30초 답변 |
| 7. 결정 | 결정자가 직접 씀. 추천과 다르면 이유를 남김 |
| 8. 결과 | 치르는 비용, 새로 생기는 문제, 후속 ADR |
| 9. 이 결정이 깨지는 조건 | 다시 열어야 하는 구체적 사건이나 수치 |
| 10. 운영에서 볼 지표와 장애 대응 | 결정이 맞았는지 운영에서 판단하는 지표 |
| 11. 예상 꼬리질문 | 면접관이 물을 질문과 답의 요지 |

상태는 `Proposed`에서 시작해 결정자가 7장을 쓰면 `Accepted`가 됩니다. Accepted된 ADR은 고치지 않고 새 ADR로 대체(`Superseded by ADR-XXXX`)합니다. 허용되는 예외는 [review-policy.md 5장](docs/review-policy.md)에 있습니다.

### 문서를 쓰는 규칙

- **결정은 프로덕션 기준으로 합니다.** "로컬에서 재기 편해서"는 근거가 아닙니다. 로컬 환경은 결정한 설계를 측정하는 도구입니다.
- **"가능한가"로 고르지 않습니다.** 대부분의 후보는 장치를 더하면 요구사항을 맞춥니다. 가장 중요한 기준을 기본값으로 충족하는지, 나머지 비용이 얼마인지로 고릅니다.
- **근거는 강한 것부터 씁니다.** 로컬 측정값(조건 포함), 공식 문서와 소스 코드, 공개 운영 사례, 일반론 순입니다. 공식 문서와 사례에는 출처 링크를 답니다. 확인하지 못한 주장은 쓰지 않거나 가정이라고 표시합니다.
- **숫자는 조건과 함께 씁니다.** 조건 없는 측정값은 환산에 쓰지 않습니다.
- **잃는 것을 반드시 씁니다.** 얻는 것만 있는 결정은 리뷰에서 지적됩니다.
- **긴 대시(U+2014, U+2013)를 쓰지 않습니다.** CI가 검사합니다.

### PR과 리뷰

모든 변경은 브랜치에서 PR로 올립니다. 리뷰는 코드 품질보다 결정의 논리(왜, 트레이드오프, 왜 최선인가)를 먼저 검증하며, 기준은 [docs/review-policy.md](docs/review-policy.md)의 Q1~Q10입니다.

1. PR 본문은 [PR 템플릿](.github/pull_request_template.md)을 따릅니다. 관련 FR/NFR, 결정, 얻는 것, 잃는 것, 버린 대안을 적습니다. PR 본문에 적은 ADR 번호는 파일이 실제로 있어야 합니다. 의존성 갱신인 Dependabot PR은 본문 검사를 건너뜁니다.
2. CI(`design-checks`)가 구조를 검사하고, 리뷰 봇이 논리의 빈틈을 찾습니다.
3. 모든 지적은 실제 문서와 공식 자료에 대조해 반영하거나, 근거를 들어 답글로 반박합니다. 봇의 지적을 그대로 받아들이지 않습니다.
4. CI가 통과하고 지적을 모두 처리하면 머지합니다.

| 검증자 | 맡는 것 | 설정 |
|---|---|---|
| CI | ADR 섹션 구조, 선택지 수, 요구사항 ID 존재, Accepted ADR 불변, 목록과 파일 일치, 깨진 링크, 긴 대시 | `scripts/check_design.py`, `.github/workflows/design-checks.yml` |
| CodeRabbit | Q1~Q10으로 논리 검증 | `.coderabbit.yaml` |
| Qodo Merge | 논리와 예시 코드의 결함 | `.pr_agent.toml` |
| Sourcery | 반례 조건 탐색 | 기본 설정 |
| 멘토 세션 | 범위 선택의 타당성, 면접관 관점의 설득력 | |

### 로컬에서 검사하기

```bash
python3 scripts/check_design.py                     # 전체 검사
python3 scripts/check_design.py --base origin/main  # Accepted ADR 불변 검사 포함
PR_BODY="$(cat body.md)" python3 scripts/check_design.py  # PR 본문 검사 포함
```
